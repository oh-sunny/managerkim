# 보낼 내용 확인 화면 수정 방향

작성일: 2026-10-07  
상태: 논의·수정 이유를 남기는 문서. **구현 기준은 [SPEC 003](../spec/spec_003.md)**이며 화면·동작·배포는 아직 이 문서에 따라 수정하지 않음.

## 운영 담당자가 웹을 사용하는 흐름

기존 행사·복지 프로젝트를 운영하던 담당자가 새 프로젝트를 시작하는 경우다. **티켓은 검토할 일을 알려주며, 공지를 자동 발송하지 않는다.**

1. **새 프로젝트 등록:** 관련 문서·기본 정보를 넣는다. 시스템이 운영 정보 후보를 채우고, 담당자가 누락·충돌을 확인해 프로젝트 정보를 저장한다. 공지에 사용할 정보 요약도 저장된 프로젝트 값에서 자동 준비된다.
2. **안내 점검 시점 설정:** 첫 안내를 언제 검토할지 정하고 리마인드 점검 규칙을 확인한다. 현재 기본 규칙은 **D-3·D-1 오전 10시, 마감 4시간 전**의 필수 미신청자 점검이며 프로젝트별 조정이 가능하다. 첫 안내는 현재 등록 시 준비 티켓을 즉시 만들므로, 별도의 첫 안내 예약일 선택은 추가할 기능이다.
3. **티켓 생성·확인:** 정해진 시점에 최신 신청 현황과 규칙을 비교해 필요한 티켓을 만든다. 화면에는 이유·대상 수·현황 확인 시각을 표시하고, 담당자가 티켓을 열어 안내 여부를 결정한다. 신청 상태와 조건이 달라지면 미발송 티켓을 갱신하거나 종료한다.
4. **공지 문구 작성:** 새 티켓은 그때 저장된 **최신 프로젝트 정보**로 시작한다. Gemini가 목적·말투에 맞는 문구를 제안하고, 담당자는 채택·직접 수정한다. 이전 안내의 보충 정보는 필요할 때만 참고한다.
5. **자료와 대상 검토:** 이번 공지에 넣을 링크·파일을 명시적으로 고른다. 최신 신청 현황에서 DM 수신자 또는 게시 채널을 확인한다. 분석용 문서는 자동 첨부하지 않는다.
6. **최종 확인·기록:** 본문·자료·대상을 확인하고 원본 신청 현황을 발송 직전에 다시 확인한다. 현재 범위에서는 **모의 발송** 결과를 기록하고, 다음 점검 때 바뀐 신청 상태를 다시 본다. 실제 Slack 발송은 이번 화면 개편의 우선 작업에서 제외한다.

이 흐름은 **목표 사용자 경험**이다. 자료의 후보 분석·프로젝트 저장·규칙 티켓·모의 발송은 일부 구현돼 있으나, 첫 안내 예약 시점 설정과 신규 프로젝트의 등록부터 결과 확인까지 이어지는 실제 계정 브라우저 검증은 남아 있다. 예시 시트의 서버 정기 실행 상태와 한계는 아래 정기 실행 절을 따른다.

## 1. 목표와 범위

운영자가 **프로젝트 등록·수정에서 분석용 자료와 기본 정보를 한 번 정리하고**, 안내 작성 화면에서는 이를 다시 입력하지 않고 메시지·공지에 포함할 자료·수신자를 검토하도록 한다.

1. **신청 원본**: 누구에게 안내할지 판단하는 Google Sheets 현황과 마지막 확인 시각.
2. **이번 안내의 정보**: 새 공지를 열 때 현재 저장된 프로젝트 정보로 자동 준비한 요약. 이전 안내의 보충 정보는 필요할 때만 참고한다.
3. **메시지 초안**: 확인한 정보와 공지 목적·말투로 Gemini가 작성한 후보 또는 운영자가 직접 쓴 본문.
4. **저장·발송 상태**: 저장 중·저장 완료·저장 실패, 최종 확인, 모의 발송 기록을 필요한 순간에만 구분한다. 브라우저 보관 방식은 기본 화면의 설명 대상이 아니다.

제품의 전체 흐름인 `운영 정보 등록 → 신청 현황 확인 → 안내 필요 판단 → 초안·대상 검토 → 승인 후 발송 → 결과 저장·재확인`은 유지한다. 이 문서는 **검토 화면의 정보 구조와 상호작용**을 제안하며 실제 Slack 발송, AI의 신청 현황 분석, 조직 공동 권한을 이번 화면 개편의 완료 범위에 넣지 않는다.

## 3. 권장 정보 구조: 프로젝트에서 준비, 안내에서 작성

**권장안은 등록·수정과 공지 작성을 분리하고, 안내 작성 화면에서 10개 입력 상자 형태의 카드를 없애는 것이다.** 정보 카드 자체는 AI에 전달할 정보와 발송 당시의 근거를 보존하는 내부 데이터로 유지한다. 화면에는 자동 준비한 프로젝트 정보를 짧게 요약한다. 누락·충돌·변경이 있을 때만 `프로젝트 정보 수정` 또는 `이번 안내만 수정`을 연다. 내부 운영 정보와 구성원에게 알릴 정보가 다를 수 있으므로, 프로젝트 전체 수정과 이번 안내의 예외 수정은 구별한다.

### A. 프로젝트 등록·수정

1. 운영자가 기본 정보를 입력하거나 자료 파일을 분석한다. 분석 결과는 **후보**이므로 충돌·누락을 확인하고 필요한 값을 선택 적용한다.
2. 프로젝트에 필요한 운영 정보와 구성원 안내에 쓸 정보를 함께 확정한다. 카드 항목은 입력된 프로젝트 값과 적용한 문서 근거로 자동 채운다. 사용자가 동일 내용을 공지 화면에서 다시 입력하게 하지 않는다.
3. `안내에 사용할 정보` 미리보기에서 무엇을·대상·해야 할 일·마감·방법·링크 등과 출처를 확인한다. 확인 필요 항목만 작업 목록으로 보여준다.
4. 프로젝트 정보를 수정·저장하면 **그 뒤에 새로 작성하는 모든 공지와 리마인드는 수정된 정보를 기본값으로 사용한다.** 작성 중이던 초안만 이전 값이 남아 있는지 확인한다.

**현재 구현 범위:** 자료를 넣고 `자료 분석하기`를 누르면 Gemini가 프로젝트 입력값의 후보를 제시한다. 운영자가 후보를 선택 적용하고 프로젝트를 저장하면, 새 안내의 카드는 저장된 프로젝트 필드에서 자동으로 채워진다. 이 마지막 카드 변환은 별도의 Gemini 분석이 아니라 필드 매핑과 문장 분류 규칙이며, 비용·예외처럼 확인이 필요한 값이 남을 수 있다. 따라서 `파일을 넣자마자 모든 카드 항목이 완성·확정됨`은 아직 구현되지 않았다. 이전 안내의 보충 정보 재사용도 아직 없다.

### B. 공지·리마인드 작성

```text
보낼 내용 확인 · 가을 워크숍
  현재 단계: ① 작성 기준 확인 → ② 초안 작성 → ③ 자료 선택 → ④ 대상 확인 → ⑤ 최종 확인

① 작성 기준 확인
  공지 목적: 첫 안내 / 추가 신청 안내 / 마감 알림
  자동 준비한 프로젝트 정보 요약: 해야 할 일 · 마감 · 신청 링크 등
  기본값: 현재 저장된 프로젝트 정보
  필요한 경우에만 이전 안내의 보충 정보 참고
  변경·누락·충돌만 강조 → 프로젝트 정보 수정 / 이번 안내만 수정

② 메시지 초안
  말투 선택 → "Gemini로 새 초안 문구 생성"
  버튼 바로 위에 이번 초안에 사용할 정보 요약 표시
  생성 후보와 현재 본문 비교 → 적용 / 유지
  직접 작성·수정 가능, "임시 저장 중/임시 저장됨" 상태를 본문 근처에 표시

③ 이번 안내에 포함할 자료
  프로젝트의 재사용 가능한 안내 자료에서 선택하거나 새 링크·파일 추가
  링크는 본문에 들어갈 문구·주소를, 파일은 별도 첨부 목록을 확인
  분석용 파일은 자동으로 공지에 포함하지 않음

④ 대상과 신청 현황
  현재 신청 원본과 마지막 성공 시각, 선택 대상 수 표시
  "신청 현황 새로고침"을 수신자 검토 옆에 배치
  DM/채널, 미신청/전체, 팀/개인 선택과 최종 명단 확인

⑤ 최종 확인
  본문 · 대상 · 링크/파일 · 원본 확인 시각을 다시 표시
  확인 체크 후 모의 발송, 결과 기록
```

데스크톱에서는 ② 본문·③ 자료와 ④ 대상을 나란히 배치해도 된다. 좁은 화면에서는 위 순서로 한 열에 놓는다. 현재의 고정 확인 막대가 요약이나 후보 비교를 가리지 않도록 높이와 위치를 조정한다. **10개 카드 입력 상자를 작성 화면에 상시 펼치지 않는다.** 이번 안내에만 필요한 변경은 별도의 작은 편집 화면에서 처리하며, 수정 전후와 적용 범위를 명시한다.

### 공지에 넣을 자료와 분석용 자료의 구분

- **분석용 자료:** 프로젝트를 등록·수정할 때 정보를 추출하기 위해 넣는 기획서·관련 파일. 공지에 자동 첨부하지 않는다. 현재 원본 파일은 프로젝트의 재사용 자료 목록에 저장되지 않는다.
- **공지에 포함할 자료:** 작성 화면의 본문 아래에서 운영자가 **이번 안내에 사용할 것만 직접 선택**한다. 링크는 표시 문구와 URL을 확인해 본문에 넣고, 파일은 본문과 구별되는 첨부 카드로 보여준다. 최종 확인에는 본문 링크와 파일명을 모두 나열한다.
- **재사용:** 프로젝트에 자주 쓰는 안내 링크·파일의 목록을 두어 첫 안내와 리마인드에서 다시 선택할 수 있게 한다. 이전 안내의 자료는 `지난 안내에 사용`으로 제안할 수 있지만 자동 첨부하지 않는다. 오래된 파일 버전·접근 불가 링크는 다시 확인한다.
- **이번 안내만 추가:** 프로젝트 자료 목록에 없는 링크나 파일도 작성 중 바로 추가할 수 있다. 프로젝트 공통 자료로 저장할지, 이번 안내에서만 쓸지는 선택할 수 있게 한다.
- **Gemini와의 관계:** 첨부한 파일 내용이 자동으로 Gemini 초안 생성에 들어가는 것은 아니다. 초안 작성에 반영하려면 프로젝트 정보 분석을 거쳐 확인한 정보로 사용한다. 안내를 받는 동료에게 파일을 보내는 것과 Gemini에게 파일을 읽히는 것은 별도 동작으로 표시한다.

현재 코드는 작성 화면에서 새 링크·파일을 추가하고 최종 확인·모의 기록에 선택 자료를 표시한다. 링크는 본문에도 삽입하며 파일은 계정별 비공개 저장소 업로드 경로가 있다. **프로젝트 공통 안내 자료 목록과 이전 안내 자료 선택은 아직 구현되지 않았다.** 실제 Slack 파일 전송과 발송 자료 검사도 미구현이며, 업로드·복원의 실제 계정 브라우저 흐름은 별도 검증이 필요하다.

### 새 공지와 리마인드의 정보 사용 순서

- **새 공지의 기본값은 언제나 현재 저장된 프로젝트 정보다.** 프로젝트 마감·장소·신청 링크를 수정했다면 이후 처음 작성하는 공지와 리마인드 모두 새 값을 사용한다.
- 이전 안내는 프로젝트 정보에 없는 보충 설명이나 표현을 참고할 때만 연다. 이전 카드의 마감·장소·링크가 현재 프로젝트 값보다 우선하지 않는다. 이전 Gemini 문장, 과거 수신자, 과거 신청률도 자동 복사하지 않는다.
- 이전 안내에만 적었던 보충 정보를 다시 쓰고 싶다면 운영자가 이번 안내에 추가한다. 이를 위해 보낸 안내에 당시 사용한 정보와 본문을 남기되, **새 안내를 만드는 데 별도의 프로젝트 카드 버전 저장소가 필요한 것은 아니다.**
- 프로젝트를 수정하기 **전에 이미 작성 중이던 초안**은 예외다. 이때는 초안에 남은 예전 마감·링크를 알려주고, 본문을 다시 확인하기 전에는 보내지 못하게 한다.

### 버튼 위치와 문구

- 생성 버튼은 처음이든 다시 생성할 때든 **`Gemini로 새 초안 문구 생성`**으로 통일하고, **공지 목적·말투·이번 초안에 사용할 정보 요약 뒤, 메시지 본문 바로 앞**에 둔다. 말투를 바꿔도 현재 본문을 유지하며, 버튼을 눌렀을 때만 새 문구를 요청한다. 이전 생성 후보는 새 말투와 맞지 않는다고 표시해 적용을 막는다.
- `임시 저장`은 작성 중인 카드·본문·대상 선택을 보관하는 동작으로, Gemini 생성과 별개다. 현재 구현은 입력 후 자동 저장을 시도하므로 별도 `임시 저장` 버튼을 추가하지 않고 **`임시 저장 중` / `임시 저장됨` / `저장 실패`**를 상태로 보여준다. 사용자가 누르는 저장 버튼을 도입한다면 자동 저장을 계속할지와 버튼의 역할을 먼저 정한다.
- 새 후보는 현재 본문을 자동으로 덮지 않는다. `새 초안 적용`과 `현재 본문 유지`를 같은 자리에서 선택하고, 작성 기준 변경으로 후보가 무효해졌다면 이유를 표시한다.
- `신청 현황 새로고침`은 대상 확인 영역으로 옮긴다. 화면 상단에는 최신성 요약만 남긴다. 새로고침은 Gemini 생성과 무관함을 명시한다.
- 말투는 서로 다른 작성 결과를 예상할 수 있게 `밝고 친근하게`, `간결하고 명료하게`, `정중하고 차분하게`, `행동 요청 중심으로`처럼 구분한다. 각 옵션 아래에 한 줄 예시 또는 작성 특징을 보여준다. 서버가 지원하지만 화면에 없는 `formal`과 실제 선택지를 맞춘다.

## 4. 데이터 흐름과 저장 계약

| 데이터 | 만들어지는 곳 | 사용처 | 저장·복원 원칙 |
| --- | --- | --- | --- |
| 운영 정보·적용한 문서 근거 | 프로젝트 등록/수정 | 프로젝트 기본 정보와 카드 자동 채움 | 로그인 계정의 `operator_states`에 저장. 원본 파일 자체는 현재 별도 보관하지 않음 |
| 새 안내의 기본 정보 | 새 공지를 열 때 현재 저장된 프로젝트 값에서 자동 구성 | 모든 새 공지와 리마인드의 기본값 | 별도 프로젝트 카드 버전 저장소 없이 현재 프로젝트 정보를 읽는다 |
| 신청 현황 | Sheets 수동 조회와 서버 정기 동기화 결과 | 안내 필요 판단, 수신 대상, 모의 발송 직전 재확인 | 원본 확인 시각과 조회 실패를 대상 영역에 표시. Gemini 초안 생성에는 자동으로 사용하지 않음 |

| 말투·공지 목적 | 초안 작성 영역 | Gemini 작성 규칙 | 정보 카드와 함께 초안에 저장 |

Gemini 요청 전에는 `이번 초안에 사용할 정보 요약`을 짧게 보여준다. 프로젝트 제목, 선택한 공지 목적·말투, **확인됨이면서 이번 초안에 포함된 카드 값**만 Gemini 본문 작성에 사용한다. 미확인·충돌·제외 항목, 수신자 명단, 신청률, 문서 원본, 첨부 파일은 현재의 초안 생성 자료가 아니다. 카드 전체 객체는 앱 서버로 전송돼 검증되므로, 화면 문구에서는 `Gemini에 사용`과 `서버로 전송`을 혼동하지 않게 설명한다. 문서 분석에 Gemini를 쓰는 **프로젝트 등록 단계**는 별도의 요청이다.

**사용자 화면에는 저장 기술을 설명하기보다 결과를 표시한다.** 로그인해야 프로젝트나 초안을 서버에 보관할 수 있으므로 작성 진입 전에 로그인 상태를 확인한다. 일반 화면의 문구는 다음 정도로 제한한다.

- 저장 중: `임시 저장 중`.
- 성공: `임시 저장됨 · 시각`.
- 실패/충돌: 오류와 재시도 또는 서버 내용 불러오기/내 변경 저장 동작을 현재처럼 제공한다. 저장 실패를 완료처럼 표시하지 않는다.
- 로그인하지 않은 사람이 작성 화면에 들어온 경우에는 `계속하려면 로그인`을 안내한다. 브라우저 저장 방식과 `Supabase`라는 제품 내부 명칭은 기본 작성 설명에 넣지 않는다.
- 새로고침 후: 이번 안내의 카드·본문·대상·자료가 복원됐는지 확인하고, 확인 체크는 비운다.

구현 내부에서는 브라우저 캐시와 서버 저장의 차이를 계속 엄격히 다룬다. 서버 저장에 실패한 내용을 `저장됨`으로 표시하지 않는다. 로그인 전 편집을 허용할지 여부는 기존 초안 복원과 충돌 처리에 영향을 주므로, 권장하는 **로그인 후 작성** 흐름으로 변경할 때 기존 로컬 초안을 잃지 않는 전환을 확인한다.

`확인됨`의 뜻도 바꾼다. 프로젝트 등록·수정이나 `이번 안내만 수정`에서 직접 입력만으로 문서 근거가 확인됐다고 표시하지 않는다. 출처를 `운영 정보`, `문서 근거`, `담당자 입력`, `이전 안내`로 분리하고, 담당자 수정값에는 **담당자 확인 동작**을 거쳐야 생성 가능 상태가 되도록 한다. 기존 근거가 수정으로 무효해지면 원문과 수정값의 차이를 볼 수 있게 하거나, 적어도 근거가 더는 적용되지 않는다고 표시한다. 무엇을·해야 할 일·마감이 필수라는 현재 생성 조건은 버튼 옆에서 설명하고 누락 항목의 수정 위치로 바로 이동할 수 있게 한다. Gemini 없이 직접 본문을 쓰는 경로는 유지한다.

## 5. 구현 순서와 인수 기준

### 먼저 확정할 계약

1. 카드 상태와 출처의 의미, 담당자 입력의 확인 절차를 정한다. 분석용 파일과 공지용 자료는 별도로 취급한다.
2. 새 안내는 현재 프로젝트 정보를 우선 사용하고, 이전 안내의 보충 정보는 운영자가 선택할 때만 사용하도록 정한다. 프로젝트 수정 전에 작성하던 초안의 재확인 조건도 정한다.
3. 생성에 사용하는 정보 목록과 저장 대상·시점을 정한다. 보낸 기록에 당시 카드와 선택 자료를 남기는 형식을 정한다.
4. 프로젝트 안내 자료 목록의 소유·버전과 이번 안내만 추가한 자료의 보관 범위를 정한다.
5. 말투 변경을 명시적 재생성으로 바꾸고, 기존 본문 보호 규칙을 정한다.
6. 기존 `notice_drafts` 카드 값을 새 표시 방식으로 읽는 호환 규칙을 정한다. 기존 저장 초안을 자동 삭제하거나 조용히 덮어쓰지 않는다.

### 구현 단계

1. 등록·수정 화면에서 자료 후보 → 운영 정보 → 자동 준비한 안내 정보 → 확인 필요 항목의 관계를 보여준다. 새 안내는 저장된 최신 프로젝트 값에서 시작한다.
2. 첫 안내의 검토 시각을 선택할 수 있게 한다. 별도 설정이 없으면 현재처럼 등록 시 `첫 안내 준비` 티켓을 만든다. 리마인드 기본 규칙은 기존 D-3·D-1 오전 10시와 마감 4시간 전을 유지한다.
3. 안내 작성 화면의 큰 카드 입력 격자를 제거하고, 자동 준비한 프로젝트 정보 요약과 `프로젝트 정보 수정`·`이번 안내만 수정`을 제공한다.
4. 첫 안내에서 사용한 카드 스냅샷을 보낸 기록에 남긴다. 새 리마인드는 최신 프로젝트 정보에서 만들고, 이전 안내의 보충 정보만 필요할 때 선택해 가져온다.
5. 공지 목적·말투·생성 버튼·후보 비교를 한 흐름으로 배치한다. AI 요청에는 확인·포함된 정보만 들어가도록 검증한다.
6. 본문 아래에 링크·파일 선택을 배치하고, 프로젝트 자료 재사용과 이번 안내만 추가를 구분한다. 최종 확인과 기록에 선택 자료의 당시 버전을 표시한다.
7. 저장 상태의 결과·오류·충돌·새로고침 복원을 연결한다. 신청 현황 새로고침을 대상 영역으로 옮기고, 원본 갱신 후 대상 변경·승인 해제를 확인한다.
8. 데스크톱과 850px·모바일 폭에서 프로젝트 정보 요약, 초안 비교, 자료 목록, 대상 명단, 확인 막대의 가림과 이동을 점검한다.

### 완료로 판단할 사용자 흐름

- **자료 입력:** 파일 분석 → 후보 선택 적용 → 프로젝트 저장 → 자동 채운 기본 카드 확인. 충돌·누락은 자동 확정되지 않는다.
- **첫 안내:** 즉시 준비 또는 선택한 검토 시각에 티켓 생성 → 등록 화면에서 확정한 값을 다시 입력하지 않고 초안 생성 → 최종 확인 → 모의 기록에서 당시 카드 조회.
- **프로젝트 수정 후 새 안내:** 마감·링크 등을 수정해 저장 → 새 공지와 리마인드에서 수정된 값이 자동으로 기본값이 됨. 이전 수신자·신청률은 복사하지 않는다.
- **작성 중이던 초안:** 프로젝트 수정 전의 초안에 예전 정보가 남았다면 변경 항목을 알려주고 본문·대상을 재확인하게 한다.
- **로그인·저장:** 카드·말투·본문·대상 수정 → 저장 완료 표시 → 새로고침/재로그인 후 복원. 저장 실패·버전 충돌도 화면에서 구별한다. 비로그인 진입과 기존 로컬 초안 전환도 확인한다.
- **Gemini:** 확인된 항목만 사용되고 제외한 비용·예외·링크가 어떤 말투에서도 되살아나지 않는다. 새 후보를 유지/적용할 수 있으며 기존 직접 수정 본문이 자동 교체되지 않는다.
- **공지 자료:** 분석용 문서가 자동 첨부되지 않는다. 프로젝트의 재사용 링크·파일을 선택하거나 새로 추가한 뒤 본문·첨부 카드·최종 확인·모의 기록에서 같은 자료와 버전을 확인한다. 링크 제거와 파일 교체 시 승인을 다시 받는다.
- **Sheets:** 원본 새로고침 → 대상 수 변화 확인 → 승인 해제 → 모의 발송 직전 원본 재조회 실패·변경 시 중단을 실제 시트와 브라우저에서 확인한다.
- **화면 밖 정기 실행:** 브라우저를 닫은 상태에서 예약 실행 → 시트 조회·규칙 판단 → 티켓과 실행 결과 저장 → 다시 로그인해 티켓·마지막 확인 시각 확인. 같은 작업을 반복해도 중복 티켓이나 중복 신청 사건이 생기지 않고, 원본 조회 실패는 오류로 남는다.
- **발송:** 본문·대상·자료 최종 확인과 저장 기록을 대조한다. 현재는 **모의 발송**임을 유지하고 실제 Slack 도착을 주장하지 않는다.

기능 변경 시 [`docs/PLAN.md`](PLAN.md), [`spec/spec_001.md`](../spec/spec_001.md), 필요하면 [`spec/spec_002.md`](../spec/spec_002.md)를 실제 동작에 맞춰 함께 갱신한다. 검증 보고에는 코드 작성, 로컬 자동 테스트, 실제 서비스 연결, 브라우저 사용자 흐름, 배포 확인을 따로 기록한다.

## 6. 화면을 닫아 둔 동안의 정기 실행

브라우저의 타이머는 창이 닫히면 실행되지 않는다. **서버에 예약 작업을 두고, 결과를 DB에 저장한 뒤 다음 접속에서 읽는 구조**로 만든다. Supabase의 공식 방식은 Cron(`pg_cron`)과 `pg_net`으로 Edge Function을 정기 호출하고, 호출 자격 정보는 Vault에 두는 것이다. ([Supabase 예약 함수 문서](https://supabase.com/docs/guides/functions/schedule-functions))

```text
예약 시각 도착 → 서버 함수 실행 → 최신 신청 원본 조회
→ 프로젝트 일정·공휴일·점검 규칙 평가
→ 필요한 티켓을 같은 키로 생성/갱신, 사라진 사유는 종료
→ 실행 시각·성공/오류 저장 → 담당자가 다시 접속하면 최신 티켓 표시
```

- **판단 대상:** 등록된 프로젝트 중 운영 중인 것. 첫 안내 준비와 리마인드 점검을 구분한다. 현재 예약 함수는 **시트 원본에 ID가 있고 앱에도 등록된 프로젝트**를 평가하므로, 직접 등록한 모든 프로젝트까지 화면 밖에서 평가하려면 작업 대상을 확장해야 한다.
- **판단 시각:** 기본 D-3·D-1 오전 10시와 마감 4시간 전을 프로젝트별 설정·한국 시간·공휴일 규칙으로 계산한다. 현재 매시간 실행은 해당 시점 뒤 첫 실행 때 티켓을 갱신한다. 특정 분 단위의 정확한 도착이 필요하면 실행 간격을 더 짧게 정해야 한다.
- **중복 방지:** 프로젝트·규칙·예정 시각으로 안정적인 티켓 키를 만들고 같은 키는 DB에서 갱신한다. 신청 사건도 원본 사건 ID로 한 번만 기록한다. 예약 작업이 재시도되거나 두 번 호출돼도 같은 티켓을 중복 생성하지 않는다.
- **실패 처리:** Sheets 조회나 공휴일 확인이 실패하면 성공한 최신 조회처럼 표시하거나 신청자 0명으로 간주하지 않는다. 실행 실패와 마지막 성공 시각을 저장해 다음 실행에서 재시도하고, 오래된 자료로 새 리마인드를 확정하지 않는다.
- **화면 연결:** 담당자가 웹을 다시 열면 DB의 최신 신청 스냅샷·티켓·실행 결과를 불러온다. 화면이 열린 동안의 수동 새로고침은 별도 제공한다. 이 예약 작업은 **공지 문구 생성·승인·발송을 하지 않는다.**

**현재 확인 범위 (2026-10-07):** 이 저장소의 [`sync-sheets` Edge Function](../supabase/functions/sync-sheets/index.ts), [`sheet-sync-hourly` 예약 SQL](../supabase/cron-hourly.sql), [`buildScheduledSync`](../supabase/functions/_shared/sheet-sync-core.mjs)가 이 흐름의 예시 시트용 기반이다. `docs/PLAN.md`의 기록에 따르면 `managerkim` Supabase에 매시간 작업을 활성화했고, 함수 직접 호출과 임시 1분 예약 실행의 저장 성공을 확인했다. **첫 매시간 정시 실행, 운영자 화면에서의 반영·새로고침 복원, 장애 후 복구는 미확인**이다. 따라서 화면 밖 실행의 사용자 흐름 완료나 모든 신규 프로젝트 지원을 아직 주장하지 않는다.

## 7. 병렬 구현 판단

**필수로 병렬화할 규모는 아니다.** 다만 이전 안내의 보충 정보와 자료 재사용까지 포함하면 화면 재배치만 할 때보다 작업이 커진다. 현재 등록·검토 화면의 표시, 이벤트, 저장 호출이 `prototype/app.js`에 모여 있어 여러 작업자가 동시에 그 파일을 바꾸면 충돌과 동작 불일치가 생기기 쉽다. 빠르게 진행해야 한다면 위의 **최신 프로젝트 정보 우선 규칙을 먼저 확정**하고 아래처럼 제한적으로 병렬 작업한다.

| 작업 흐름 | 담당 범위 | 담당 파일·인터페이스 |
| --- | --- | --- |
| A. 화면 표현 | 등록 화면의 기본 카드 확인, 공지 화면의 프로젝트 정보 요약·자료 선택·예외 편집, 반응형·확인 막대 | 새 화면 모듈과 `prototype/styles.css`. 데이터는 `projectCard`, `noticeCard`, `resources`, `sourceStatus`를 인자로 받고 변경 이벤트만 내보냄 |
| B. 카드·저장 의미 | 최신 프로젝트 값으로 새 안내 구성, 안내별 스냅샷, 재사용 안내 자료, 작성 중 초안 재확인, 기존 초안 호환 | `prototype/notice-draft.js`, 저장 접근 모듈·필요한 DB 변경과 관련 테스트. 카드와 자료의 ID·출처 계약을 A·C에 먼저 공유 |
| C. 생성 규칙 | 생성 입력 미리보기와 실제 API 입력의 일치, 말투·목적, 제외 항목 검증 | `scripts/notice-generation.mjs`, 생성 관련 테스트. 프런트와 공유할 입력 형식을 먼저 확정 |
| 통합 담당 | 등록·검토의 `app.js` 연결, Sheets 버튼 이동, 승인 무효화, 이전 기록 호환, 명세 갱신 | `prototype/app.js`, `docs/PLAN.md`, `spec/`. **병렬 작업 중 `app.js`의 최종 수정자는 한 명** |

워크트리를 쓴다면 담당 파일과 모듈 입출력, 변경할 기존 초안·기록 형식을 먼저 정한다. 각 브랜치가 확인한 범위와 미확인 조건을 공유한 뒤 병합한다. 병합 후에는 **로그인 → 자료 분석·프로젝트 저장 → 프로젝트 정보 수정 → 새 안내에서 수정값 확인 → 이전 안내의 보충 정보 선택 → 대상 재확인 → 모의 발송 → 기록·새로고침 복원**을 브라우저·API·Sheets 원본·Supabase 저장까지 다시 확인한다. 개별 브랜치의 통과나 모의 API 응답만으로 현재 앱의 연동 완료를 주장하지 않는다.
