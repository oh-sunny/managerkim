# 행사 복지 안내 운영 도구 구현 계획

작성일: 2026년 10월 5일  
현재 위치: 1단계 로컬 운영 정보·신청 현황 연결 완료. 2단계부터 미완료.

**다음 작업은 2단계다. 등록 정보와 신청 현황을 이용해 확인할 일과 캘린더 일정을 규칙으로 생성한다.** 첫 번째 목표는 로컬에서 핵심 업무 흐름을 끝까지 확인하는 것이고, 두 번째 목표는 실제 신청 원본과 Slack을 연결하는 것이다.

이 문서는 구현 순서와 완료 기준을 관리한다. 제품의 목적·정책은 [PRD](PRD.md), 현재 구현의 상세 동작과 한계는 [SPEC](spec_001.md)를 기준으로 한다. 기능을 완성할 때 PLAN의 진행 상태와 SPEC의 실제 동작을 함께 갱신한다. 제품 정책이 달라질 때만 PRD를 수정한다.

## 1 구현 중 유지할 방향

완성할 흐름은 **운영 정보 등록 → 신청 현황 확인 → 안내 필요 판단 → 초안과 대상 검토 → 승인 후 발송 → 기록과 현황 재확인**이다. 전체 총무 업무 중 공지 준비부터 신청 기간의 안내 운영에 집중한다.

- 기존 F01~F09를 중심으로 연결한다. 홈에서 전체 티켓 열기, 하단 캘린더, 안내 원문·Slack 링크, 팀별 개별 DM·채널 선택 흐름을 유지한다.
- 현황 계산과 안내 판단은 규칙으로 먼저 구현한다. AI는 자료 입력·작성·설명을 개선하는 단계에서 붙인다.
- 신청 상태, 참여·이용 확정 상태, 안내 처리 상태, 발송 결과, 운영 종료를 구분한다.
- 신청 데이터의 첫 원본은 엑셀 등 스프레드시트를 고려한다. 원본을 읽는 기능을 분리해 이후 DB 교체가 판단 기능 전체의 재작성이 되지 않게 한다.
- 복지 결재, 구매·지급, 업체·담당자 인계, 직원용 신청 포털 전체, 범용 업무 관리 기능은 이번 구현 범위에 추가하지 않는다.

새 기능을 떠올리면 먼저 위 흐름의 어느 막힌 부분을 해결하는지 확인한다. 현재 단계의 완료에 필요하지 않으면 후속 후보로 남기고 진행 중인 기능을 끝낸다.

## 2 현재 출발점

현재 웹앱은 HTML·CSS·JavaScript와 정적 파일용 Node 서버로 동작한다. 운영 정보 등록·수정, 로컬 신청·취소·확정, 현황·DM 대상 재계산과 저장·복원은 구현했다. 예시 티켓, 초안 편집, 대상·채널 선택, 모의 발송과 안내 기록을 제공한다. 텍스트 기획서의 명시적 항목 후보 검토·적용도 가능하다. 실제 원본 연결·규칙에 따른 티켓 생성·Slack 전송·주기 실행은 없다. 티켓·캘린더의 예시 기준일은 2026년 10월 3일이다.

기존 화면과 동작은 활용한다. 구현에 필요한 범위로 화면·계산·저장 코드를 분리하고, 기술 스택 선택이나 화면 전면 재작성 자체를 첫 목표로 삼지 않는다. 서버·저장소·배포 구성은 4단계 착수 전에 정한다.

## 3 단계별 구현과 완료 기준

### 1 운영 정보와 신청 현황 연결

목표: 예시 숫자를 표시하던 화면을 등록 정보와 신청 기록에서 계산하는 화면으로 바꾼다. 관련 기능은 F01·F02·F05·F09다.

- [x] 최소 등록·수정 화면을 만든다. 이름, 설명, 신청 기간과 마감 시각, 행사·운영 일정, 신청 링크, 담당자, 대상 명단과 필수 여부, 신청 후 확정 방식을 입력한다.
- [x] 운영자 입력 정보와 신청 원본에서 가져올 정보를 구분한다. 프로젝트·동료 식별자, 신청·취소·확정 상태, 조회 시각을 연결할 공통 형식을 정한다. 별도 방대한 설계 문서는 만들지 않고 SPEC에 필요한 항목만 기록한다.
- [x] 로컬 검증용 신청·취소와 확정 상태 변경 수단을 만든다. 즉시 확정형과 별도 확인·승인·선정형을 재현하되 결재 기능은 만들지 않는다.
- [x] 현황 요약과 DM 대상이 같은 계산 결과를 사용하도록 연결한다. 신청률은 프로젝트별 대상 명단을 분모로 계산한다.
- [x] 등록 정보와 신청 기록을 저장·복원한다. 예시 초기화와 직접 입력 데이터의 구분을 표시한다.

**완료 기준:** 등록한 행사에서 신청·취소를 바꾸면 홈·상세 현황·DM 명단이 함께 바뀐다. 중복 신청으로 인원이 늘지 않으며, 승인·선정 대기자를 미신청자로 잡지 않는다. 대상 0명과 식별 불가 기록을 정상 현황처럼 표시하지 않고 새로고침해도 저장한 상태가 유지된다.

### 2 확인할 일과 캘린더 생성

목표: 미리 작성된 티켓을 실제 현황과 시간에 따라 생성·갱신한다. 관련 기능은 F01·F02·F03이다. 1단계의 명단·신청 계산을 사용한다.

- [ ] 필수 미신청자를 D-3·D-1 날짜의 오전 10시와 기본 마감 4시간 전에 확인한다. 마지막 확인 간격은 프로젝트별 변경 가능하게 한다. 한국 시간 평일 09:00~18:00, 주말·공휴일 제외를 기본으로 업무시간 밖 시점을 직전 업무시간으로 당긴다.
- [ ] 자율 신청 목표를 신청률로 입력하거나 목표 없이 운영하게 한다. D-3에 목표 인원의 70% 미만, D-1에 90% 미만이면 검토를 제안하며 프로젝트별 기준 변경을 지원한다. 목표가 없으면 현황만 보여준다.
- [ ] 같은 프로젝트·대상·목적의 안내 후 24시간 추가 제안을 제한한다. 마지막 마감 전 확인에도 적용하며 제한 사유와 다음 확인 가능 시점을 표시한다.
- [ ] 티켓에 이유, 사용한 수치, 원본 확인 시각, 추천 대상을 연결한다. 검토 화면에서 최근 발송 시각·대상·원문·Slack 링크를 바로 확인하게 한다.
- [ ] 동일 사유의 중복 생성 방지, 보류·안내하지 않기, 재검토 조건을 구현한다. 신청·취소·일정 변경으로 사유가 없어지면 미발송 티켓을 갱신하고 이력을 남긴다.
- [ ] 홈·전체 티켓·캘린더가 같은 일정과 상태를 사용하게 한다. 실제 현재 시각과 검증용 시각을 분리해 날짜가 지나기를 기다리지 않고 확인할 수 있게 한다.

**완료 기준:** 조건이 충족될 때 해당 티켓이 생기고, 반복 계산해도 중복되지 않는다. 신청 완료·마감 연장·보류에 따라 티켓과 캘린더가 일관되게 바뀐다. 필수 안내와 자율 안내가 구분되며, 마감 후 모집 안내나 오래된 자료에 근거한 잘못된 제안을 막는다.

주말·공휴일 조정, 조정 후 겹친 점검, 24시간 제한의 직전·해제 시점, 목표 기준과 정확히 같은 신청률, 목표 없는 운영을 함께 확인한다. 시점별 기준은 합의한 초기 정책이며 추세 예측으로 표시하지 않는다.

### 3 검토부터 모의 발송과 기록까지 완성

목표: 로컬에서 한 건의 안내 운영을 끝까지 처리한다. 관련 기능은 F04~F09이며 2단계에서 만든 티켓을 사용한다.

- [ ] 등록 정보로 초안을 만들고 필수 항목 누락·날짜·링크 불일치를 표시한다. 직접 수정한 초안도 저장한다.
- [ ] 팀별 개별 DM과 채널 게시를 구분하고 수신 대상·게시 범위를 검토할 수 있게 한다. 이 단계의 채널 정보와 결과는 모의 값임을 표시한다.
- [ ] 본문·대상·발송 방식 변경 시 승인을 해제한다. 모의 실행 직전에도 현재 신청 기록과 대상을 다시 대조한다.
- [ ] 중복 실행을 막고 성공·부분 실패·결과 불명을 구분하는 결과 구조를 만든다. 결과 불명은 확인 없이 재발송하지 않는다.
- [ ] 발송 당시 본문·대상·시각과 결과를 보존한다. 수동으로 추가한 외부 안내는 출처를 구분하고 수정 이력을 남긴다. 모의 결과에는 실제 Slack 링크를 만들어 넣지 않는다.

**완료 기준:** 등록 → 신청 변화 → 티켓 생성 → 초안 수정 → 대상 선택 → 승인 → 모의 발송 → 원문 조회 → 다음 현황 확인을 이어서 수행할 수 있다. 발송 직전 새 신청자가 생기면 재확인하고, 발송 성공으로 신청 상태나 행사 전체가 완료되지 않는다.

**1~3단계가 끝나면 로컬 MVP 완료다.** 실제 업무에 연결한 서비스의 완료와 구분한다.

### 4 실제 신청 원본과 Slack 연결

목표: 로컬에서 확인한 흐름을 실제 원본·전송 결과와 연결한다. 아래 순서로 진행하며 연결 수단은 이 단계에서 확정한다.

| 순서 | 구현할 내용 | 완료 기준 |
| --- | --- | --- |
| 4A 서버 저장과 접근 | 운영 정보·초안·승인·발송 기록 저장, 운영자 인증, 연동 자격 정보 관리 | 브라우저를 바꿔도 승인된 사용자가 같은 기록을 확인하고, 연동 비밀값이 브라우저에 노출되지 않음 |
| 4B 신청 원본 연결 | 스프레드시트 제품·위치·열 의미 확정, 식별자·상태 대응, 조회·변환, 오류·최신성 표시 | 원본의 신청·취소·확정 변화가 반영되고, 조회 실패가 신청 0명으로 바뀌지 않음 |
| 4C Slack 발송 | 계정·채널 연결, 공개·외부 공유·게시 권한 확인, 서버 승인과 실행 전 재조회, 발송·결과·링크 저장 | 승인한 본문과 대상에 실제로 발송되고, 부분 실패·결과 불명을 구분해 중복 없이 복구 가능 |
| 4D 주기 실행과 배포 | 현황 조회·검토 시점 실행, 실행 이력, 중복 작업 방지, 장애 후 복구 | 담당자가 화면을 닫아도 확인 작업이 실행되며, 재시작·재실행이 중복 티켓·발송을 만들지 않음 |

파일 업로드만 지원하는 경우 마지막 업로드 시점의 자료라는 점을 표시한다. 상시 갱신하려면 접근 가능한 원본과 조회 방식이 필요하다. 주기 실행은 현황 갱신과 제안 생성에 사용하며 승인 없는 자동 발송으로 범위를 바꾸지 않는다.

**완료 기준:** 관리 가능한 테스트 대상·채널에서 실제 흐름과 실패 복구를 확인한다. 사용 원본·계정·접근 범위·보존 정책을 정한 뒤 현업에서 제한적으로 사용할 준비를 마친다. 특정 클라우드나 스프레드시트 서비스를 미리 확정한 것으로 해석하지 않는다.

### 5 AI와 과거 기록으로 품질 개선

목표: 기본 흐름을 유지하면서 입력·검토 부담과 안내 제안 품질을 개선한다. 관련 기능은 F01·F02·F04다.

기획서 입력 흐름은 [문서에서 채우기 구현 방향](document-import-plan.md)에 단계별로 정리했다. 현재는 텍스트 파일의 명시적 항목 후보와 근거를 검토해 적용할 수 있다. PDF·DOCX 및 선택적 AI 해석은 아직 이 단계의 후속 작업이다.

- [ ] 운영 자료에서 일정·대상·확정 방식 등을 추출하고 근거 문구와 후보를 보여준다. 사용자가 확인한 값만 적용하며 누락·충돌을 추측으로 채우지 않는다.
- [ ] 확인된 정보에 기반한 초안 작성·말투 조정·제안 이유 설명을 추가한다. AI를 사용하지 못해도 직접 입력·템플릿으로 계속 운영할 수 있게 한다.
- [ ] 과거 비교에 필요한 시점별 현황과 발송 이력을 확보한다. 현재 합계만으로 과거 추이를 복원했다고 주장하지 않는다.
- [ ] 유사 운영의 같은 마감 전 시점을 비교하고 기록 수·조건 차이를 표시한다. 목표 미달 예측은 기본 규칙과 비교해 판단 품질을 확인한 뒤 도입한다.

**완료 기준:** 추출값의 오류, 초안 수정 부담, 제안 채택·보류 이유를 기본 방식과 비교할 수 있다. 잘못된 판단을 사람이 발견·수정할 수 있고, AI 도입으로 수신자 결정이나 승인 규칙이 달라지지 않는다. 과거 기록이 부족하면 해당 분석은 보류하고 나머지 기능은 운영한다.

## 5 검증과 완료 표시

각 단계에서는 변경한 업무 흐름과 실패하기 쉬운 경계를 확인한다. 신청자 대조·날짜 판단·승인 무효화·중복 발송 방지처럼 결과가 중요한 계산은 자동 검증하고, 화면 이동·입력·원문 조회는 브라우저에서 연결해서 확인한다. 상세 예시 데이터는 구현할 기능에 필요한 만큼 준비한다.

| 표시 | 의미 |
| --- | --- |
| 미착수 | 요구사항만 정리됨 |
| 진행 중 | 구현 중이며 완료 기준을 아직 통과하지 못함 |
| 결정 대기 | 어느 결정에 의존하는지 명시하고 독립적인 작업을 진행 |
| 완료 | 해당 단계의 완료 기준을 실제로 확인하고 결과를 SPEC에 기록함 |

모의 전송 성공으로 실제 Slack 연동을 완료 표시하지 않는다. 문서에 적었다는 이유로 기능을 완료 표시하지 않는다. 예시 데이터의 정상 동작과 현업에서 유용하다는 검증도 구분한다.

현업 효용은 기존 방식과 비교해 현황 확인·안내 준비 시간, 잘못된 대상·중복 안내, 초안 수정 부담, 새 도구 입력 부담으로 살핀다. 지금 실제 업무 자료가 없다는 이유로 로컬 구현을 미루지는 않는다.
