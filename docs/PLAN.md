# 행사 복지 안내 운영 도구 구현 계획

작성일: 2026년 10월 5일  
현재 위치: 1단계의 기본 화면·계산·계정별 저장 구현, 2단계의 규칙 티켓·캘린더 연결, 3단계의 모의 발송 및 Sheets 발송 직전 재확인 구현. 실사용 통합 검증과 실제 Slack 발송은 남음.

**2026-10-07 현재:** 계정별 Supabase 운영 상태·초안 저장, 규칙 티켓·캘린더, 공지 정보 카드와 Gemini 초안, Google Sheets 네 탭 수동 조회, Sheets 기반 모의 발송 직전 재조회·변경 차단을 구현했다. `managerkim` Supabase 프로젝트에 예약 동기화 DB·Edge Function·비밀값·Vault·매시간 Cron을 적용했다. 예시 시트의 직원 160명·신청 사건 17건을 함수가 읽어 저장했고, 임시 예약 실행의 재조회 성공도 확인했다. **첫 매시간 정시 실행과 운영자 브라우저의 가져오기·화면 반영·새로고침 복원은 아직 미확인이다.** 실제 Slack 발송, 발송 자료 검사, 조직 공동 권한은 아직 없다.

이 문서는 구현 순서와 완료 기준을 관리한다. 제품의 목적·정책은 [PRD](PRD.md), 현재 구현의 상세 동작과 한계는 [SPEC 001](../spec/spec_001.md), 다음 프로젝트 등록·안내 화면 흐름의 구현 목표는 [SPEC 003](../spec/spec_003.md)을 기준으로 한다. 기능을 완성할 때 PLAN의 진행 상태와 SPEC 001의 실제 동작을 함께 갱신한다. 제품 정책이 달라질 때만 PRD를 수정한다.

## 1 구현 중 유지할 방향

완성할 흐름은 **운영 정보 등록 → 신청 현황 확인 → 안내 필요 판단 → 초안과 대상 검토 → 승인 후 발송 → 기록과 현황 재확인**이다. 전체 총무 업무 중 공지 준비부터 신청 기간의 안내 운영에 집중한다.

- 기존 F01~F09를 중심으로 연결한다. 홈에서 전체 티켓 열기, 하단 캘린더, 안내 원문·Slack 링크, 팀별 개별 DM·채널 선택 흐름을 유지한다.
- 현황 계산과 안내 판단은 규칙으로 먼저 구현한다. AI는 자료 입력·작성·설명을 개선하는 단계에서 붙인다.
- 신청 상태, 참여·이용 확정 상태, 안내 처리 상태, 발송 결과, 운영 종료를 구분한다.
- 신청·취소 데이터의 첫 원본은 Google Drive의 Google 스프레드시트로 정했다. Sheets API 조회 기능을 판단 기능과 분리해 이후 원본 교체가 판단 기능 전체의 재작성이 되지 않게 한다.
- 복지 결재, 구매·지급, 업체·담당자 인계, 직원용 신청 포털 전체, 범용 업무 관리 기능은 이번 구현 범위에 추가하지 않는다.

새 기능을 떠올리면 먼저 위 흐름의 어느 막힌 부분을 해결하는지 확인한다. 현재 단계의 완료에 필요하지 않으면 후속 후보로 남기고 진행 중인 기능을 끝낸다.

## 2 현재 출발점

현재 웹앱은 HTML·CSS·JavaScript와 Node 서버 또는 Vercel 함수로 동작한다. 운영 정보 등록·수정, 신청·취소·확정, 현황·DM 대상 재계산, 계정별 Supabase 저장·복원, Google Sheets 수동 가져오기를 구현했다. 기존 예시 티켓과 새 프로젝트의 규칙 티켓을 구분해 표시하며, 초안 편집·Gemini 생성·대상·채널 선택·모의 발송·안내 기록을 제공한다. 여러 문서의 Gemini 분석과 OCR도 연결했다. 예시 시트의 서버 주기 조회·티켓 평가가 활성화됐지만 실제 Slack 전송은 없다. 초기 예시 티켓과 안내 기록은 2026년 10월 3일 무렵의 가상 사례다.

기존 화면과 동작은 활용한다. 구현에 필요한 범위로 화면·계산·저장 코드를 분리하고, 화면 전면 재작성 자체를 목표로 삼지 않는다. Node/Vercel·Supabase 기반은 구성했으며, 실제 조직 자료와 배포 환경의 권한·보존·장애 복구 설정은 운영 전에 확정한다.

## 3 단계별 구현과 완료 기준

### 1 운영 정보와 신청 현황 연결

목표: 예시 숫자를 표시하던 화면을 등록 정보와 신청 기록에서 계산하는 화면으로 바꾼다. 관련 기능은 F01·F02·F05·F09다.

- [x] 최소 등록·수정 화면을 만든다. 이름, 설명, 신청 기간과 마감 시각, 행사·운영 일정, 신청 링크, 담당자, 대상 명단과 필수 여부, 신청 후 확정 방식을 입력한다.
- [x] 운영자 입력 정보와 신청 원본에서 가져올 정보를 구분한다. 프로젝트·동료 식별자, 신청·취소·확정 상태, 조회 시각을 연결할 공통 형식을 정한다. 별도 방대한 설계 문서는 만들지 않고 SPEC에 필요한 항목만 기록한다.
- [x] 로컬 검증용 신청·취소와 확정 상태 변경 수단을 만든다. 즉시 확정형과 별도 확인·승인·선정형을 재현하되 결재 기능은 만들지 않는다.
- [x] 현황 요약과 DM 대상이 같은 계산 결과를 사용하도록 연결한다. 신청률은 프로젝트별 대상 명단을 분모로 계산한다.
- [x] 등록 정보와 신청 기록을 저장·복원한다. 예시 초기화와 직접 입력 데이터의 구분을 표시한다.
- [ ] 실제 운영자 계정으로 로그인 → Sheets 수동 가져오기 → Supabase 저장·새로고침 복원까지 화면에서 이어서 검증한다. 다른 기기 복원과 실제 파일 업로드도 별도로 확인한다.

**완료 기준:** 등록한 행사에서 신청·취소를 바꾸면 홈·상세 현황·DM 명단이 함께 바뀐다. 중복 신청으로 인원이 늘지 않으며, 승인·선정 대기자를 미신청자로 잡지 않는다. 대상 0명과 식별 불가 기록을 정상 현황처럼 표시하지 않고 새로고침해도 저장한 상태가 유지된다.

### 2 확인할 일과 캘린더 생성

목표: 미리 작성된 티켓을 실제 현황과 시간에 따라 생성·갱신한다. 관련 기능은 F01·F02·F03이다. 1단계의 명단·신청 계산을 사용한다.

- [x] D-3·D-1 오전 10시와 기본 마감 4시간 전의 필수 미신청자 점검 규칙을 구현한다. 점검 간격·업무시간은 프로젝트별 변경할 수 있으며 주말·전국 공휴일·업무시간 밖 점검은 직전 업무시간으로 조정한다. 규칙 계산은 화면에서 현황이 갱신될 때 실행한다.
- [x] 자율 대상만의 신청률과 목표를 계산한다. 목표 없음·자율 대상 0명은 판정하지 않으며 D-3의 70%, D-1의 90% 기준과 프로젝트별 설정을 반영한다.
- [x] 고정 재안내 시간 제한 없이 최근 안내 기록을 보여주고 같은 사유의 규칙 티켓이 중복 생성되지 않게 한다.
- [ ] 실제 발송 요청의 중복 실행을 서버에서 막고 결과 불명 시 재시도 여부를 판단한다. 모의 발송의 버튼 잠금만으로는 실제 전송의 중복을 막을 수 없다.
- [x] 규칙 티켓 데이터에 이유·수치·원본 확인 시각·추천 대상 ID를 연결한다. 화면에는 티켓 이유와 최근 안내 원문·수동 등록 Slack 링크를 표시한다.
- [ ] 검토 화면에서 추천 대상·원본 조회 시각·최근 안내의 시각과 대상을 한곳에서 확인하는 흐름을 완성한다.
- [x] 동일 사유 중복 방지, 보류·안내하지 않기와 사유·재검토 시각 저장, 신청·취소·일정 변경으로 사유가 사라진 미발송 티켓의 종료 처리를 구현한다.
- [x] 홈·전체 티켓·캘린더가 같은 티켓 상태를 사용한다. 규칙 계산의 현재 시각은 자동 테스트에서 주입해 경계 날짜를 확인한다.
- [ ] 신규 프로젝트·신청 변경·공휴일 조정이 이어지는 브라우저 전체 흐름을 실제 계정으로 검증한다. 예시 시트의 화면 밖 정기 실행은 4D에서 활성화했다.

**완료 기준:** 조건이 충족될 때 해당 티켓이 생기고, 반복 계산해도 중복되지 않는다. 신청 완료·마감 연장·보류에 따라 티켓과 캘린더가 일관되게 바뀐다. 필수 안내와 자율 안내가 구분되며, 마감 후 모집 안내나 오래된 자료에 근거한 잘못된 제안을 막는다.

주말·공휴일 조정, 조정 후 겹친 점검, 같은 사유의 티켓 중복 방지, 목표 기준과 정확히 같은 자율 신청률, 필수·자율 혼합 대상, 목표 없는 운영을 함께 확인한다. 시점별 기준은 합의한 초기 정책이며 추세 예측으로 표시하지 않는다.

### 3 검토부터 모의 발송과 기록까지 완성

목표: 로컬에서 한 건의 안내 운영을 끝까지 처리한다. 관련 기능은 F04~F09이며 2단계에서 만든 티켓을 사용한다.

- [x] 등록 정보와 확인된 공지 정보 카드로 Gemini 초안을 만들고 누락·날짜·링크·근거 없는 주장을 검사한다. 직접 수정한 본문과 대상 선택은 계정별 서버 초안에 저장한다.
- [x] 팀별·개인별 DM 선택과 채널 게시 선택을 구분하고 모의 수신 대상·게시 범위를 최종 확인 창에 표시한다. 채널 구성원 정보는 예시라고 표시한다.
- [x] 본문·대상·자료·방식 변경 시 확인을 해제하고, 화면 재진입·새로고침 후 초안만 복원한다. Sheets 기반 프로젝트는 모의 발송 직전 시트를 다시 읽어 승인 당시의 대상·신청 상태와 비교하고 변경·조회 실패를 차단한다.
- [x] 모의 발송 기록에 당시 본문·대상 ID·자료 목록·시각·원본 재조회 시각을 저장하고 수동 기록과 출처를 구분한다. 모의 기록에 실제 Slack 링크를 만들지 않는다.
- [x] 필수 미신청자만 선택·필수 대상 전체 선택 빠른 동작과 선택 명단의 필수·자율 수신 인원 구분을 코드에 연결하고 로컬 자동 테스트로 확인한다. 실제 계정의 브라우저 클릭·저장·재진입 확인은 아래 통합 검증에 남긴다.
- [ ] 발송용 본문·파일의 검사 상태와 미검토·검사 실패 차단을 구현한다. 문서 분석용 파일 검사는 발송용 민감 정보 검사와 다르다.
- [ ] 실제 전송을 위한 서버 승인·요청 ID와 목적지별 성공·부분 실패·결과 불명 구조를 구현한다.
- [ ] 실제 발송 기록의 원문·대상·결과를 변경 불가로 보존하고, 수동 기록의 수정 이력을 남긴다. 현재 모의·수동 기록의 원문은 수정할 수 있다.
- [ ] 등록부터 모의 발송·원문 조회·다음 현황 확인까지 실제 계정의 브라우저 흐름을 검증한다.

**완료 기준:** 등록 → 신청 변화 → 티켓 생성 → 초안 수정 → 대상 선택 → 승인 → 모의 발송 → 원문 조회 → 다음 현황 확인을 이어서 수행할 수 있다. 발송 직전 새 신청자가 생기면 재확인하고, 발송 성공으로 신청 상태나 행사 전체가 완료되지 않는다.

**1~3단계가 끝나면 로컬 MVP 완료다.** 실제 업무에 연결한 서비스의 완료와 구분한다.

### 4 실제 신청 원본과 Slack 연결

목표: 로컬에서 확인한 흐름을 실제 원본·전송 결과와 연결한다. 아래 순서로 진행하며 연결 수단은 이 단계에서 확정한다.

| 순서 | 구현할 내용 | 완료 기준 |
| --- | --- | --- |
| 4A 서버 저장과 접근 | 운영 정보·초안·승인·발송 기록 저장, 운영자 인증, 연동 자격 정보 관리 | 브라우저를 바꿔도 승인된 사용자가 같은 기록을 확인하고, 연동 비밀값이 브라우저에 노출되지 않음 |
| 4B 신청 원본 연결 | Google 스프레드시트의 열 의미·권한 확정, Sheets API로 최신 상태와 이력 행 읽기, 사건 ID·식별자·시각·상태 대응, 오류·최신성 표시 | 원본의 신청·취소·확정 변화와 이력이 중복 없이 반영되고, 조회 실패가 신청 0명으로 바뀌지 않음 |

**4A 진행 상태 (2026-10-07):** Supabase Auth와 계정별 `operator_states`·`operator_state_revisions`에 프로젝트·신청 이력·티켓·모의 안내 기록을 저장하고 버전 충돌을 표시한다. 초안은 `notice_drafts`에 저장하며, 발송 확인 체크는 복원하지 않는다. 현재 웹앱은 안내 파일을 브라우저의 사용자 JWT로 비공개 Supabase Storage에 직접 올리고 `notice_resources`에 기록하도록 수정했다. 실제 계정의 예시 초안 저장·복원은 확인했으나 직접 파일 업로드·다른 탭 복원·운영 상태의 다른 기기 복원은 별도 실사용 검증이 필요하다. 조직 공동 권한과 실제 발송 승인·결과 모델은 남았다.

**4B 진행 상태 (2026-10-07):** 읽기 전용 서비스 계정으로 실제 예시 시트의 직원명부 160명·프로젝트 3개·신청 사건 17건을 조회해 현재 신청 상태 11건으로 정규화했다. 화면의 수동 가져오기는 네 탭을 읽어 직원·대상·신청 현황을 갱신하며 마지막 성공 시각과 오류를 표시한다. Sheets 기반 프로젝트의 모의 발송 직전에는 서버가 시트를 다시 읽고 브라우저에서 승인 당시 명단·신청 상태와 대조한다. 변경 시 최신 값을 반영하고 재승인을 요구하며 조회 실패도 발송을 막는다. 시트의 프로젝트 ID는 웹앱에 먼저 등록돼 있어야 한다. 로그인 → 가져오기 → Supabase 저장·복원 → 모의 발송의 전체 흐름 검증은 남았다. 실제 Slack 발송 시에는 서버의 전송 처리 안에서 재검증해야 한다. 예시 시트의 정기 조회는 아래 4D에서 활성화했으며 승인 없는 자동 발송은 하지 않는다.

새 프로젝트 등록 화면에 시트의 `projectId`를 직접 지정하는 입력을 추가했다. 저장된 ID와 시트 ID가 같으면 이후 동기화에서 연결되며, 비워 두면 로컬 ID를 생성한다. 중복·형식 검사는 자동 테스트로 확인했으나 새 프로젝트를 실제 시트에 추가하는 브라우저 전체 흐름과 배포 반영은 미확인이다. 미등록 시트 ID가 생기면 현재 예약 실행은 오류로 멈추므로 운영자가 프로젝트를 먼저 등록해야 한다.

**4D 진행 상태 (2026-10-07):** `managerkim` Supabase에 `sync-sheets` Edge Function, 최신 스냅샷·신청 사건·자동 티켓·실행 결과 테이블, Cron·`pg_net`과 매시간 작업을 적용했다. 함수 직접 호출에서 직원 160명·사건 17건을 읽고 새 사건 17건·티켓 3건을 저장했다. 임시 1분 예약 작업의 실제 실행은 성공했고 다음 실행에서 새 사건 0건을 확인한 뒤 임시 작업을 제거했다. `sheet-sync-hourly`만 활성 상태다. 첫 매시간 정시 실행, 운영자 브라우저의 가져오기·새로고침 복원, 장애 후 복구는 미확인이다. 자동 발송은 하지 않는다.

**완료 기준:** 관리 가능한 테스트 대상·채널에서 실제 흐름과 실패 복구를 확인한다. Google 스프레드시트의 시트 구조·계정·접근 범위·보존 정책을 정한 뒤 현업에서 제한적으로 사용할 준비를 마친다.

### 5 AI와 과거 기록으로 품질 개선

목표: 기본 흐름을 유지하면서 입력·검토 부담과 안내 제안 품질을 개선한다. 관련 기능은 F01·F02·F04다.

사용자 요청에 따라 [SPEC 002의 9절](../spec/spec_002.md#9-기획서에서-프로젝트-정보-채우기)의 여러 자료 분석을 우선 연결했다. PDF·DOCX·TXT·MD와 붙여넣은 내용을 Gemini로 통합 분석하고, 스캔 PDF는 OCR한다. 후보·충돌·근거를 검토해 선택 적용하며 서버 원본 보관은 후속으로 분리했다.

2026-10-06 후속 개선: 공지에 바로 사용할 짧은 목적·대상·신청 절차로 편집하도록 바꾸고, 근거는 발췌 ID로 연결해 모델 출력량을 줄였다. 결과 노트와 접힌 수정·근거 화면, 실제 경과 시간, 추가 설정 안의 전체 PDF 이미지 인식을 적용했다. health 3개 자료의 텍스트 분석은 직접 호출과 웹에서 각각 약 19초를 확인했으며, 다양한 문서와 OCR의 지연시간·요약 품질은 추가 평가 대상이다.

- [x] 운영 자료에서 일정·대상·확정 방식 등을 추출하고 근거 문구와 후보를 보여준다. 사용자가 확인한 값만 적용하며 누락·충돌을 추측으로 채우지 않는다.
- [x] 자료 후보와 확정 운영 정보로 수정 가능한 **공지용 정보 카드**를 만든다. 행동·방법·비용·예외를 분리하고 근거·확인 상태를 연결하며 충돌·미확인 항목을 확인 또는 제외하기 전에는 Gemini에 전달하지 않는다. [SPEC 002의 10절](../spec/spec_002.md)을 따른다.
- [x] 확인된 카드 정보로 Gemini 초안을 만들고 말투와 첫 안내·추가 신청·마감 알림의 작성 규칙을 구분한다. 생성 본문은 카드의 사실과 대조하고 근거 없는 주장도 검사한다.
- [ ] 다양한 실제 문서에서 카드 항목 분류와 초안 품질을 평가하고, 기존 저장 초안 갱신·AI 실패 후 직접 입력 흐름을 실사용 검증한다. 티켓의 제안 이유를 초안에 연결하는 작업도 남았다.
- [ ] 과거 비교에 필요한 시점별 현황과 발송 이력을 확보한다. 현재 합계만으로 과거 추이를 복원했다고 주장하지 않는다.
- [ ] 유사 운영의 같은 마감 전 시점을 비교하고 기록 수·조건 차이를 표시한다. 목표 미달 예측은 기본 규칙과 비교해 판단 품질을 확인한 뒤 도입한다.

**완료 기준:** 추출값의 오류, 초안 수정 부담, 제안 채택·보류 이유를 기본 방식과 비교할 수 있다. 잘못된 판단을 사람이 발견·수정할 수 있고, AI 도입으로 수신자 결정이나 승인 규칙이 달라지지 않는다. 과거 기록이 부족하면 해당 분석은 보류하고 나머지 기능은 운영한다.

## 5 검증과 완료 표시

각 단계에서는 변경한 업무 흐름과 실패하기 쉬운 경계를 확인한다. 신청자 대조·날짜 판단·승인 무효화·중복 발송 방지처럼 결과가 중요한 계산은 자동 검증하고, 화면 이동·입력·원문 조회는 브라우저에서 연결해서 확인한다. 상세 예시 데이터는 구현할 기능에 필요한 만큼 준비한다.

| 표시 | 의미 |
| --- | --- |
| 미착수 | 요구사항만 정리됨 |
| 진행 중 | 구현 중이며 완료 기준을 아직 통과하지 못함 |
| 결정 대기 | 어느 결정에 의존하는지 명시하고 독립적인 작업을 진행 |
| 완료 | 해당 단계의 완료 기준을 실제로 확인하고 결과를 SPEC에 기록함 |

모의 전송 성공으로 실제 Slack 연동을 완료 표시하지 않는다. 문서에 적었다는 이유로 기능을 완료 표시하지 않는다. 예시 데이터의 정상 동작과 현업에서 유용하다는 검증도 구분한다.

현업 효용은 기존 방식과 비교해 현황 확인·안내 준비 시간, 잘못된 대상·중복 안내, 초안 수정 부담, 새 도구 입력 부담으로 살핀다. 지금 실제 업무 자료가 없다는 이유로 로컬 구현을 미루지는 않는다.

### SPEC 003 · 워크트리 병렬 구현 순서

이번 묶음은 **모의 발송과 기록 확인까지** 완성한다. 실제 Slack 전송·파일 전송·서버 발송 승인은 4C의 별도 작업이다. W1~W4 워크트리는 같은 기준 커밋에서 만들었고, 각 변경을 통합 작업 폴더에 모아 로컬 검증 중이다. 통합 변경은 아직 커밋·원격 반영하지 않았다.

**0. 병렬 시작 전 공통 계약을 고정한다.** 모든 워크트리는 같은 기준 커밋에서 시작하고, 구현 전에 다음 항목의 필드·함수 입출력과 기존 저장 데이터의 읽기 규칙을 공유한다. 이 계약을 바꾸면 관련 워크트리에 먼저 알리고 통합 담당자가 한 번만 반영한다.

- 프로젝트의 현재 저장값이 새 안내의 기준이다. 첫 안내 검토 시각(미설정 시 즉시), 프로젝트 공통 공지 자료의 ID·버전·소유 범위, 신청 원본의 연결·최신성 상태를 정의한다. 기존 프로젝트를 읽을 때 새 필드가 없어도 보존·복원한다.
- 작성 중 초안에는 사용한 프로젝트 주요 값과 이번 안내의 수정값·선택 자료를 구분한다. 새 안내는 최신 프로젝트 값으로 시작하고, 기존 초안은 본문·대상·자료를 보존한 채 변경 항목을 재확인한다. 모의 기록에는 사용한 정보와 자료의 당시 값을 남긴다.
- Gemini 요청에는 담당자가 확인하고 포함한 카드 값·제목·목적·말투만 사용한다. 말투 변경은 현재 본문을 보존하고 명시적 생성 요청의 결과만 본문에 넣는다. 생성 중 카드·대상·본문이 바뀌면 덮어쓰지 않는다. 생성 계약과 화면 미리보기의 포함 항목을 일치시킨다.
- 자동 티켓의 중복 키는 소유 계정·프로젝트·사유/규칙·예정 시각을 기준으로 한다. 시트 미연결·조회 실패·오래된 원본은 신청자 수나 추천 대상을 확정하지 않는다. 예약 작업은 Gemini·승인·발송을 호출하지 않는다.

W2의 저장 계약을 통합한 뒤 W3의 생성 입력과 화면을 연결한다. 각 워크트리는 변경 파일, 자동 테스트 결과, 실제 서비스·브라우저에서 확인하지 못한 조건을 공유한다. 병합 뒤 `npm test`와 Edge 공통 코드 생성 결과를 확인하고, 같은 실제 계정에서 **자료 입력 → 프로젝트 저장 → 첫 안내/리마인드 티켓 → 최신 정보로 초안 작성 → 자료·대상 확인 → 모의 발송 → 기록·새로고침 복원**을 다시 검증한다. Sheets 원본·Supabase 저장·예약 실행·배포 확인은 각각 별도로 기록한다. 개별 워크트리의 테스트 통과를 통합 완료로 표시하지 않는다.

**2026-10-07 로컬 통합 검증:** W1~W4 코드를 통합하고 `npm run build:edge` 및 `npm test`(103개 통과)를 확인했다. 브라우저에서는 새 프로젝트 화면의 저장 전 정보 요약, 안내 검토 화면 표시, 말투 변경 시 본문 보존, 이번 안내 링크의 추가·새로고침 복원·제거를 확인했다. 390px 화면의 안내 검토에서 가로 넘침이 없었다. 검토 화면 첫 이동에서 누락된 `projectReviewMarkup` 오류를 발견해 수정하고 다시 열어 확인했다. 운영자 계정으로 Supabase에 로그인한 뒤 운영 정보 충돌을 서버 기준으로 해소하고, 새 빈 초안의 서버 저장·검증 문구 저장·새로고침 복원·원상복귀를 확인했다. 브라우저에서 확인된 카드 값으로 Gemini 후보를 실제 생성하고 현재 본문을 유지했으며 검증용 카드 값도 되돌렸다. 별도 가상 자료의 Gemini 호출도 성공했다. 예시 Google Sheets를 서비스 계정의 읽기 전용 경로로 직접 조회해 직원 160명·프로젝트 3개·신청 사건 17건·현재 신청 11건을 확인했다. 기존 배포 `sync-sheets`의 브라우저 사전 요청은 405와 CORS 헤더 없음으로 확인됐고 화면의 수동 새로고침은 `Failed to fetch`로 실패했다. 로컬 함수에 CORS 처리를 추가하고 테스트했지만 배포하지 않았다. 새 프로젝트 저장·첫 안내 티켓·파일 업로드·모의 발송 기록의 전체 흐름은 아직 미확인이다. 새 마이그레이션 2개는 파일만 작성했고 DB에 적용하지 않았으므로 예약 평가와 자료 버전의 실제 서비스 동작도 미확인이다.

**2026-10-07 사용성 수정:** 운영 정보의 서로 다른 항목 변경은 자동 병합하고 같은 항목만 충돌로 남기도록 로컬 코드와 병합 테스트를 추가했다. 로그인 복원 중 저장 대기 변경을 덮어쓰지 않도록 했다. 저장 실패 때 로그아웃할 수 있는 명시적 폐기 선택, 프로젝트 양식의 이동 경고·대상 0명 차단·선택 설정 접기, 마감 경과 티켓과 보내기 차단, Gemini 필수 정보 입력 경로, 보내기 잠금 사유, 출처별 안내 기록 필터·정정 이력, 예시 자료·현재 날짜 표기를 연결했다. 편집 중 다른 탭의 저장은 양식 저장까지 적용을 미루도록 했다. 로컬 자동 테스트 **106개 통과**(탭 간 세션 전달·로그아웃 모의 테스트 포함). 별도 비로그인 브라우저에서 마감 경과 경고, Gemini 카드 이동, 기록 출처 필터, 편집 화면의 접힌 설정과 저장 전 이동 경고·취소 후 입력 보존을 확인했다. **실제 두 탭의 운영 정보 자동 병합·로그아웃·운영자 서버 저장, Gemini 실제 재생성, Sheets 수동 가져오기와 새 프로젝트 저장·복원은 이번 수정 후 실계정 브라우저에서 미확인**이다. **2026-10-07 초안 입력 흐름 교정:** Gemini 결과를 별도 비교 상자에 두지 않고 메시지 본문 입력 칸에 바로 적용·자동 저장하도록 로컬 화면 코드를 수정했다. 같은 화면에서 생성 직전 본문으로 되돌릴 수 있고, 생성 중 본문·정보·대상이 바뀌면 응답으로 덮어쓰지 않는다. 운영자 로그인 브라우저에서 앞서 생성돼 있던 문구를 본문에 적용한 뒤 Supabase 저장 표시와 새로고침 후 본문 복원을 확인했다. 새 화면 코드로 실제 Gemini를 다시 호출했을 때 새 문구가 본문 입력 칸에 들어가고 되돌리기 버튼과 서버 저장 표시가 나타났다. `npm test`는 106개 통과했다. 되돌리기 클릭과 이번 새 문구의 새로고침 후 복원은 미확인이다. 실제 Slack 발송과 웹 배포는 하지 않았다.

**2026-10-07 로그아웃 흐름 교정:** 미저장 초안은 로그아웃을 막지 않도록 바꿨다. 로그아웃 시 초안 저장을 재시도하지 않고 로컬 초안을 버리며, 연결 창에 이 동작을 표시한다. 운영 정보 저장 실패와 프로젝트 편집 양식의 미저장 변경은 기존 확인 흐름을 유지한다. 실제 운영자 브라우저의 로그아웃 조작은 계정 세션을 종료하므로 이 변경 뒤 아직 확인하지 않았다.

**2026-10-07 로그인 명칭 교정:** 상단 로그인 진입 버튼·대화상자 제목과 로그인 요구 문구를 ‘관리자 로그인’으로 표시한다. 인증·저장 구현은 Supabase를 사용한다. 운영자 로그인 브라우저에서 새로고침 뒤 대화상자 제목 ‘관리자 로그인’을 확인했다. 로컬 자동 테스트 106개가 통과했다.
