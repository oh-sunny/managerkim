# 사내 행사와 복지 운영의 실제 업무 조사

조사일: 2026년 10월 5일  
목적: 회사에서 실제로 사용할 제품을 만들기 위해, 공개된 운영 경험과 업무 지침에서 문제와 업무 흐름을 확인한다.  
상태: 공개 자료 기반 1차 조사. 제품 수요와 효과가 검증된 단계는 아니다.

이번 조사에서 더 분명하게 확인된 문제는 흩어진 제출물 취합, 불완전한 신청에 대한 재질문, 안내를 받지 못하는 대상자, 신청 이후 처리 상태의 연결이다. **현재 제품의 다음 검증 대상으로는 행사·복지의 신청 및 제출 누락을 정확히 찾고, 필요한 후속 업무를 담당자에게 연결하는 흐름을 제안한다.** 참여율을 분석해 리마인드 주기를 최적화하는 기능은 별도의 효과 검증이 필요하다.

이 문서는 실제 사례와 그 사례에서 도출한 조사 당시의 제품 제안을 구분한다. 현재 확정된 제품 범위·정책은 [PRD](PRD.md), 구현 순서와 진행 상태는 [PLAN](PLAN.md)을 기준으로 한다. 아래 제안과 다음 액션은 조사 기록이며 현재의 확정 요구사항이나 개발 순서를 대체하지 않는다.

## 1 조사 범위와 근거의 해석

본문을 확인한 핵심 자료는 4개 기업의 업무에 관한 8건이다. 기업 자체 기술·조직 블로그 5건, 공식 공개 업무 지침 2건, 외부 서비스 기업이 실무자를 인터뷰한 자료 1건을 선정했다. 행사 운영에 직접 연결되는 사례와 다른 총무 업무에서 참고할 운영 원리를 구분했다.

| 자료 유형 | 확인할 수 있는 것 | 확인할 수 없는 것 |
| --- | --- | --- |
| 담당자가 작성한 기업 공식 운영 사례 | 해당 조직이 겪었다고 밝힌 문제, 운영 방식, 구현 경험 | 모든 기업에서의 발생 빈도, 독립적으로 검증된 효과 |
| 기업 공식 업무 지침 | 정해진 입력 정보, 대상 조건, 담당 역할, 처리 단계 | 실제 준수율, 담당자의 불편 정도, 도입 수요 |
| 외부 기업이 게재한 실무자 인터뷰 | 이름과 소속이 명시된 담당자의 업무 경험 | 인터뷰 내용의 독립 검증, 업계 대표성 |

검색은 사내 행사·복지 운영에서 시작해 총무 자동화, 신청 누락, 도구 접근, 온보딩, 지원금 처리까지 넓혔다. 일반적인 AI 활용 예시, 강의 홍보만 있는 글, 소비자 대상 행사, 출처 불명 재인용은 핵심 근거에서 제외했다. 열람이 불완전했던 카카오 모바일사원증 글도 핵심 분석에서 제외했다.

국내 기술기업과 자동화 성공 사례에 표본이 치우쳐 있다. 원티드랩 자료 3건은 같은 팀의 경험이므로 독립된 3개 기업의 증거로 세지 않는다. 일부 글은 자사 AI 서비스나 교육 홍보를 함께 포함한다. 게시 당시의 경험을 조사한 것이며, 모든 기능이 지금도 같은 방식으로 운영된다는 뜻은 아니다.

## 2 실제 업무 사례

### 2.1 우아한형제들 사내 해커톤 운영

출처: 우아한형제들 기술블로그, 김지은, 2026-07-21. [기술이 없던 곳에 기술 더하기: 사내 해커톤 플랫폼 만들기](https://techblog.woowahan.com/26624/)

**확인된 사실:** 운영 담당자는 팀별 제출 여부와 필수 항목 누락을 확인하고, 심사와 집계를 짧은 시간 안에 처리해야 했다고 설명한다. 파일과 드라이브에 분산된 제출물을 모으는 일에서 시작해, 제출 자료가 평가와 최종 심사 화면으로 이어지는 운영 시스템을 만들었다.

| 구분 | 글에서 확인한 업무 |
| --- | --- |
| 입력 | 참가팀 정보, 제출 자료, 평가 결과 |
| 처리 | 제출 현황 확인 → 동료평가 → 예선 집계 → 최종 심사 |
| 출력 | 심사 단계별 대상과 결과, 종료 후 결과물 전시 |
| 담당자 역할 | 단계 개시와 종료를 관리하고 행사 운영을 진행 |

**제품 시사점 — 추론:** 신청률만 보여주는 화면보다 ‘어느 팀의 어떤 필수 자료가 빠졌는지’와 ‘다음 단계로 넘길 수 있는지’를 보여주는 기능이 구체적인 업무 문제와 가깝다. 이 사례는 리마인드 최적화 효과나 GPT의 필수성을 입증하지 않는다.

### 2.2 PFCT 방문 주차 신청과 담당자 전달

출처: 오피스버디, PFCT 총무팀 실무자 인터뷰, 2026-08-27. [비개발자가 AI로 사내 시스템을 만드는 법](https://blog.buddie.kr/비개발자가-ai로-사내-시스템을-만드는-법-pfct-총무팀-ax-인터뷰-242894)

자료 성격: PFCT 자체 블로그가 아닌 외부 서비스 기업의 인터뷰. 운영 결과는 인터뷰이의 설명이다.

**확인된 사실:** Slack으로 받은 요청에 차량번호·시간 등이 빠지면 재질문이 필요했다. 예약 충돌을 대조하고 주차관리실에 문자로 전달하는 일도 총무팀이 맡았다. 개선 후에는 필수 입력과 가능한 시간대를 제공하고, 담당자 처리 후 신청자 안내와 문자 작성 링크를 연결했다. 문자 최종 발송은 사람이 수행한다.

| 구분 | 인터뷰에서 확인한 업무 |
| --- | --- |
| 입력 | 신청자, 차량번호, 입차 및 주차 시간 |
| 처리 | 신청 접수 → 예약 가능 여부 확인 → 총무 처리 → 주차관리실 전달 |
| 출력 | 등록 또는 반려 안내, 주차 위치 안내, 작성된 문자 링크 |
| 담당자 역할 | 처리 결정, 특이사항 작성, 문자 발송 |

**제품 시사점 — 추론:** 메시지 초안 생성에 앞서 입력 누락과 충돌을 잡아야 한다. 알림 생성·발송과 실제 업무 처리를 각각 기록할 필요가 있다. 행사 신청 자체의 빈도나 비용을 보여주는 자료는 아니다.

### 2.3 원티드랩 자산관리와 사내 도서 대여

출처: 원티드랩 공식 블로그, 피플팀 이찬영, 2026-04-24. [비개발자 총무는 어떻게 사내 AI 에이전트를 만들었을까?](https://blog.wantedlab.com/story/team/people-ai-agent)

**확인된 사실:** 기존 스프레드시트의 조회·계산 부담과 도서 대여 가능 상태를 알기 어려운 문제를 설명한다. 내부 자산 교체 규정을 참고하는 에이전트와 도서대장 갱신 후 Slack DM을 보내는 흐름을 구축했다.

| 구분 | 글에서 확인한 업무 |
| --- | --- |
| 입력 | 자산대장과 내부 규정, 도서 ISBN과 대여·반납 요청 |
| 처리 | 자산 정보·규정 참고 또는 도서 상태 갱신 |
| 출력 | 교체 대상 제안, 갱신된 도서대장, 처리 확인 DM |
| 담당자 역할 | 자산 관련 최종 결정 |

**제품 시사점 — 추론:** 기존 시트나 DB를 기준으로 상태를 바꾸고 확인 결과를 알려주는 연결이 중요하다. 행사마다 별도 자료를 다시 입력하게 만드는 설계는 도입 부담을 늘릴 수 있다. 글의 저비용 구축 경험은 기존 사내 플랫폼·교육·동료 지원이 있었던 조건이므로 우리 제품의 총비용으로 환산할 수 없다.

### 2.4 원티드랩 피플팀 도구의 발견과 사용

출처: 원티드랩 공식 블로그, 피플팀 이찬영, 2026-09-22. [구성원이 가장 많이 사용한 AI 에이전트는? 피플팀 AI 허브, 도피처](https://blog.wantedlab.com/story/team/people-ai-dopicheo)

**확인된 사실:** 도구가 늘면서 주소와 Slack 공지가 흩어지고 신규 입사자는 도구의 존재를 알기 어려웠다. 한 화면에서 상황에 맞는 도구를 찾도록 구성했다. 약 7주 동안 카드 클릭 1,100회를 기록했으며 좌석 체크인이 가장 많았고, 성장지원비 신청이 뒤를 이었다.

| 구분 | 글에서 확인한 업무 |
| --- | --- |
| 입력 | 구성원이 처한 상황이나 찾는 업무 |
| 처리 | 상황 단어로 도구 검색 → 해당 신청·처리 도구로 이동 |
| 출력 | 필요한 업무 창구, 도구별 클릭 기록 |
| 담당자 역할 | 배치·이름·설명을 사용 기록에 따라 조정 |

**제품 시사점 — 추론:** 안내를 여러 번 보내도 신청 창구를 찾기 어렵다면 문제가 남는다. 공지에서 정확한 신청 화면까지 이어지는 접근 경로도 검증해야 한다. 클릭은 고유 사용자·처리 완료·시간 절감 수치가 아니며, 적은 클릭만으로 온보딩처럼 발생 빈도가 낮은 업무의 가치를 판단할 수 없다.

### 2.5 우아한형제들 온보딩 안내 누락

출처: 우아한형제들 기술블로그, 김하루, 2022-11-28. [작고 아기자기하지만, 개발조직의 문화 만들기 ep 3](https://techblog.woowahan.com/9766/)

**확인된 사실:** 팀에 같은 직군 동료가 없는 신규 입사자가 직군 공식 Slack 채널에 초대되지 않아 정보를 놓친 사례가 있었다. 운영진은 인터뷰로 상황을 확인하고, 채용팀으로부터 신규 입사 소식을 받아 맞춤 온보딩을 운영했다.

| 구분 | 글에서 확인한 업무 |
| --- | --- |
| 입력 | 직군별 신규 입사 정보, 당사자 인터뷰 |
| 처리 | 채용팀 알림 → 운영진 확인 → 관련 정보·온보딩 제공 |
| 출력 | 신규 입사자에게 필요한 직군 정보와 개별 온보딩 |
| 담당자 역할 | 부서 간 정보 연결, 일정 조정, 개별 대화 |

**제품 시사점 — 추론:** 미신청 상태만 보고 무관심이나 망각을 추정하면 안 된다. 대상 명단과 공지 채널 접근 범위가 어긋났을 가능성도 확인해야 한다. 이는 2022년 경험이며 현재의 누락률이나 자동화된 처리 수준을 말해주지는 않는다.

### 2.6 GitLab 성장 지원금의 신청부터 종료까지

출처: GitLab 공식 Handbook. [Growth and Development Fund](https://handbook.gitlab.com/handbook/people-group/learning-and-development/growth-and-development/)  
페이지 하단 최종 수정: 2026-09-13. 최초 게시일은 확인하지 않음.

**확인된 절차:** 대상 자격, 요청 정보, 비용에 따른 승인, 구매·참여, 증빙을 갖춘 비용 청구, 종료와 피드백을 구분한다. 신규 요청은 Compass, 비용 청구는 Navan을 사용한다. 이미 진행 중인 기존 요청은 재제출 없이 이전 절차로 완료할 수 있다고 안내한다.

| 구분 | 지침에 명시된 업무 |
| --- | --- |
| 입력 | 신청 자격, 교육·행사명, 제공 업체, 날짜, 비용, 성장 목적 |
| 처리 | 관리자 논의 → 신청 → 승인 → 구매·참여 → 비용 청구 → 종료 |
| 출력 | 승인된 요청, 지출·수료 증빙, 비용 청구와 종료 기록 |
| 사람 역할 | 관리자 등 승인자의 검토, 신청자의 참여와 증빙 제출 |

**제품 시사점 — 추론:** ‘신청 완료’와 ‘복지 이용 완료’를 구분해야 한다. 제도나 도구가 바뀔 때 기존 건에 어느 절차를 적용할지도 필요하다. 이 지침은 실제 운영 규칙의 증거이며, 담당자가 현재 큰 불편을 겪는다는 증거는 아니다. 국내 기업에 같은 자격·금액 기준을 적용하자는 제안도 아니다.

### 2.7 GitLab 지역별 구성원 모임

출처: GitLab 공식 Handbook. [Executive Connect events](https://handbook.gitlab.com/handbook/company/culture/exec-connect/)  
본문 내용 갱신 표시: 2025-11-03. 페이지 하단 파일 수정 표시: 2026-08-03.

**확인된 절차:** 리더 출장에 맞춰 지역 구성원과 모임을 열고, 지정 운영 담당자가 장소·초대·시간을 조율한다. 행사 지역에서 약 60분 거리 이내의 구성원을 대상으로 Slack에 초대하고, 스레드에서 참석 의사를 받는다. 지원 조직은 템플릿과 추적을 돕는다.

| 구분 | 지침에 명시된 업무 |
| --- | --- |
| 입력 | 리더 출장 일정, 행사 위치, 인근 구성원, 운영 조건 |
| 처리 | 일정·장소 조율 → 대상 초대 → 참석 의사 접수 → 행사 진행 |
| 출력 | 참석 의사, 행사 운영, 행사 후 소감·인사이트 공유 |
| 사람 역할 | 운영 담당자의 조율, 리더의 진행과 사후 공유 |

**제품 시사점 — 추론:** 대상 기준이 팀뿐 아니라 위치일 수 있고, 신청 원본이 별도 DB가 아닌 Slack 응답일 수도 있다. 초기에는 지원 가능한 원본을 하나로 한정하되, 회사마다 구조가 다름을 전제로 설계해야 한다. 문서에는 미응답 문제의 규모나 자동 리마인드 효과가 없다.

### 2.8 원티드랩 오피스 모니터링

**확인된 사실:** 센서 정보를 근무시간·공간별 규칙과 연결해 제어·알림·일일 보고를 운영한다. 센서 허브가 꺼져 데이터가 멈춘 경험 이후 전체 데이터 중단 자체를 알리는 규칙을 추가했다.

| 구분 | 글에서 확인한 업무 |
| --- | --- |
| 입력 | 온도·누수 등 센서값, 운영시간과 공간별 기준 |
| 처리 | 정해진 규칙으로 상태 판단 → 제어 또는 알림 → 이력 집계 |
| 출력 | Slack 알림, 아침 보고, 데이터 수집 이상 알림 |

**제품 시사점 — 추론:** 행사 분석도 ‘변화가 없음’과 ‘연동이 끊겨 관측하지 못함’을 나눠야 한다. 단순 임계값은 규칙으로 판단할 수 있다. 이 사례는 시설 운영의 참고 사례이며 행사 참여 분석의 정확도를 입증하지 않는다. AI라는 명칭만으로 모든 판단을 언어모델이 수행한다고 볼 수 없다.

**아직 검증되지 않은 핵심 가설**

- 추가 안내가 참여 증가에 기여하는지, 단순히 마감 효과와 함께 나타나는지.
- 과거 유사 행사를 비교할 만큼 일관된 이력이 존재하는지.
- 담당자가 새로운 화면을 열어 검토하는 수고보다 절감 효과가 큰지.
- 기존 폼·시트·Slack 자동화만으로 충분한 조직에도 별도 제품이 필요한지.

**추천하는 첫 업무 범위:** 모집과 제출 마감이 있는 사내 행사 한 유형에서, ‘대상 명단·신청 자료 대조 → 미제출·정보 누락 구분 → 필요한 후속 업무와 안내 초안 → 담당자 검토 → 처리 결과 확인’을 끝까지 검증한다.

건강검진, 워크숍, 지원금, 공모전은 대상·증빙·종료 기준이 다르다. 동시에 다루기보다 첫 유형에 필요한 차이를 정확히 처리하고 확장하는 편이 낫다. 총무 요청 접수라는 다른 방향도 유력하지만, 이 조사만으로 제품 전체를 그쪽으로 전환할 근거까지 확보한 것은 아니다.

## 5 검증용 업무 흐름 제안

다음 흐름은 여러 자료에서 얻은 시사점을 결합한 우리 제품의 설계 제안이며, 특정 기업이 그대로 운영하는 절차가 아니다.

| 단계 | INPUT | 처리와 책임 | OUTPUT |
| --- | --- | --- | --- |
| 기준 준비 | 행사 정보, 신청 자격, 필수 항목, 기한, 신청 링크 | 담당자가 기준을 확정. AI는 문서에서 후보 값을 추출할 수 있음 | 출처와 버전이 있는 운영 기준 |

| 후속 업무 준비 | 미완료 사유, 기존 안내와 처리 이력 | 시스템이 중복을 점검. AI는 근거를 설명하고 초안 작성 가능 | 누구에게 무엇을 확인할지, 안내 초안 또는 담당자 확인 요청 |

규칙으로 판별할 수 있는 일은 명단 대조, 기한, 필수값, 중복과 최근 안내 여부다. AI 적용 후보는 비정형 문서에서 항목 추출, 서로 다른 표현의 비교, 미완료 사유 설명, 안내 초안 작성이다. 자격·금액·기한·대상자의 확정과 실제 발송은 검증된 기준 및 사람의 책임과 연결한다.

안내 링크 검증은 연결 성공 여부, 올바른 행사 신청 페이지인지, 대상자가 실제 접근할 수 있는지를 나눠 평가해야 한다. 단순히 페이지가 열리는 것만으로 ‘올바른 링크’라고 판정하지 않는 것이 제안 기준이다.

## 6 다음 액션과 필요한 결정

### 먼저 할 일

1. 위 첫 업무 범위에 맞는 행사 한 유형을 고르고, 기존 폼·시트·Slack으로 처리할 때의 최소 흐름을 작성한다. 이를 비교 기준으로 삼는다.
2. 가상 운영 자료를 만든다. 행사 기준문서, 대상 명단, 신청 기록, 안내 이력에 의도적인 누락과 변경을 넣고, 각 경우의 정답을 별도로 기록한다.
3. 같은 자료로 기존 방식과 제품 흐름을 실행해 누락 탐지, 불필요한 안내, 검토에 필요한 단계를 비교한다. 가상 데이터 결과는 동작·정확성 검증으로 표시한다.
4. 입력과 완료 조건이 분명해지면 PRD의 문제·범위·workflow를 수정한다. 공개 근거가 있는 내용, 제품 가설, 확정한 정책을 표시한다.
5. 이후 현업 검토 기회가 생기면 익명화된 자료나 시나리오만으로도 업무 흐름의 현실성을 확인한다. 실제 회사 데이터를 확보할 때까지 개발 전체를 미룰 필요는 없다.

### 사용자가 정할 제품 정책

- 첫 운영 유형: 행사 모집·제출을 우선 검증할지, 총무 요청 처리를 비교 실험할지. 이번 추천은 전자다.
- 첫 입력 원본: CSV 또는 시트 한 종류부터 시작할지, 특정 신청 API를 전제로 할지.
- 제품의 완료 범위: 후속 업무 준비까지인지, 승인한 알림 실행과 처리 결과 확인까지인지.

지금 PRD를 수정하지 말아야 하는 것은 아니다. **이번 조사로 근거와 가설을 구분하고, 다음에는 첫 업무의 원본·예외·완료 조건을 정해 PRD를 수정할 수 있는 단계다.** 실제 고객의 절감 시간, 지불 의사, 운영 품질 향상은 후속 현장 검증 과제로 남는다.
