# 사내 행사·복지 안내 운영 도구 PRD

수정일: 2026년 10월 6일

상태: 제품 방향과 개발 범위. 구현 완료 여부는 [spec_001](../spec/spec_001.md)에서 확인한다.

**여러 행사와 복지를 운영할 때, 신청 현황·일정·이전 안내를 함께 확인해 누구에게 언제 무엇을 안내할지 결정하고 실행하는 도구.**

**공지 작성의 중심은 기획서 요약이 아니라 구성원의 행동이다.** 공지를 읽는 사람이 자신에게 해당하는지, 무엇을 어떻게 해야 하는지, 언제까지 해야 하는지를 바로 알 수 있도록 기획서·관련 자료에서 필요한 사실만 골라 재구성한다. 배경·예산·운영 논리는 구성원 행동이나 이해에 필요한 경우에만 포함한다.

## 1 해결할 문제와 사용자

주 사용자는 사내 행사와 복지를 운영하는 총무·피플 운영 담당자다. 담당자는 신청 명단에서 아직 신청하지 않은 사람을 찾고, 공지의 날짜·설명·신청 링크가 맞는지 검토하며, 이전 안내와 다음 일정을 반복해서 확인한다. 여러 건을 함께 운영하거나 신청·취소가 계속 발생하면 이 대조 작업을 다시 해야 한다.

제품은 이 반복 확인을 줄이고, 근거 있는 안내를 준비하는 데 집중한다. 동료는 기존 신청 창구를 이용하며 첫 버전의 운영자는 1명이다.

공개 업무 사례와 출처는 [research_001](research_001.md)에 보관한다. 관련 업무가 존재한다는 근거와 이 제품의 도입 수요는 구분한다. 실제 사용자의 절감 시간·오발송 감소·도입 의사는 아직 검증하지 않았다.

## 2 제품 범위와 핵심 기능

모집·신청·안내가 필요한 사내 행사와 복지에 적용한다. 행사 종류마다 다른 전체 업무를 자동화하기보다, 공통으로 반복되는 **현황 확인 → 안내 판단 → 검토·발송 → 기록과 현황 재확인**을 완성한다.

| 핵심 기능 | 제품이 제공할 가치 | SPEC 연결 |
| --- | --- | --- |
| 홈과 전체 확인할 일 | 오늘 살필 행사·복지와 근거를 확인하고, 하나를 열면 예정·대기·완료 티켓을 모두 조회 | F01·F02 |
| 캘린더 | 신청 마감·행사일·안내 검토 일정을 함께 확인 | F03 |
| 공지용 정보 카드와 안내 초안 | 자료에서 구성원의 행동에 필요한 사실을 추출·확정한 뒤, 안내 목적과 말투에 맞는 초안을 검토·수정 | F04·SPEC 002 |
| 대상·발송 방식 선택 | 대상 동료를 팀 또는 개인별로 골라 개별 DM을 보내거나 지정한 여러 Slack 채널에 게시 | F05·F06 |
| 승인 후 발송 | 최신 대상과 본문을 확인하고 실행 결과를 구분해 기록 | F07 |
| 안내 기록과 저장 | 당시 원문·대상·시각·Slack 링크를 다시 확인하고 운영을 이어감 | F08·F09 |

현황 분석과 리마인드 제안은 홈·티켓·초안을 작동시키는 핵심 판단 기능이다. 별도 분석 화면을 늘리는 것보다 담당자가 다음 행동을 결정할 때 근거를 제공한다.

개인별 복지 신청의 승인·증빙 심사·구매·지급·담당자 인계와 범용 업무 관리 기능은 향후 확장 후보이며, 위 기능의 완성 조건이 아니다. 화면에는 실제 행사·복지 이름과 ‘확인할 일’을 우선 사용한다. 현재 구현 명칭인 ‘프로젝트·티켓’은 SPEC에서 유지한다.

## 3 사용 흐름과 입력·출력

| 단계 | 입력 | 시스템과 사람이 하는 일 | 출력 |
| --- | --- | --- | --- |
| 1 운영 정보 등록 | 이름, 설명, 대상 명단·팀, 필수/자율 여부, 신청 후 확정 방식, 신청 기간, 행사일 또는 운영 일정, 목표 신청률, 신청·참고 링크, 담당자 | 담당자가 직접 입력하거나 AI가 자료에서 추출한 후보를 검토·확정하고 시스템이 누락·충돌을 표시 | 안내와 현황 판단에 사용할 기준 정보 |
| 2 신청 현황 확인 | 대상 명단, 신청·취소 기록, 조회 시각 | 시스템이 고유 식별자로 대조하고 최신성·조회 실패를 구분 | 신청률, 신청 전 동료, 필수 대상 현황, 마지막 확인 시각 |
| 3 다음 안내 검토 | 현황, 남은 기간, 이전 안내, 선택적으로 과거 유사 운영 기록 | 시스템이 정한 규칙에 따라 최초 공지·추가 안내·보류 검토를 제안 | 중복 없는 확인할 일, 제안 이유, 추천 대상·검토 시점, 초안 |
| 4 담당자 검토 | 제안 근거, 초안, 수신 명단 또는 채널 | 담당자가 사실·링크·대상을 확인하고 수정·승인·보류·안내하지 않기를 선택 | 확정한 안내 또는 사유와 다음 검토 시점 |
| 5 발송과 기록 | 승인한 본문·대상·발송 방식 | 시스템이 실행 전 최신 상태를 다시 확인하고 승인된 범위로 발송 | 성공·실패·결과 불명, 당시 원문과 대상, Slack 링크 |
| 6 현황 재확인 | 새 신청·취소, 발송 결과, 다음 확인 일정 | 시스템이 현황과 미처리 제안을 갱신하고 담당자가 종료 여부 확인 | 갱신된 홈·전체 티켓·캘린더·안내 이력 |

원본이 바뀌거나 정한 확인 시점이 되면 2~6단계를 반복한다. 안내를 보낸 것과 동료가 신청한 것, 행사가 끝난 것은 각각 다른 상태다. 발송했다고 신청률을 올리거나 행사 전체를 완료 처리하지 않는다.

현황 판단은 Google Drive에 있는 Google 스프레드시트의 신청·취소 데이터를 첫 원본으로 한다. 원본에는 최신 상태뿐 아니라 신청·취소의 이력 행도 둔다. 서버가 Google Sheets API로 읽으며, 추후 다른 DB로 바꿀 수 있도록 원본 조회와 현황 계산·안내 판단을 분리한다. 미신청자는 신청 기록만으로 알 수 없으므로 프로젝트별 대상 명단도 필요하다.

자료 입력은 여러 PDF·DOCX·텍스트를 함께 해석하는 흐름을 지원한다. 스캔 PDF는 OCR을 사용하고 인식 결과임을 표시한다. 항목별 원문 출처·누락·서로 다른 정보를 보여주며, 운영자가 선택·수정한 값만 운영 기준으로 적용한다. 원본 문서의 명령을 실행하거나 대상 동료를 임의로 확정하지 않는다. 파일 지원 범위·처리 제한·보관 방식의 현재 구현은 [SPEC 002 9절](../spec/spec_002.md#9-기획서에서-프로젝트-정보-채우기)을 따른다.

### 공지용 정보 카드: 기획서와 공지 사이의 확인 단계

**기획서·관련 자료 입력 → 공지용 정보 후보 추출 → 담당자 확인·수정·제외 → 이번 안내의 정보 카드 확정 → 안내 목적·말투 선택 → 공지 초안 생성** 순서로 진행한다. 프로젝트 운영 정보 등록과 공지용 정보 카드 확인은 서로 다른 작업이다. 등록 정보에는 내부 운영에 필요한 내용도 남을 수 있지만, 정보 카드에는 이번 공지를 받는 구성원이 알아야 할 내용만 담는다. 리마인드라면 현재 신청 현황과 이전 안내도 함께 확인한다.

| 정보 카드 항목 | 구성원이 알아야 할 내용 | 확인할 원본 |
| --- | --- | --- |
| 무엇을 | 행사·복지·프로그램의 이름과 이번 안내의 목적 | 제목·운영 내용 |
| 대상 | 누가 참여하거나 신청할 수 있는지 | 대상 조직·자격·필수/자율 조건 |
| **해야 할 일** | 신청·제출·선택 등 구체적인 행동 | 신청 절차·제출 요구 |
| **마감** | 행동을 끝내야 할 날짜와 시각, 시간대 | 신청 기간·마감 조건 |
| 언제·어디서 | 행사일·운영 기간·장소 | 일정·장소·검진기관 등 |
| 어떻게 | 행동 순서와 필요한 경로 | 신청 방법·프로세스 |
| 비용·지원 | 구성원이 부담하거나 지원받는 범위 | 비용·회사 지원 조건 |
| 예외·주의 | 변경·취소·미참여 시 알아야 할 조건 | 예외 규정·유의사항 |
| 문의 | 질문할 담당자·채널 | 담당자·문의처 |
| 링크·첨부 | 행동에 필요한 신청 링크와 상세 자료 | 신청서·안내문·파일 |

**해야 할 일과 마감은 별도 항목**으로 다룬다. 신청을 요청하는 안내에서는 두 항목을 초안의 핵심으로 확인한다. 단순 정보 공지처럼 행동이나 마감이 적용되지 않는 경우에는 ‘해당 없음’으로 표시한다. 적용되지만 원본에 없는 경우에는 임의로 채우지 않고 ‘확인 필요’로 남긴다. 예를 들어 기획서에 ‘10월 16일까지 제출’만 있으면 마감일은 추출할 수 있지만 `18:00`은 확인된 시각으로 쓰지 않는다. 비용 지원이나 마감 후 변경 불가도 원본에 없으면 사실처럼 추가하지 않는다.

예를 들어 ‘전 임직원이 10월 16일까지 희망 검진기관을 선택해 제출하고, 검진 기간은 11월 1~30일’이라는 원문이라면 카드에는 **대상: 전 임직원 / 해야 할 일: 희망 검진기관 선택·제출 / 마감: 10월 16일(시각 확인 필요) / 검진 기간: 11월 1~30일**을 담는다. 지원 비용·변경 제한·문의처는 별도 근거가 없다면 확인 필요로 남긴다.

각 후보에는 **출처와 상태(자료에서 확인됨 / 확인 필요 / 자료 간 충돌 / 해당 없음)**를 붙인다. 담당자는 값을 수정하거나 이번 공지에서 제외할 수 있으며, 직접 입력한 값은 문서에서 확인한 값과 구분한다. 서로 다른 날짜·대상·링크가 있으면 자동으로 하나를 선택하지 않는다. 누락·충돌한 핵심 항목은 담당자가 확인하기 전까지 확정된 사실로 초안에 넣지 않는다.

말투와 안내 유형(최초 공지·마감 강조·리마인드 등)은 **확정한 정보 카드의 표현 방식**을 바꾼다. 말투를 바꿔도 대상·행동·마감·링크 같은 사실은 바뀌지 않아야 한다. 담당자가 제외한 항목을 다시 넣거나 원문에 없는 사실을 보태지 않는다. 초안은 발송 전에 본문·대상·자료를 다시 확인하며, 실제 발송 기록에는 당시 사용한 확정 정보와 본문을 남긴다. 세부 화면·상태 계약과 현재 구현 범위는 [SPEC 002](../spec/spec_002.md)를 따른다.

신청 후 확정 방식은 프로젝트마다 설정한다. 최소한 **신청 즉시 확정 / 별도 확인·승인·선정 후 확정**을 구분하고 정원·대기 조건은 별도로 확인한다. AI는 자료의 근거와 함께 후보를 제시하며, 명시되지 않은 조건은 미정으로 남긴다. 사용자가 확정하기 전에는 운영 규칙으로 적용하지 않는다. 별도 절차가 있는 경우 신청 완료와 참여·이용 확정을 구분하며, 이미 신청한 승인·선정 대기자에게 미신청 안내를 하지 않는다. 승인·선정 자체의 자동화는 현재 범위에 포함하지 않는다.

## 4 분석과 리마인드 제안의 기준

- **신청률의 기준:** 프로젝트별 신청 대상 명단 중 유효한 신청자 수 ÷ 해당 대상 명단 인원 수로 계산한다. 전사 대상이면 전사 직원 수, 특정 팀·조건 대상이면 그 명단의 인원 수가 분모다. 중복·취소를 반영하고 유효한 신청자와 참여·이용 확정자를 구분한다. 채널 구성원 수·DM 발송 수·실제 열람 수와 혼용하지 않는다. 대상이 0명이거나 조회에 실패하면 정상 비율처럼 표시하지 않는다. 신청률과 실제 참석률도 구분한다.
- **필수 신청 안내:** 필수 신청자 중 아직 신청하지 않은 동료가 있으면 마감 3일 전·1일 전 날짜의 오전 10시와 마감 4시간 전에 안내 검토를 제안한다. 마지막 확인의 시간 간격은 프로젝트별 변경 가능하다. D-3·D-1은 영업일이 아닌 달력 날짜로 계산한 후 아래 업무시간 규칙을 적용한다. 종전 D-7·D-3·D-1 기본안을 대체하며 자동 발송은 하지 않는다. 마감 후에는 마감·연장 정책에 따른다.
- **자율 신청 안내:** 목표 신청률의 분모는 프로젝트 대상 중 **자율 신청자 수**이고 분자는 그중 유효한 신청자 수다. 필수 신청자는 자율 목표의 분자·분모에서 모두 제외하며, 프로젝트 전체 신청률은 별도로 표시한다. 목표가 있으면 D-3 오전 10시에 목표 인원의 70% 미만, D-1 오전 10시에 90% 미만일 때 추가 안내 검토를 제안한다. 목표 없이 운영할 수도 있으며 그때는 현황만 표시한다. 점검 기준은 프로젝트별 변경 가능하다. 비교에는 표시용 반올림 전 값을 사용하며 기준과 같거나 높으면 이 사유로 제안하지 않는다. 자율 대상이 0명이면 목표 달성률을 계산하지 않는다. 이 수치는 합의한 초기 운영 기준이며 달성 실패를 예측한 결과는 아니다. 실제 추세와 과거 기록을 이용한 예측은 이후 검증해 추가한다.
- **업무시간:** 기본은 한국 시간(Asia/Seoul) 평일 오전 9시~오후 6시이며 주말·공휴일을 제외한다. 업무시간 밖의 확인 시점은 그보다 앞선 가장 가까운 업무시간으로 당긴다. 월요일 오전 8시라면 직전 근무일 오후 6시가 된다. 프로젝트별 변경을 지원하고 원래 시각과 조정 시각을 함께 표시한다. 업무 종료 시각인 18:00도 조정 결과로 사용할 수 있다. 조정 후 같은 대상·목적의 점검이 겹치면 중복 티켓을 만들지 않는다. 신청 기간 시작 전으로 이동하는 등 유효한 점검 시각이 없으면 담당자의 확인이 필요하다고 표시한다. 공휴일 자료를 조회하지 못한 경우 모든 평일을 근무일로 확인한 것처럼 표시하지 않는다.
- **재안내와 이력:** 고정된 24시간 재안내 제한은 두지 않는다. 제안 검토 화면에서 최근 발송 시각·대상·목적·원문·Slack 링크를 쉽게 확인해 담당자가 재안내 여부를 판단한다. 같은 사유의 티켓 중복 생성과 한 번의 발송 요청이 기술적으로 중복 실행되는 것은 별도로 막는다. 제안은 자동 발송을 뜻하지 않는다.
- **공통 발송 조건:** 최근 안내, 대상과 데이터 최신성, 접수 종료·정원 상태를 함께 확인한다. 기준이 없는 자율 신청은 목표 미달을 임의 판정하지 않는다. 자율 참여의 미신청은 직원의 잘못이나 미이행으로 표시하지 않는다. 동일 프로젝트에 필수·자율 대상이 함께 있으면 각 대상의 안내 조건을 구분한다.
- **과거 비교:** 운영 유형·대상·필수 여부·모집 기간이 유사한 기록의 같은 마감 전 시점과 비교한다. 비교 기록 수·기간·차이를 표시하며, 자료가 부족하면 기본 규칙으로 판단한다. 안내 후 신청이 늘었다고 안내의 효과나 최적 주기가 입증된 것으로 설명하지 않는다.
- **제안 근거:** 판단에 사용한 수치·원본 확인 시각·최근 안내와 제안 이유를 함께 보여준다. 같은 사유의 티켓을 반복 생성하지 않으며, 보류한 제안은 정한 재검토 조건이 있을 때 갱신한다.
- **변경과 불확실성:** 일정·대상·신청 상태가 바뀌면 미발송 제안을 다시 계산한다. 조회 실패는 신청 0명으로 취급하지 않고, 마지막 확인 상태와 오류를 표시한다.

## 5 안내 품질과 발송의 필수 조건

- 홈의 확인할 일을 열면 해당 행사·복지의 전체 티켓이 열린다. 홈 하단에는 캘린더·목록 보기를 제공한다.
- 초안은 확정된 운영 정보에서 날짜·대상·신청 링크를 가져온다. 필수 항목 누락과 기준 정보의 불일치를 표시하고, 확인할 수 없는 설명·링크 접근 권한은 담당자 검토 항목으로 남긴다. 링크 형식이 맞는 것만으로 실제 신청 가능을 보장하지 않는다.
- DM은 대상 범위와 팀 또는 개인 선택의 교집합에 해당하는 동료에게 각각 발송한다. 그룹 DM 생성과 구분한다. 채널은 여러 곳을 선택할 수 있으며 각 채널의 공개 범위를 개별 확인한다. 채널에는 개인별 미신청 상태를 자동 공개하지 않는다.
- 지정 채널의 공개·비공개·외부 공유 여부와 게시 가능 여부를 확인한다. 채널 구성원 수를 전체 공개 범위나 실제 열람 수로 표시하지 않는다.
- 본문·대상·발송 방식·채널이 바뀌면 기존 승인을 해제한다. 실행 전 조회가 실패하면 발송을 보류하고, 신청·취소로 승인 대상이 달라졌으면 다시 확인한다.
- 초안 본문·대상·링크·파일 선택은 서버에 임시 저장해 복원한다. **발송 확인 체크는 저장·복원하지 않는다.** 화면을 새로 열면 최종 본문과 대상·자료를 다시 확인해야 보내기 버튼이 활성화된다.
- 첨부 자료는 발송 전에 민감 정보 검사를 거친다. 개인 건강검진 결과나 주민등록번호 등 개인별 민감 정보가 탐지되거나 파일을 읽을 수 없으면 발송을 보류하고, 위치·유형을 담당자에게 보여 수정·삭제·재검토하게 한다. 자동 검사를 통과해도 자료의 적합성과 공개 범위는 담당자가 최종 확인한다. 검사 원문과 탐지값을 불필요하게 로그에 남기지 않는다.
- 수신자별 발송 결과와 채널 게시 결과를 구분한다. 부분 실패·결과 불명을 성공으로 처리하거나 확인 없이 전체 재발송하지 않는다.
- 실제 발송 원문은 보존한다. 수동으로 추가한 외부 안내 기록은 출처와 확인 수준을 구분하며 원문 또는 Slack 링크를 남긴다. 수정 가능한 수동 기록을 실제 발송 증거와 혼동하지 않는다.
- 화면은 ‘확인할 일’, ‘신청 전’, ‘보낼 내용 확인’처럼 행동을 알 수 있는 표현을 사용한다. 특정 회사의 공식 내부 말투라고 주장하지 않는다.

## 6 사람·시스템·AI의 역할

| 주체 | 맡는 일 |
| --- | --- |
| 규칙 기반 시스템 | 신청 현황 계산, 일정 확인, 대상 대조, 기본 제안, 중복 방지, 사실 항목 검사, 승인 검사, 발송과 결과 저장 |
| 선택적 AI | 확정된 정보를 이용한 안내 초안 작성, 비교 결과와 제안 이유의 설명, 운영 자료에서 입력 후보 추출 |
| 담당자 | 운영 기준 확정, 예외 판단, 사실·링크·공개 범위 검토, 제안 채택·보류, 최종 발송 승인 |

GPT API는 필수가 아니다. 먼저 규칙과 템플릿으로 흐름을 완성하고, 작성·해석 품질이 좋아지는 부분에 AI를 적용한다. AI가 수신 명단을 추측하거나 승인 없이 발송하지 않는다.

주기 조회와 예약된 검토는 배포된 서버의 작업 실행 기능이 맡는다. 모델 API를 연결하는 것만으로 상시 감시가 실행되지는 않는다. 현재 프로토타입에는 이 자동 실행 기능이 없다.

## 7 성공 기준

구현 순서·단계별 완료 기준과 진행 상태는 [PLAN](PLAN.md)에서 관리한다. 현재 동작과 기능별 한계는 [SPEC](../spec/spec_001.md)에서 확인한다.

성공 기준은 현황 대조부터 안내 준비까지 걸리는 시간, 누락·잘못된 대상·중복 안내 발생, 초안 수정 부담, 제안 채택·보류 이유다. 새 도구에 정보를 입력하고 관리하는 시간도 함께 측정한다. 참여율 증가는 참고 결과로 보고 제품 효과로 단정하지 않는다. 예시 데이터는 동작 검증에 쓰며 현업 효용의 증거로 삼지 않는다.

## 8 구현 전에 남은 결정

| 결정 | 필요한 내용 |
| --- | --- |
| 첫 신청 원본 | Google 스프레드시트로 확정하고 신청·취소 이력 행을 포함. 시트 ID·접근 권한, 대상 명단, 동료 식별자, 이력 행의 ID·시각·상태 값과 갱신 방식은 확인 필요. 로컬에서는 버튼으로 같은 변화를 재현 |
| 등록 정보와 대상 변경 | 필수/자율 대상 지정, 프로젝트별 확정 방식과 정원·대기 조건, 진행 중 명단·일정 변경의 적용 기준 |
| 안내 예외와 운영 달력 | 공개 전국 공휴일 달력의 갱신 시차·장애 대응, 채널과 DM 사이의 동일 대상 판정, 수동 기록의 발송 확인 수준, 총 안내 횟수 상한·보류 후 재검토 조건. 회사 자체 휴무일은 범위에서 제외 |
| 마감과 종료 | 마감 후 신규 모집 안내 중단, 연장·취소 시 처리, 운영 종료 판단 주체 |
| 실제 연동 권한과 보존 | 조회·발송 가능한 정보와 채널, 발송 기록 보존 기간, 계정·접근 범위 |

미정 항목은 해당 개발 단계에서 결정한다. 이 PRD에는 임의의 효과 수치·세부 DB 설계·가상 테스트 정답표를 넣지 않는다.
