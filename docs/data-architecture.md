# 데이터 흐름과 저장 구조 초안

작성일: 2026년 10월 5일  
상태: 설계 초안. Supabase·Gemini·Slack 연동은 아직 구현되지 않았다.

이 문서는 [PRD](PRD.md)의 제품 흐름을 데이터와 API 관점에서 풀어 쓴다. [SPEC](spec_001.md)은 **현재 동작**, [PLAN](PLAN.md)은 **구현 순서**, 이 문서는 **앞으로 연결할 데이터의 책임과 관계**를 관리한다. 테이블 이름과 필드는 논리 모델의 제안이며 확정된 SQL 스키마가 아니다.

## 1. 전체 흐름과 데이터의 책임

```text
운영자 웹사이트
  ├─ 프로젝트 필드 직접 입력 ───────────────────────────────┐
  ├─ 텍스트 붙여넣기 → Database: 원문 텍스트                  │
  └─ 파일 업로드(TXT/MD/PDF/DOCX 등)                         │
                       ↓                                   │
             Supabase Storage: 원본 파일                    │
                       ↓                                   │
             서버 함수: 형식별 읽기·후보 추출               │
                       ↔ Gemini API: 복잡한 해석(선택)     │
                       ↓                                   │
             Database: 근거가 있는 필드 후보                │
                       ↓                                   │
             운영자 검토·수정·확정 ──────────────────────────┤
                                                           ↓
                           Database: 확정 운영 정보·승인된 참고 내용·입력 출처
                                                           ↓
신청 원본/API → 조회·정규화 → 신청 현황 → 규칙 기반 점검 일정·티켓
                                                           ↓
확정 정보 + 승인된 참고 내용 + 최신 현황 + 이전 안내
                                  → 템플릿 또는 Gemini API → 공지 초안
                                                           ↓
                               담당자 검토·승인 → 발송 시도·결과
                                                           ↓
                                           안내 이력과 다음 현황 재확인
```

사용자는 프로젝트 필드를 직접 입력하거나, 설명·기획 내용을 **텍스트로 붙여넣거나**, TXT·MD·PDF·DOCX 등 파일로 제공할 수 있다. 붙여넣은 원문은 접근 제한이 있는 Database에, 업로드한 원본 파일은 비공개 Supabase Storage에 보관하는 안이다. 파일명·형식·Storage 경로와 입력자·시각은 Database에 기록한다. 모든 입력에서 추출한 값은 우선 후보이며, 운영자가 확정한 정보와 구분한다.

Gemini는 입력 내용을 해석해 후보를 반환하거나, 확정된 정보를 바탕으로 공지 문안을 작성할 수 있지만 Supabase에 직접 기록하지 않는다. 서버 함수가 데이터를 읽고 모델을 호출하며 응답을 검사·저장한다. **일정 판단과 공지의 사실 항목**에는 운영자가 확정한 정보·승인한 참고 내용과 조회 시각을 확인한 신청 현황만 사용한다. AI가 미확정 원문의 날짜·대상을 그대로 사실로 쓰지 않는다.

파일이나 텍스트를 먼저 넣고 나중에 프로젝트 정보를 확정하는 등록 흐름에는 임시 프로젝트 ID와 `draft` 상태를 만든다. 입력 원본과 후보는 그 ID에 연결하고, 운영자가 등록을 완료할 때 프로젝트를 `active`로 바꾼다. 중간에 등록을 그만둔 원본은 별도 정리 기준을 적용한다.

파일 업로드 또는 텍스트 저장 직후 웹사이트가 분석 함수를 호출하는 방식을 우선 검토한다. 원본 저장 성공, 분석 성공, 프로젝트 정보 확정은 각각 다른 단계다. 분석 실패 시에도 원본과 오류 상태를 확인하고 다시 시도할 수 있어야 한다.

| 안내 기록·모의 발송 | `records`, `completed`와 `localStorage` | 발송 시도·대상별 결과·원문·외부 링크, 수동 기록 분리 |
| 실제 Slack·서버 주기 실행 | 미지원 | 서버 측 발송 기능·작업 실행 이력 |

지금의 [계산 코드](../prototype/data.js)는 프로젝트별 대상 명단과 신청 상태를 받아 신청률과 미신청 명단을 계산한다. 저장 위치를 옮기더라도 **원본 읽기 → 공통 신청 형식 → 현황 계산**의 경계를 유지한다. 브라우저 저장 자료를 Supabase로 자동 이전할지, 예시 자료를 새로 시작할지는 별도로 결정한다.

## 3. 최소 데이터 묶음

아래 묶음은 개념적 구조다. 모든 항목을 한 번에 구현하지 않고 연결하는 기능에 맞춰 추가한다. 각 행은 안정적인 ID와 생성·수정 시각을 갖고, 연결 관계에는 해당 프로젝트 ID를 사용한다.

| 묶음 | 제안 테이블 | 최소로 구분할 정보 |
| --- | --- | --- |
| 운영 기준 | `projects` | 이름·설명·신청 시작/마감·행사/운영 일정·신청 링크·담당자·확정 방식·운영 상태·목표 신청률·시간대. 미정 값은 `NULL`로 두고 확정 여부를 구분 |
| 대상과 식별 | `people`, `project_targets` | 동료의 안정적인 ID·팀, 프로젝트 대상 여부·필수 여부. 문서의 이름만으로 실제 동료 ID를 확정하지 않음 |
| 입력 원본 | `project_inputs`와 비공개 Storage 버킷 | `input_kind`(붙여넣은 텍스트/파일), 프로젝트 ID, 입력자·시각. 텍스트는 접근 제한된 원문, 파일은 파일명·형식·크기·Storage 경로를 연결. 원본과 확정값은 다름 |
| 분석 실행과 후보 | `input_analyses`, `field_candidates` | 어떤 입력·모델/규칙 버전에서 나온 후보인지, 필드명·후보값·근거 문구·위치(텍스트 줄/문서 페이지·문단)·검토 상태. 재분석 결과는 이전 결과와 구분 |
| 확정값의 출처 | `project_field_sources` | 프로젝트의 각 주요 값에 대해 직접 입력인지, 어떤 후보를 적용했는지, 누가 언제 확정했는지. 확정값 자체는 `projects`에 둠 |
| 공지용 참고 내용 | `approved_source_notes` | 고정 필드에 담기 어려운 행사 내용·준비물·문의 방법·주의사항 중 운영자가 사용을 승인한 문장/요약과 원문 위치·승인자·시각 |
| 신청 원본과 현재 상태 | `application_sources`, `source_sync_runs`, `applications` | 원본 종류·연결 상태, 마지막 **성공** 조회와 실패, 프로젝트·동료별 최신 신청 상태(`applied`/`confirmed`/`cancelled`), 원본 식별자와 변경 시각 |
| 점검 규칙과 제안 | `reminder_rules`, `check_schedules`, `tickets` | 프로젝트별 기준과 시간대, 원래 점검 시각·업무시간 조정 시각, 판단에 쓴 현황·원본 확인 시각, 티켓 목적·대상·상태·보류/재검토 조건 |
| 안내 준비 | `notice_drafts`, `notice_approvals` | 초안 본문과 버전, 초안 생성 방식(템플릿/AI), 사용한 확정 운영 정보·신청 현황 조회 시각·이전 안내 참조, 대상·발송 방식·채널, 승인자·승인 시각 |
| 실행과 안내 이력 | `send_attempts`, `send_results`, `manual_notice_records` | 시도 ID, 실행 시각, 당시 본문·대상, 수신자 또는 채널별 성공/실패/결과 불명, Slack 메시지 ID·링크. 수동 입력 기록과 실제 발송 결과 구분 |
| 업무 변경 이력 | `activity_events` | 행위자·시각·프로젝트·행동 유형·대상 ID·이전/이후 상태의 필요한 부분. 민감한 본문·파일 전체를 무조건 복제하지 않음 |

### 현재 상태와 이력을 함께 남기는 이유

- `applications`의 현재 상태가 `cancelled`이면 현황 계산에서는 미신청자로 돌아간다. 별도 변경 이력에는 신청과 취소가 언제 발생했는지 남긴다.
- `projects.deadline`의 현재 값이 바뀌어도, 과거 티켓·승인·발송이 어떤 마감일을 기준으로 만들어졌는지 추적할 수 있어야 한다.
- `send_attempts`에는 버튼 클릭이나 API 요청 **시도**를, `send_results`에는 실제 전송 결과를 기록한다. 시도만으로 성공 처리하지 않는다.
- Supabase의 기술 로그와 `activity_events` 같은 **제품 업무 이력**은 목적이 다르다. 취소·승인·보류의 의미를 나중에 확인하려면 앱이 업무 이력을 직접 기록해야 한다.

## 4. 파일·텍스트 분석에서 확정까지

1. **원본 저장:** 로그인한 운영자가 텍스트를 붙여넣거나 파일을 선택한다. 붙여넣은 글은 `project_inputs`에 원문으로 저장한다. 파일은 비공개 버킷에 저장하고 `project_inputs`에 경로와 상태를 기록한다. 길이·파일 형식·크기·접근 권한을 검사한다.
2. **분석 요청:** 웹사이트가 입력 ID를 서버 함수에 보낸다. 함수는 프로젝트 접근 권한을 확인하고 텍스트 원문 또는 Storage의 파일을 읽는다. Supabase의 비공개 경로 문자열만 Gemini에 전달해서 읽게 하지 않는다.
3. **내용 해석:** 명시적 항목은 규칙으로 찾고, 복잡한 문장은 선택한 AI 서비스에 필요한 내용만 전달한다. TXT/MD와 붙여넣은 글은 텍스트로 처리한다. PDF는 문서 처리 방식으로 보낼 수 있다. DOCX는 우선 텍스트/표 추출 또는 PDF 변환 방식을 정한다. 스캔본과 표의 품질은 별도로 검증한다.
4. **구조화와 검증:** 모델에는 필요한 필드, 값이 없을 때 `null`, 근거 원문과 위치를 요구한다. 서버는 응답 형식·날짜·URL·값의 범위를 검사한다. JSON 형식이 맞아도 사실이 맞는 것은 아니다. 후보와 분석 실행 ID를 저장하고 상태를 `review_required`로 바꾼다.
5. **운영자 확정:** 각 후보를 적용·수정·제외한다. 입력 원본끼리 또는 기존 직접 입력과 값이 다르면 차이를 보여준다. 고정 필드에 담기 어려운 상세 안내 내용도 공지에 사용할 부분을 선택·수정해 승인할 수 있다. 확정값·승인된 참고 내용과 출처·시각을 저장하고, 이를 기준으로 초안과 점검 일정을 다시 계산한다.

예시 후보 응답의 형태:

```json
{
  "field": "deadline_at",
  "candidate_value": "2026-10-20T18:00:00+09:00",
  "evidence_text": "참가 신청은 10월 20일 오후 6시에 마감합니다.",
  "source_location": "2쪽, 신청 방법",
  "extraction_method": "ai",
  "review_status": "pending"
}
```

이 예시는 계약 형식의 초안이다. 붙여넣은 글이라면 `source_location`은 줄 번호 등으로 표시할 수 있다. 모델이 근거 위치를 정확히 찾지 못하면 위치를 추측해 채우지 않고 확인 필요로 둔다. 원본은 Supabase에 보관하며, 분석을 위해 Gemini에 전달한 내용은 별도 서비스에서 처리된다. 어떤 입력을 외부 AI에 보낼 수 있는지와 보존 정책은 연동 전에 결정한다.

## 5. 공지 초안 작성에 사용하는 데이터와 API

초안 생성은 파일 분석과 **별도 요청**이다. 등록 화면에서 확정된 프로젝트 정보뿐 아니라, 초안을 만드는 시점의 신청 현황과 이전 안내도 함께 읽는다. 서버 함수가 이 자료를 모아 템플릿을 채우거나 Gemini API에 문장 작성을 요청한다. Supabase API는 저장된 정보를 읽고 초안 버전을 기록하는 데, Gemini API는 필요한 경우 문장을 작성하는 데 쓰인다. 신청 원본 API가 연결되면 최신 신청·취소 상태를 가져오는 데 사용한다. Slack API는 초안 생성이 아니라 승인 후 실제 발송 단계에서 사용한다.

| 초안 입력 | 출처 | 사용할 때의 확인 |
| --- | --- | --- |
| 프로젝트명·설명·대상·필수 여부·일정·신청 링크·담당자 | 운영자가 직접 입력하거나 파일/텍스트 후보에서 **확정한** `projects` 정보 | 미확정 후보를 사실로 사용하지 않음. 변경된 날짜와 링크를 확인 |
| 행사 상세 내용·준비물·문의 방법 등 | 운영자가 직접 작성하거나 파일/텍스트에서 골라 승인한 `approved_source_notes` | 원문 근거와 승인 범위를 확인. 미검토 원문 전체를 그대로 초안의 사실로 쓰지 않음 |
| 신청·취소·확정, 미신청 대상과 신청률 | 정규화한 `applications`와 마지막 성공 조회 기록 | 조회 실패나 오래된 자료를 최신 현황으로 표현하지 않음 |
| 이번 안내의 목적·추천 시점·대상 | 규칙으로 생성한 티켓과 운영자가 선택한 발송 범위 | 필수/자율 안내를 구분하고 대상 ID는 명단과 대조 |
| 이전 안내의 시각·목적·본문·대상 | 저장된 실제 발송 결과와 확인 수준을 표시한 수동 기록 | 최근 안내와 중복·24시간 제한을 확인 |
| 말투·추가 안내 문구 | 운영자가 명시적으로 입력한 작성 지시와 톤 가이드 | 날짜·대상 등 확정된 사실을 덮어쓰지 않음 |

서버는 위 값과 **각 값의 출처·조회 시각**을 초안 생성용 입력 묶음으로 만든다. 템플릿 또는 Gemini가 반환한 문안은 `notice_drafts`에 초안 버전으로 저장하고, 사용한 프로젝트 정보 버전·신청 원본 조회 시각·티켓 ID·생성 방식과 연결한다. 누락되거나 충돌하는 사실은 임의로 채우지 않고 담당자 확인 항목으로 표시한다. 운영자가 본문을 수정하면 새 버전으로 남기고, 본문·대상·방식·채널 또는 기준 데이터가 바뀌면 기존 승인을 무효화한다. 실제 발송 직전에는 신청 상태와 승인 범위를 다시 확인한다.

현재 프로토타입의 초안은 예시 템플릿이며, 아직 Supabase·신청 원본 API·Gemini API에서 데이터를 읽어 생성하지 않는다. 구현 여부는 [SPEC](spec_001.md)과 [PLAN](PLAN.md)에 표시한다.

## 6. 웹사이트 버튼과 저장 작업

| 사용자 또는 시스템 행동 | 기준 데이터의 변화 | 함께 남길 이력 |
| --- | --- | --- |
| 프로젝트 등록·수정 | `projects`, 대상 명단, 확정 필드 출처 저장 | 등록/변경자·시각, 주요 필드 변경 |
| 파일 업로드·텍스트 입력 | 원본 파일은 Storage, 붙여넣은 원문과 양쪽의 입력 메타데이터는 `project_inputs`에 저장 | 입력자·시각, 분석 상태·오류 |
| 신청·취소·확정 | 해당 동료의 최신 `applications` 상태 변경 | 이전/새 상태, 원본 또는 조작 주체, 발생 시각 |
| 원본 조회 | 정규화한 신청 상태 갱신. 실패 시 기존 정상 상태를 0명으로 대체하지 않음 | `source_sync_runs`에 성공/실패·조회 시각·건수 |
| 입력 내용 재분석 | 새 분석 실행과 후보 추가. 확정값을 자동 덮어쓰지 않음 | 실행자·모델/규칙 버전·오류 |
| 티켓 보류·안내하지 않기 | 티켓 상태·재검토 조건 변경 | 사유·담당자·시각 |
| 공지 초안 생성 | 확정 정보·최신 현황·이전 안내를 모아 초안 버전 저장 | 입력 출처·조회 시각, 템플릿/AI 방식, 생성 시각·오류 |
| 초안 수정·대상/방식 변경 | 새 초안 버전 저장, 기존 승인 무효화 | 어떤 값이 바뀌었는지 |
| 승인 | 본문·대상·채널·기준 데이터 버전을 묶어 기록 | 승인자·시각 |
| 알림 발송 | 최신 신청 원본과 승인 범위를 서버에서 재검사한 후 실행 | 시도 ID, 당시 원문·대상, 수신자/채널별 결과·외부 메시지 ID |

웹사이트가 직접 Supabase의 테이블과 Storage를 호출할 수 있는 범위는 로그인과 접근 정책으로 제한한다. 파일·텍스트 분석, 공지 초안의 외부 AI 호출, 승인 검증, 실제 Slack 발송처럼 비밀키와 재검사가 필요한 작업은 서버 함수에 둔다. 사용자의 브라우저에 Supabase secret key, Gemini API 키, Slack 토큰을 넣지 않는다.

API 이름은 구현 시 정한다. 업무 단위로 보면 `파일 업로드/텍스트 저장`, `입력 내용 분석 요청`, `후보 확정`, `신청 상태 변경`, `티켓 판단`, `공지 초안 생성`, `초안 승인`, `발송 실행` 요청이 필요하다. **화면의 버튼 이름이 곧 API나 테이블 이름일 필요는 없다.**

## 7. 일정·현황·발송의 기준 데이터

- 신청률은 프로젝트 대상의 고유 동료 수를 분모로 하고 유효 신청자 수를 분자로 계산한다. 조회 실패·대상 0명은 정상 비율과 구분한다.
- 일정과 티켓은 확정된 마감일·대상·필수 여부·신청 현황·최근 안내에 근거한다. 계산 결과에는 사용한 운영 정보 버전, 신청 원본의 마지막 성공 조회 시각, 원래 점검 시각과 조정된 시각을 연결한다.
- 같은 프로젝트·대상·목적의 최근 안내와 24시간 제한을 보려면 발송 당시의 대상과 목적을 구조화해 보관해야 한다. 발송 건수만으로 재안내 가능 여부를 판단하지 않는다.
- 달력에 표시할 일정을 저장할지 매번 규칙에서 재계산할지는 구현 방식에 따라 정한다. 어느 경우든 홈·티켓·캘린더는 같은 판단 결과를 사용한다.
- 발송 성공, 신청 완료, 행사 운영 종료는 서로 다른 상태다. Slack 응답이 불명확하면 `unknown`으로 남겨 확인 없이 전체 재발송하지 않는다.

## 9. 구현 순서 제안

1. 현재 [PLAN 2단계](PLAN.md)의 현황·일정·티켓 규칙을 로컬 데이터로 완성해 판단 기준을 검증한다.
2. Supabase의 비공개 파일 저장과 텍스트 입력·프로젝트·입력 메타데이터부터 연결한다. 로그인·접근 정책을 함께 적용한다.
3. 입력 분석 함수를 붙여 후보·근거·검토 결과를 저장한다. 붙여넣은 텍스트·TXT/MD → PDF/DOCX → 선택적 AI 순으로 입력 범위를 넓힌다.
4. 신청 원본·상태·조회 이력을 연결하고, 확정 정보와 현황을 이용한 공지 초안 생성·승인·모의 발송 데이터를 검증한다.
5. 실제 Slack 발송과 실행 결과, 서버 주기 작업을 연결한다.

이 순서는 데이터 구조를 이해하고 점진적으로 연결하기 위한 제안이다. 구체적인 작업 우선순위와 완료 표시는 [PLAN](PLAN.md)을 갱신해 관리한다.
