# 데이터 흐름과 저장 구조 초안

작성일: 2026년 10월 5일  
상태: 설계 초안과 현재 구현이 함께 있다. Supabase 인증·초안·안내 파일 저장, 계정별 운영 상태와 버전 이력 저장을 구현했다. 규칙 평가기는 화면 티켓·달력에 연결했고 키 없는 공개 공휴일 달력을 사용한다. `managerkim` Supabase에는 Google Sheets 예시 시트의 서비스 계정 조회·정규화, 수동/매시간 Edge Function 동기화와 실행 이력을 적용했다. 임시 예약 실행의 저장 성공을 확인했다. 운영자 브라우저의 전체 동기화·복원, 실제 조직 원본, 조직 공동 권한, Slack 전송과 원본 기획서 보존은 후속이다.

이 문서는 [PRD](PRD.md)의 제품 흐름을 데이터와 API 관점에서 풀어 쓴다. [SPEC](../spec/spec_001.md)은 **현재 동작**, [PLAN](PLAN.md)은 **구현 순서**, 이 문서는 **앞으로 연결할 데이터의 책임과 관계**를 관리한다. 아래 테이블 이름과 필드는 대체로 논리 모델의 제안이다. 실제 첫 단계 SQL은 [`notice_drafts`, `notice_resources` 마이그레이션](../supabase/migrations/20261006015431_notice_drafts_and_resources.sql)에 따로 있다.

## 0. 현재 구현한 자료 분석 경로 (2026-10-06)

현재 구현은 **브라우저 파일/텍스트 → 인증된 POST /api/documents/analyze → 서버 형식별 추출 → 필요한 PDF 페이지의 Gemini OCR → Gemini 통합 분석 → 원문 근거 검사 → 후보 카드 검토·선택 적용 → 프로젝트 Supabase 저장 → 공지 정보 카드 수정·제외 → Gemini 초안 생성**이다. Gemini는 Gemini API를 통해 호출하며 GEMINI_API_KEY·GEMINI_MODEL은 서버 환경 변수다. 로컬 서버와 Vercel API가 같은 분석 모듈을 사용한다.

원본과 전체 분석 결과를 Supabase에 저장하는 아래 설계는 아직 목표 구조다. 이번 구현에서는 원본·페이지 이미지·전체 텍스트를 요청 메모리에서 처리하고, 적용한 값과 근거·파일 해시·시각·모델을 프로젝트 `sourceReviews`에, 선택하지 않은 충돌·재확인 항목을 `sourceIssues`에 저장한다. 프로젝트는 계정별 `operator_states`에 저장하고 변경 시점의 스냅샷을 `operator_state_revisions`에 남긴다. 업로드 자료는 기존 notice-files/notice_resources 안내 첨부와 별개이며 자동으로 발송용 자료가 되지 않는다.

분석에는 기존 Supabase 인증을 적용한다. 파일 6개·개별 2MB·합계 2.8MB, PDF 파일당 30쪽·OCR 합계 8쪽, 추출 텍스트 8만 자, 요청 JSON 4.1MB로 제한한다. 같은 서버 인스턴스의 사용자별 동시 요청을 차단하고 제공자 오류는 키·원문 없이 사용자용 오류로 반환한다. 원문 인용은 서버의 sourceId/segmentId·문구 일치 검사로 검증하며 OCR은 인식 텍스트 기준임을 표시한다. 후보의 의미 정확성, 적용한 수정값, 원본의 표·이미지 문맥은 운영자가 검토한다.

현재 운영 자료는 프로젝트·신청 상태·신청 변경 이력·티켓·보낸 안내를 하나의 계정별 JSON 상태로 저장한다. 저장할 때 이전 버전과 일치해야 하며 성공한 각 버전은 별도 불변 행으로 남긴다. 아래의 `projects`, `applications`, `tickets` 등 분리 테이블은 조직 공동 작업과 독립 조회를 위한 목표 모델이며 아직 생성하지 않았다. 발송 확인 체크는 서버에 저장하지 않고 새 검토 때 다시 받는다.

아래 1~9절의 DB 입력·후보·원본 보관은 후속 목표이며 현재 완료된 기능으로 해석하지 않는다. 상세 계약은 [SPEC 002 9절](../spec/spec_002.md#9-기획서에서-프로젝트-정보-채우기)을 따른다.

## 1. 전체 흐름과 데이터의 책임

```text
운영자 웹사이트
  ├─ 프로젝트 필드 직접 입력 ───────────────────────────────┐
  ├─ 텍스트 붙여넣기 → Database: 원문 텍스트                  │
  └─ 파일 업로드(TXT/MD/PDF/DOCX 등)                         │
                       ↓                                   │
             Supabase Storage: 원본 파일                    │
                       ↓                                   │
             서버 함수: 형식별 읽기·후보 추출               │
                       ↔ Gemini API: 복잡한 해석(선택)     │
                       ↓                                   │
             Database: 근거가 있는 필드 후보                │
                       ↓                                   │
             운영자 검토·수정·확정 ──────────────────────────┤
                                                           ↓
                           Database: 확정 운영 정보·승인된 참고 내용·입력 출처
                                                           ↓
Google Drive 신청 원본 → 형식별 조회·정규화 → 신청 현황 → 규칙 기반 점검 일정·티켓
                                                           ↓
확정 정보 + 승인된 참고 내용 + 최신 현황 + 이전 안내
                                  → 공지용 정보 후보 → 담당자 확인·제외 → 확정 정보 카드
                                  → 템플릿 또는 AI 모델 → 공지 초안
                                                           ↓
                               담당자 검토·승인 → 발송 시도·결과
                                                           ↓
                                           안내 이력과 다음 현황 재확인
```

사용자는 프로젝트 필드를 직접 입력하거나, 설명·기획 내용을 **텍스트로 붙여넣거나**, TXT·MD·PDF·DOCX 등 파일로 제공할 수 있다. 붙여넣은 원문은 접근 제한이 있는 Database에, 업로드한 원본 파일은 비공개 Supabase Storage에 보관하는 안이다. 파일명·형식·Storage 경로와 입력자·시각은 Database에 기록한다. 모든 입력에서 추출한 값은 우선 후보이며, 운영자가 확정한 정보와 구분한다.

Gemini는 입력 내용을 해석해 후보를 반환하거나, 확정된 정보를 바탕으로 공지 문안을 작성할 수 있지만 Supabase에 직접 기록하지 않는다. 서버 함수가 데이터를 읽고 모델을 호출하며 응답을 검사·저장한다. **일정 판단과 공지의 사실 항목**에는 운영자가 확정한 정보·승인한 참고 내용과 조회 시각을 확인한 신청 현황만 사용한다. AI가 미확정 원문의 날짜·대상을 그대로 사실로 쓰지 않는다.

파일이나 텍스트를 먼저 넣고 나중에 프로젝트 정보를 확정하는 등록 흐름에는 임시 프로젝트 ID와 `draft` 상태를 만든다. 입력 원본과 후보는 그 ID에 연결하고, 운영자가 등록을 완료할 때 프로젝트를 `active`로 바꾼다. 중간에 등록을 그만둔 원본은 별도 정리 기준을 적용한다.

파일 업로드 또는 텍스트 저장 직후 웹사이트가 분석 함수를 호출하는 방식을 우선 검토한다. 원본 저장 성공, 분석 성공, 프로젝트 정보 확정은 각각 다른 단계다. 분석 실패 시에도 원본과 오류 상태를 확인하고 다시 시도할 수 있어야 한다.

## 2. 현재 코드와 전환 목표

| 데이터 | 현재 웹앱 | 연결 후의 기준 위치 |
| --- | --- | --- |
| 프로젝트 운영 정보·대상 ID | `projects` 배열을 계정별 `operator_states`에 저장, 브라우저는 캐시 | 조직 공동 사용을 위한 `projects`, `project_targets` |
| 신청·취소·확정 | 로컬 변경 또는 Google Sheets 가져오기로 갱신한 `applications`, `applicationEvents`를 계정별 `operator_states`에 저장. 예시 시트의 최신 스냅샷·불변 사건·실행 이력은 별도 Supabase 테이블에 시간별 저장 | 실제 조직 원본과 공동 사용을 지원하는 동기화 기록 |
| 텍스트 붙여넣기와 파일 입력 후보 | PDF·DOCX·TXT·MD와 붙여넣은 글을 서버에서 Gemini로 분석. 미적용 후보는 화면 메모리에만, 적용값·근거는 프로젝트의 계정별 상태에 보관 | 원본 보존 정책을 갖춘 `project_inputs`, `input_analyses`, `field_candidates` |
| PDF·DOCX 등 파일 원본 | 요청 중 분석만 지원, 원본 보관 없음 | 비공개 Storage 버킷과 `project_inputs`의 파일 메타데이터 |
| 티켓·캘린더 | 예시 티켓과 수동 Sheets 조회 또는 직접 입력으로 갱신한 규칙 티켓을 화면에 표시. 예시 시트의 서버 정기 실행은 `automation_tickets`도 갱신 | 조직 공동 티켓과 점검 일정 |
| 초안·승인 | 수정 가능한 공지 카드와 Gemini 초안을 `notice_drafts`에 저장. 확인 체크는 저장·복원하지 않음 | 확정 정보·최신 현황·이전 안내를 반영한 초안 버전과 입력 근거. 실제 실행에 사용한 승인 사건만 감사 이력으로 기록 |
| 안내 기록·모의 발송 | `records`, `completed`와 선택 자료를 계정별 `operator_states`에 저장 | 실제 발송 시도·대상별 결과·원문·외부 링크, 수동 기록 분리 |
| 실제 Slack·서버 주기 실행 | Slack 미지원. 예시 시트의 시간별 조회·티켓 평가와 `sheet_sync_runs` 실행 이력 활성화 | 서버 측 발송·결과 이력과 장애 복구 |

지금의 [계산 코드](../web/data.js)는 프로젝트별 대상 명단과 신청 상태를 받아 신청률과 미신청 명단을 계산한다. 저장 위치를 옮기더라도 **원본 읽기 → 공통 신청 형식 → 현황 계산**의 경계를 유지한다. 브라우저 저장 자료를 Supabase로 자동 이전할지, 예시 자료를 새로 시작할지는 별도로 결정한다.

## 3. 최소 데이터 묶음

아래 묶음은 개념적 구조다. 모든 항목을 한 번에 구현하지 않고 연결하는 기능에 맞춰 추가한다. 각 행은 안정적인 ID와 생성·수정 시각을 갖고, 연결 관계에는 해당 프로젝트 ID를 사용한다.

| 묶음 | 제안 테이블 | 최소로 구분할 정보 |
| --- | --- | --- |
| 운영 기준 | `projects` | 이름·설명·신청 시작/마감·행사/운영 일정·신청 링크·담당자·확정 방식·운영 상태·목표 신청률·시간대. 미정 값은 `NULL`로 두고 확정 여부를 구분 |

| 업무 변경 이력 | `activity_events` | 행위자·시각·프로젝트·행동 유형·대상 ID·이전/이후 상태의 필요한 부분. 민감한 본문·파일 전체를 무조건 복제하지 않음 |

### 현재 상태와 이력을 함께 남기는 이유

- 원본의 이력 행은 `application_events`에 사건 ID 기준으로 한 번만 반영한다. 그 사건들에서 계산한 `applications`의 최신 상태가 `cancelled`이면 현황 계산에서는 미신청자로 돌아간다. 신청→취소→재신청 순서와 각 발생 시각은 이력에 남는다.
- `projects.deadline`의 현재 값이 바뀌어도, 과거 티켓·승인·발송이 어떤 마감일을 기준으로 만들어졌는지 추적할 수 있어야 한다.
- `send_attempts`에는 버튼 클릭이나 API 요청 **시도**를, `send_results`에는 실제 전송 결과를 기록한다. 시도만으로 성공 처리하지 않는다.
- Supabase의 기술 로그와 `activity_events` 같은 **제품 업무 이력**은 목적이 다르다. 취소·승인·보류의 의미를 나중에 확인하려면 앱이 업무 이력을 직접 기록해야 한다.
- 초안과 자료 선택은 저장·복원하지만 화면의 발송 확인 체크는 저장하지 않는다. `notice_approvals`는 실제 실행 요청의 감사용 승인 사건이며, 이전 화면의 체크를 다시 활성화하는 근거로 사용하지 않는다.

## 4. 파일·텍스트 분석에서 확정까지

1. **원본 저장:** 로그인한 운영자가 텍스트를 붙여넣거나 파일을 선택한다. 붙여넣은 글은 `project_inputs`에 원문으로 저장한다. 파일은 비공개 버킷에 저장하고 `project_inputs`에 경로와 상태를 기록한다. 길이·파일 형식·크기·접근 권한을 검사한다.
2. **분석 요청:** 웹사이트가 입력 ID를 서버 함수에 보낸다. 함수는 프로젝트 접근 권한을 확인하고 텍스트 원문 또는 Storage의 파일을 읽는다. Supabase의 비공개 경로 문자열만 Gemini에 전달해서 읽게 하지 않는다.
3. **내용 해석:** 명시적 항목은 규칙으로 찾고, 복잡한 문장은 선택한 AI 서비스에 필요한 내용만 전달한다. TXT/MD와 붙여넣은 글은 텍스트로 처리한다. PDF는 문서 처리 방식으로 보낼 수 있다. DOCX는 우선 텍스트/표 추출 또는 PDF 변환 방식을 정한다. 스캔본과 표의 품질은 별도로 검증한다.
4. **구조화와 검증:** 모델에는 필요한 필드, 값이 없을 때 `null`, 근거 원문과 위치를 요구한다. 서버는 응답 형식·날짜·URL·값의 범위를 검사한다. JSON 형식이 맞아도 사실이 맞는 것은 아니다. 후보와 분석 실행 ID를 저장하고 상태를 `review_required`로 바꾼다.
5. **운영자 확정:** 각 후보를 적용·수정·제외한다. 입력 원본끼리 또는 기존 직접 입력과 값이 다르면 차이를 보여준다. 고정 필드에 담기 어려운 상세 안내 내용도 공지에 사용할 부분을 선택·수정해 승인할 수 있다. 확정값·승인된 참고 내용과 출처·시각을 저장하고, 이를 기준으로 초안과 점검 일정을 다시 계산한다.

예시 후보 응답의 형태:

```json
{
  "field": "deadline_at",
  "candidate_value": "2026-10-20T18:00:00+09:00",
  "evidence_text": "참가 신청은 10월 20일 오후 6시에 마감합니다.",
  "source_location": "2쪽, 신청 방법",
  "extraction_method": "ai",
  "review_status": "pending"
}
```

이 예시는 계약 형식의 초안이다. 붙여넣은 글이라면 `source_location`은 줄 번호 등으로 표시할 수 있다. 모델이 근거 위치를 정확히 찾지 못하면 위치를 추측해 채우지 않고 확인 필요로 둔다. 원본은 Supabase에 보관하며, 분석을 위해 Gemini에 전달한 내용은 별도 서비스에서 처리된다. 어떤 입력을 외부 AI에 보낼 수 있는지와 보존 정책은 연동 전에 결정한다.

## 5. 공지 초안 작성에 사용하는 데이터와 API

초안 생성은 파일 분석과 **별도 요청**이다. 현재 화면은 프로젝트 값과 적용한 문서 근거·충돌 상태로 공지용 정보 카드를 만들고 담당자가 항목을 수정·확인·제외한 뒤 Gemini에 보낸다. 생성 API는 항목별 확인 상태를 검사하고 확인된 포함 값만 모델에 전달한다. 원문 근거는 화면에 표시하고 초안 저장 데이터에 남지만 모델 생성 입력에는 넣지 않는다. 최신 신청 현황과 이전 안내 원문도 생성 입력에 자동 연결하지 않는다. 생성된 본문은 날짜·링크·수치 대조와 별도 Gemini 주장 검사를 거쳐 운영자가 비교·채택한다. 아래 입력 표와 카드 버전 연결은 목표 구조이며 실제 Slack API는 아직 사용하지 않는다.

| 초안 입력 | 출처 | 사용할 때의 확인 |
| --- | --- | --- |
| 프로젝트명·설명·대상·필수 여부·일정·신청 링크·담당자 | 운영자가 직접 입력하거나 파일/텍스트 후보에서 **확정한** `projects` 정보 | 미확정 후보를 사실로 사용하지 않음. 변경된 날짜와 링크를 확인 |
| 행사 상세 내용·준비물·문의 방법 등 | 운영자가 직접 작성하거나 파일/텍스트에서 골라 승인한 `approved_source_notes` | 원문 근거와 승인 범위를 확인. 미검토 원문 전체를 그대로 초안의 사실로 쓰지 않음 |
| 신청·취소·확정, 미신청 대상과 신청률 | 정규화한 `applications`와 마지막 성공 조회 기록 | 조회 실패나 오래된 자료를 최신 현황으로 표현하지 않음 |
| 이번 안내의 목적·추천 시점·대상 | 규칙으로 생성한 티켓과 운영자가 선택한 발송 범위 | 필수/자율 안내를 구분하고 대상 ID는 명단과 대조 |
| 이전 안내의 시각·목적·본문·대상 | 저장된 실제 발송 결과와 확인 수준을 표시한 수동 기록 | 최근 안내와 동일 사유의 티켓·실행 중복을 확인. 고정된 재안내 시간 제한은 적용하지 않음 |
| 말투·추가 안내 문구 | 운영자가 명시적으로 입력한 작성 지시와 톤 가이드 | 날짜·대상 등 확정된 사실을 덮어쓰지 않음 |

목표 구조에서는 서버가 카드 버전과 항목별 **출처·조회 시각·포함 여부**를 초안 입력으로 만들고, 사용한 카드·프로젝트 정보 버전·신청 원본 조회 시각·티켓 ID·생성 방식을 초안과 연결한다. 현재는 카드 값과 포함 여부를 초안에 저장한다. Sheets 기반 프로젝트의 모의 발송 직전에는 서버에서 시트를 새로 읽고 승인 당시 신청 상태·대상 명단과 화면에서 비교하지만, 실제 Slack 전송과 동일한 서버 처리 안에서의 승인·원본 검증은 후속이다. 본문·대상·자료·방식·채널이 바뀌면 화면의 발송 확인 체크를 해제하며, 화면을 다시 열 때는 내용만 복원한다.

현재 웹앱은 카드 기반 Gemini 초안 생성과 Supabase 초안 저장·복원을 구현했다. Google Sheets 수동 가져오기는 신청 상태를 갱신하지만 생성 API가 조회 시점의 현황을 별도 재조회하지는 않는다. SQL 마이그레이션과 실제 계정의 초안 저장·복원을 확인했다. 안내 파일 저장과 화면 전체 흐름은 별도 검증 대상이다. 구현 여부는 [SPEC](../spec/spec_001.md)과 [PLAN](PLAN.md)에 표시한다.

## 6. 웹사이트 버튼과 저장 작업

| 사용자 또는 시스템 행동 | 기준 데이터의 변화 | 함께 남길 이력 |
| --- | --- | --- |
| 프로젝트 등록·수정 | `projects`, 대상 명단, 확정 필드 출처 저장 | 등록/변경자·시각, 주요 필드 변경 |
| 파일 업로드·텍스트 입력 | 원본 파일은 Storage, 붙여넣은 원문과 양쪽의 입력 메타데이터는 `project_inputs`에 저장 | 입력자·시각, 분석 상태·오류 |
| 신청·취소·확정 | 해당 동료의 최신 `applications` 상태 변경 | 이전/새 상태, 원본 또는 조작 주체, 발생 시각 |
| 원본 조회 | 정규화한 신청 상태 갱신. 실패 시 기존 정상 상태를 0명으로 대체하지 않음 | `source_sync_runs`에 성공/실패·조회 시각·건수 |
| 입력 내용 재분석 | 새 분석 실행과 후보 추가. 확정값을 자동 덮어쓰지 않음 | 실행자·모델/규칙 버전·오류 |
| 티켓 보류·안내하지 않기 | 티켓 상태·재검토 조건 변경 | 사유·담당자·시각 |
| 공지 초안 생성 | 확정 정보·최신 현황·이전 안내를 모아 초안 버전 저장 | 입력 출처·조회 시각, 템플릿/AI 방식, 생성 시각·오류 |
| 초안 수정·대상/방식 변경 | 새 초안 버전 저장, 기존 승인 무효화 | 어떤 값이 바뀌었는지 |
| 발송 직전 확인 | 화면에서 본문·대상·자료·채널을 확인. 체크는 다음 화면 열기 때 복원하지 않음 | 실제 실행 요청에 사용된 확인자·시각·검토한 버전만 감사 사건으로 기록 |
| 알림 발송 | 최신 신청 원본과 승인 범위를 서버에서 재검사한 후 실행 | 시도 ID, 당시 원문·대상, 수신자/채널별 결과·외부 메시지 ID |

웹사이트가 직접 Supabase의 테이블과 Storage를 호출할 수 있는 범위는 로그인과 접근 정책으로 제한한다. 파일·텍스트 분석, 공지 초안의 외부 AI 호출, 승인 검증, 실제 Slack 발송처럼 비밀키와 재검사가 필요한 작업은 서버 함수에 둔다. 사용자의 브라우저에 Supabase secret key, Gemini API 키, Slack 토큰을 넣지 않는다.

API 이름은 구현 시 정한다. 업무 단위로 보면 `파일 업로드/텍스트 저장`, `입력 내용 분석 요청`, `후보 확정`, `신청 상태 변경`, `티켓 판단`, `공지 초안 생성`, `초안 승인`, `발송 실행` 요청이 필요하다. **화면의 버튼 이름이 곧 API나 테이블 이름일 필요는 없다.**

## 7. 일정·현황·발송의 기준 데이터

- 프로젝트 전체 신청률은 전체 고유 대상 중 유효 신청자 비율로 계산한다. **자율 목표 신청률은 자율 대상만** 분모에 두고 그중 유효 신청자만 분자에 둔다. 필수 대상은 자율 목표에서 제외한다. 조회 실패·대상 0명은 정상 비율과 구분한다.
- 일정과 티켓은 확정된 마감일·대상·필수 여부·신청 현황·최근 안내에 근거한다. 계산 결과에는 사용한 운영 정보 버전, 신청 원본의 마지막 성공 조회 시각, 원래 점검 시각과 조정된 시각을 연결한다.
- 최근 안내의 시각·대상·목적은 구조화해 보관하고 담당자에게 보여준다. 고정된 재안내 시간 제한은 없다. 티켓 계산의 동일 사유 중복과 단일 발송 요청의 중복 실행은 별도로 차단한다.
- 달력에 표시할 일정을 저장할지 매번 규칙에서 재계산할지는 구현 방식에 따라 정한다. 어느 경우든 홈·티켓·캘린더는 같은 판단 결과를 사용한다.
- 발송 성공, 신청 완료, 행사 운영 종료는 서로 다른 상태다. Slack 응답이 불명확하면 `unknown`으로 남겨 확인 없이 전체 재발송하지 않는다.

### Google Drive 신청 원본 동기화

현재 서버는 환경 변수의 스프레드시트 ID와 읽기 전용 서비스 계정으로 네 탭을 한 번에 읽는다. `managerkim` Supabase의 Edge Function은 매시간 같은 예시 시트를 읽어 `sheet_sync_snapshots`, `sheet_application_events`, `automation_tickets`, `sheet_sync_runs`에 반영한다. 임시 예약 실행은 성공했고 첫 매시간 정시 실행과 브라우저 반영·복원은 미확인이다. 새 프로젝트 등록 화면에는 시트의 `projectId`와 맞출 입력란이 있지만, 운영자가 스프레드시트 ID나 범위를 화면에서 등록하는 기능은 없다. 다음은 실제 조직 원본까지 확장할 때의 동기화 계약이다.

1. 운영자가 사용할 원본 시트와 접근 범위를 확정한다. 서버는 Sheets API로 지정한 셀 값을 읽는다. 실제 조직 자료를 적용할 때는 서비스 계정의 공유 범위와 열 구조를 검증한다.
2. 원본은 우선 **읽기 전용**으로 연결한다. 대상 명단, 최신 상태, 신청·취소 이력 행의 열 의미를 확인한다. 각 이력 행은 안정적인 사건 ID, 프로젝트 ID, 변하지 않는 동료 ID, 상태(`applied`/`confirmed`/`cancelled`), 발생 시각을 가져야 한다. 이름이나 시트의 행 번호를 영구 ID로 사용하지 않는다. 원본이 현재 상태도 별도로 제공하면 이력에서 계산한 결과와 대조한다.
3. 서버 동기화는 원본 이력을 공통 사건 형식으로 검증·변환하고 사건 ID로 중복 반영을 막은 뒤, 프로젝트·동료별 시각 순서로 최신 상태를 계산한다. 같은 시각의 상충 사건, 알 수 없는 ID·상태, 취소 후 재신청과 현재 상태 불일치를 검사한다. `source_sync_runs`에는 성공/실패·파일 버전·조회 시각·건수를 남긴다. 실패하면 이전 정상 현황과 마지막 성공 시각을 유지하고 최신 현황인 것처럼 발송하지 않는다.
4. 성공한 읽기 결과로 변경 이력과 신청 현황을 갱신한다. 발송 직전에는 다시 최신 원본을 확인하고 대상이 달라지면 화면의 발송 확인을 요구한다. 원본을 수정하는 기능은 별도 권한·충돌·감사 설계가 끝날 때까지 만들지 않는다.

두 워크트리 사이의 계약은 원본 열 이름과 분리한다. Drive 연결 코드는 `projectId`, `employeeId`, `required`가 있는 대상 목록과 `sourceEventId`, `projectId`, `employeeId`, `status`, `occurredAt`이 있는 사건 목록, 마지막 성공 조회 시각 또는 오류를 반환한다. 판단 엔진은 이 공통 형식만 사용한다. 사건 ID가 원본에 없다면 연동 전에 변하지 않는 대체 식별 방법을 정해야 한다.

### 안내 자료의 민감 정보 검사

파일 업로드와 본문 수정 시 서버가 고정된 버전의 텍스트를 추출한다. PDF·문서·이미지의 추출/OCR 결과에 식별 번호·연락처·계좌 등 패턴 검사와 건강검진 결과 같은 문맥 검사를 적용한다. 탐지 위치·유형과 검토 상태를 보여주되 검사 로그와 오류에 개인값 전문을 남기지 않는다. 읽기 실패, 검사 실패, 검토되지 않은 탐지 항목이 있으면 발송을 보류한다. 운영자는 자료를 수정·삭제하고 재검사하거나 조직 정책에 따른 예외 사유를 기록한다. 검사 완료는 무해성 보증이 아니므로 최종 본문·첨부·채널 공개 범위는 담당자가 확인한다. 외부 AI에 원문을 전달하는 검사는 별도의 허용 범위가 정해진 후에만 사용한다.

## 9. 다음 연결 순서

1. 로그인 화면에서 실제 Sheets 가져오기 → 현황·규칙 티켓 갱신 → Supabase 저장·복원까지 검증한다. 공휴일 조정과 신청 변경에 따른 티켓 갱신도 함께 확인한다.
2. 공지 정보 카드에 현재 신청 원본의 확인 시각을 연결하고, 자료에서 나눈 행동·비용·예외와 초안 품질을 실제 사례로 평가한다. 카드의 문서 근거·충돌 상태 표시는 기본 구현했다.
3. 발송용 본문·파일의 민감 정보 검사와 실제 대상·채널 권한 확인을 연결한다. Slack 전송 시에는 현재 모의 발송의 원본 대조를 서버의 전송 처리 안으로 옮겨 승인 유효성과 함께 재검증한다.
4. 실제 Slack 발송과 목적지별 결과·링크·재시도 이력을 저장한다.
5. 서버 주기 조회·실행 이력과 조직 공동 권한·자료 보존 정책을 연결한다.

구체적인 완료 기준과 진행 상태는 [PLAN](PLAN.md)에서 관리한다.
