# 총무 행사·복리후생 안내 운영 도구 발표 자료

작성 기준일: 2026년 10월 7일 · 당시 로컬 브랜치: `codex/spec003-integration-ux`

이 문서는 작성 당시의 발표 자료입니다. 최신 구현·검증 상태는 [PLAN](../PLAN.md)과 [SPEC 001](../../spec/spec_001.md)을 확인하세요.
발표할 때의 상태 표현: **웹 프로토타입과 모의 발송까지 구현 중. 실제 Slack 발송은 아직 없음.**

## 1. 한 문장 소개

행사와 복리후생을 운영할 때 흩어지는 **운영 정보, 신청 현황, 안내 일정, 공지 초안과 기록**을 한 화면에서 확인하고, 담당자가 다음 안내를 준비하도록 돕는 웹사이트입니다.

> 발표 멘트: “공지 문구를 쓰는 것만이 일이 아니었습니다. 누가 신청해야 하는지, 아직 신청하지 않은 사람이 누구인지, 지금 다시 안내해야 하는지를 계속 대조하는 일이 반복됐습니다.”

## 2. 문제 정의: 왜 만들었나

HR·총무 경험을 돌아보며, 자택 간식박스, 포인트 쿠폰, 서비스 이용 후기 이벤트처럼 운영 방식은 달라도 비슷한 일이 반복된다는 점에서 출발했습니다.

1. 행사별 일정·대상·신청 방법을 확인하고 공지를 작성합니다.
2. 신청해야 할 사람과 실제 신청자를 비교해 신청률·미신청자를 확인합니다.
3. 안내가 더 필요한지 판단하고, 전체 또는 일부 대상에게 리마인드를 준비합니다.
4. 마감 뒤 명단을 확정하는 다음 업무로 이어집니다.

현재 제품 범위는 **운영 정보 등록부터 안내 검토·모의 발송 기록까지**입니다. 마감 후 명단 확정과 실제 전달까지 모두 자동화했다고 설명하지 않습니다. 실제 시간 절약 효과도 아직 측정하지 않았습니다.

> 발표 멘트: “총무 업무 전체를 만들기보다, 신청 기간에 반복해서 현황을 대조하고 안내를 준비하는 구간부터 풀기로 했습니다.”

## 3. 무엇을 만들었나: 화면과 업무 흐름

| 단계 | 현재 구현한 내용 | 발표에서 구분할 점 |
| --- | --- | --- |
| ① 프로젝트 등록과 티켓 | 행사 이름, 기간·마감, 대상·필수 여부, 신청 링크, 첫 안내 시각 등을 등록하고 확인할 일을 홈·프로젝트·캘린더에 표시 | 초기 프로젝트·동료·과거 티켓 일부는 가상 사례. 새 프로젝트의 전체 브라우저 흐름은 아직 미검증 |
| ② 프로젝트 정보 요약 | 문서에서 일정·대상·방법 등의 후보와 근거를 뽑고, 운영자가 선택한 정보로 요약·공지 정보 카드를 구성 | AI 후보를 사람이 확인해야 하며, 분석용 원본 문서는 현재 서버·DB에 영구 보관하지 않음 |
| ③ 신청 현황 가져오기 | Google Sheets의 직원명부·프로젝트·대상·신청이력 네 탭을 읽어 신청·취소·확정 상태와 신청률을 계산 | 예시 시트의 서버 조회는 확인. 배포 함수의 CORS 문제로 브라우저 수동 가져오기 전체 흐름은 미완료 |
| ④ 안내 필요 판단 | 필수 미신청자와 자율 대상 신청률, 마감까지 남은 시간, 공휴일·업무시간을 규칙으로 평가해 티켓 제안 | 판단을 보여주는 기능이며 자동 발송 기능은 아님 |
| ⑤ 공지 초안 준비 | 확인한 정보 카드, 안내 목적, 말투를 입력으로 Gemini 문구를 생성하고 담당자가 수정 | 실제 Gemini 결과가 브라우저 본문 칸에 들어오는 일부 흐름은 확인. 모든 실제 문서의 품질을 검증한 것은 아님 |
| ⑥ 최종 확인과 기록 | 본문·대상·자료를 검토하고, Sheets 기반 모의 발송 직전에 원본 변경을 다시 확인해 모의 기록 저장 | **Slack으로 실제 전송하지 않음.** 모의 기록을 발송 성공으로 표현하지 않음 |

목표 흐름은 **운영 정보 등록 → 신청 현황 확인 → 안내 필요 판단 → 초안·대상 검토 → 승인 후 실제 발송 → 결과 저장·재확인**입니다. 현재 마지막 두 단계의 실제 Slack 실행·결과 확인은 개발 전입니다.

> 시연 순서 제안: 홈에서 프로젝트 선택 → 티켓의 ‘보낼 내용 확인’ → 정보·본문·대상·자료 검토 → 모의 발송 결과와 기록 확인. 시연 전에는 실제 계정에서 이 순서를 한 번 이어서 확인해야 합니다.

## 4. 폴더 구조와 데이터 흐름

| 위치 | 맡은 일 |
| --- | --- |
| `prototype/` | 사용자가 보는 웹 화면, 신청률 계산, 규칙 티켓, 초안·대상 선택, 모의 발송 |
| `scripts/`와 `api/` | 로컬·Vercel API, 문서 분석, Gemini 호출, Sheets 읽기와 데이터 변환 |
| `supabase/migrations/` | 로그인 계정별 저장, 초안·자료, 시트 동기화, 티켓·실행 이력의 DB 변경 파일 |
| `supabase/functions/` | 화면이 닫혀도 시트를 읽고 티켓을 평가하는 Edge Function |
| `tests/` | 가상 직원·문서·신청 사례와 자동 테스트 |
| `docs/`, `spec/` | 제품 목표·계획·데이터 설계와 현재 동작·남은 요구사항 |
| `outputs/` | 예시 Sheets 설명·미리보기 산출물. 운영 데이터는 아님 |

현재 구현된 주요 데이터 이동은 다음과 같습니다.

```text
Google Sheets 네 탭 ──읽기 전용 조회──> Supabase Edge Function
           │                                ├─ 최신 스냅샷·신청 사건·실행 이력 저장
           │                                └─ 규칙으로 확인 티켓 평가
           └─ 수동 조회/모의 발송 전 재조회 ──> 웹 화면의 현황·대상 확인

운영자 입력·확정한 정보 ──> 계정별 Supabase 운영 상태·초안 저장
자료 파일/텍스트 ──> 서버 추출·Gemini 분석 ──> 운영자 후보 검토
확정 정보 카드 ──> 서버 Gemini 초안 생성 ──> 운영자 수정·모의 발송 기록
```

**서버와 DB가 계속 데이터를 주고받는 이유:** 프로젝트를 수정하거나 신청 이력이 새로 들어오면 현황과 티켓도 달라집니다. 초안과 안내 기록은 새로고침 후 복원해야 하고, 화면을 닫은 동안에는 예약 작업이 시트를 다시 읽어야 합니다. 현재 프로젝트·신청·티켓·모의 기록의 상당 부분은 계정별 `operator_states` JSON 상태에 묶어 저장합니다. 조직 전체가 함께 쓰는 분리 테이블 구조는 아직 목표 설계입니다.

**연결한 기술의 역할:** Supabase는 로그인·상태·초안·자료 메타데이터·정기 실행 저장에, Vercel은 웹 화면과 서버 API 제공에, Google Sheets는 신청 원본에, Gemini API는 문서 해석과 공지 문구 생성에 사용합니다. Gemini의 **유료 요금제·과금 상태와 정확한 운영 모델명은 이 폴더만으로 확인하지 않았습니다.** 모델은 서버 설정 `GEMINI_MODEL`로 지정합니다. Slack API 연결은 아직 없습니다.

## 5. 구현 상태를 정확히 나누기

### 구현 완료로 말할 수 있는 것: 코드와 로컬 검증 기준

- 프로젝트 등록·수정, 요약 카드, 첫 안내·리마인드 티켓, 신청률·미신청자 계산, 홈·캘린더 표시 코드가 있습니다.
- PDF·DOCX·TXT·MD 자료 분석, 확인한 정보에 기반한 Gemini 공지 초안, 편집·대상 선택·자료 선택·모의 발송 기록 코드가 있습니다.
- 로그인 계정별 Supabase 운영 상태·초안 저장, Sheets 네 탭 조회·정규화, 예시 시트의 예약 동기화 코드가 있습니다.
- 2026년 10월 7일 현재 이 폴더에서 `npm test` **106개 통과**를 다시 확인했습니다.
- 앞선 작업 기록상 예시 Sheets의 직원 160명·신청 사건 17건 조회, Supabase 함수 직접 호출과 임시 예약 실행의 저장 성공, 브라우저의 일부 초안·Gemini 흐름이 확인됐습니다. 이번 문서 작업에서 외부 서비스에 재접속한 결과는 아닙니다.

### 기존 상태로 남은 것: 아직 바뀌지 않은 사용 범위

- 시작 화면의 일부 직원·프로젝트·과거 안내는 가상 데이터입니다. 실제 사내 명부·Slack 사용자·채널로 전환하지 않았습니다.
- Slack 채널 목록·구성원 수는 예시이며, 공개 범위나 게시 권한을 실제로 확인하지 않습니다.
- 사용자별 저장 구조이며 조직의 여러 운영자가 공동으로 관리하는 권한 모델은 없습니다.
- 안내 자료를 분석하는 파일과 실제 발송에 붙일 파일은 구분합니다. 분석 원본의 장기 보관 정책은 아직 구현하지 않았습니다.
- `README.md`는 이번 작업에서 수정하지 않습니다. 폴더 소개 일부는 최근 추가 파일까지 반영하지 않아, 발표 때는 이 문서의 폴더 표를 기준으로 설명합니다.

### 수정·검증이 필요한 것: 이미 만든 경로의 미완료 부분

1. **브라우저 Sheets 가져오기:** 로컬 CORS 수정 코드는 있으나 배포 함수에는 반영되지 않았습니다. 반영 후 로그인 → 가져오기 → 화면 갱신 → Supabase 저장 → 새로고침 복원을 실제 계정으로 확인해야 합니다.
2. **새 DB 변경 반영:** 최근 공지 자료 버전과 신규 프로젝트 예약 평가용 마이그레이션은 로컬 파일에 있고 원격 적용·검증은 기록되지 않았습니다.
3. **등록부터 기록까지의 사용자 흐름:** 새 프로젝트, 티켓, Gemini 초안, 대상·자료, 모의 발송, 기록 조회를 한 번에 브라우저에서 확인해야 합니다. 파일 업로드·다른 기기 복원도 남았습니다.
4. **예약 작업:** 임시 예약 실행은 확인했지만 첫 매시간 정시 실행, 신규 프로젝트 반영, 장애 후 복구와 화면 재접속 결과는 미확인입니다.
5. **문서 상태표:** `docs/PLAN.md`의 SPEC 003 체크박스와 `spec/spec_003.md`의 ‘구현 목표’ 표기는 이미 통합된 로컬 코드보다 이전 단계에 머물러 있습니다. 브라우저·원격 검증 범위를 확인한 뒤 상태를 갱신해야 합니다.

### 더 개발해야 할 것: 목표 흐름의 마지막 단계

1. 실제 Slack 계정·수신자·채널·게시 권한 연결과 테스트 대상에서의 실제 수신 확인.
2. 발송 요청을 서버에서 승인·기록하고, **같은 서버 처리 안에서** Sheets 원본·대상·본문·자료를 다시 확인한 뒤 전송.
3. 중복 발송 방지, 수신자별 성공·부분 실패·결과 불명 처리와 안전한 재시도.
4. 최종 본문·발송 파일의 검사, 실제 발송 원문·대상·결과의 변경 불가 이력.
5. 실제 조직 자료를 사용할 때 필요한 접근 권한·보존 정책, 여러 운영자의 공동 사용, 다양한 실제 문서에 대한 AI 품질 평가.

> 발표 멘트: “현재는 안내할 시점을 제안하고 사람이 검토한 내용을 **모의로 기록**하는 단계입니다. 실제 직원에게 Slack 메시지를 보내려면 계정 연결뿐 아니라 발송 직전 최신 명단 확인과 실패·중복 처리까지 완성해야 합니다.”

## 6. 시행착오와 설계 판단

| 고민 | 선택한 방식과 이유 |
| --- | --- |
| AI 에이전트나 Codex 안의 workflow 대신 웹사이트를 만든 이유 | 여러 프로젝트의 일정·신청 현황·이전 안내를 담당자가 반복해서 열어 보고 수정해야 하므로, 계속 접근할 수 있는 화면과 저장·복원 흐름이 필요했습니다. 티켓은 판단을 돕고, 실제 메시지는 사람이 확인하는 구조로 잡았습니다. |
| 무엇을 AI에 맡길까? | 자료에서 운영 정보 **후보**를 찾고 확인된 정보로 공지 문구를 쓰는 일은 Gemini에 맡겼습니다. 후보의 사실 여부와 최종 발송은 사람이 확인합니다. |
| 무엇을 코드 규칙으로 처리할까? | 신청률·필수 미신청자, D-3·D-1·마감 전 점검, 업무시간·공휴일 조정처럼 재현 가능해야 하는 판단은 코드로 계산합니다. 같은 입력이면 같은 결과를 내고 근거를 설명할 수 있기 때문입니다. |
| 외부 API와 모델을 어떻게 다룰까? | Gemini는 서버에서만 호출하고 키는 환경 변수에 둡니다. 입력 크기와 응답을 검사하고 모델 결과가 근거 없는 날짜·링크를 확정하지 못하게 합니다. 모델 이름을 코드에 고정하지 않고 설정으로 바꿀 수 있게 했습니다. |
| 데이터를 왜 나눠 생각했을까? | Sheets의 신청 이력은 원본, Supabase는 운영자 상태·초안·동기화 결과의 저장소입니다. 과거 사건과 현재 상태, 초안 확인과 실제 발송 결과를 섞으면 잘못된 안내나 중복 발송을 추적하기 어렵습니다. |
| 구현 중 확인된 문제 | 화면의 Sheets 수동 가져오기는 배포 함수의 CORS 오류를 확인했고 로컬에서 수정했습니다. 서버 호출 성공만으로 브라우저 사용 가능을 주장하지 않도록 검증 범위를 나눴습니다. |

## 7. 마무리: 지금의 성과와 다음 순서

**지금의 성과:** 흩어진 운영 정보와 신청 이력을 한 흐름으로 연결하고, 안내 시점은 규칙으로, 문서 해석·문구 초안은 AI로, 최종 확인은 담당자가 하는 구조를 구현했습니다. 자동 테스트는 106개가 통과했습니다.

**가장 가까운 다음 순서:** 배포된 Sheets 가져오기 오류와 DB 변경을 반영한 뒤, 실제 운영자 계정에서 **새 프로젝트 등록 → 신청 현황 확인 → 초안·대상 검토 → 모의 발송 → 기록·새로고침 복원**을 이어서 검증합니다. 그 결과를 확인한 후 실제 Slack 발송을 별도 단계로 개발합니다.

**발표 시 피할 표현:** “Slack 발송 완료”, “실제 회사에 바로 사용 가능”, “모든 API 연동 검증 완료”, “AI가 리마인드 시점을 결정한다”, “유료 Gemini 모델을 확인했다”.
