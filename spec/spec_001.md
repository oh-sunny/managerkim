# spec_001 현재 프로토타입 기능 명세

작성일: 2026년 10월 3일  
수정일: 2026년 10월 5일  
대상: 팀 행사·복지 운영 웹앱의 현재 구현

이 문서는 **현재 구현된 기능과 이를 완성하기 위해 남은 일**을 정리합니다. [PRD](../docs/PRD.md)의 제품 중심은 신청 현황·일정·이전 안내를 연결한 안내 운영입니다. 아래 1~12절은 현재 코드의 동작이며, 13절은 F01~F09의 구현 차이를 정리합니다. 제품 정책은 [PRD](../docs/PRD.md), 구현 순서와 진행 상태는 [PLAN](../docs/PLAN.md)에서 관리합니다. 범용 업무 관리로의 확장을 전제하지 않습니다.

현재는 예시 동료 160명을 대상으로 행사·복지 운영 정보를 직접 등록하고 신청·취소·확정 상태를 로컬에서 바꿀 수 있습니다. 프로젝트별 현황과 DM 대상은 같은 신청 기록에서 계산합니다. 티켓과 캘린더의 안내 판단은 아직 예시입니다. 자료 입력의 Gemma 분석과 Supabase 초안 저장은 연결했으며, 안내 시점의 AI 판단과 실제 Slack 전송은 연결하지 않았습니다.

**현재 티켓 완료는 모의 안내 발송 완료입니다. 동료의 신청 완료나 행사·복지 운영 종료를 뜻하지 않습니다.** ‘프로젝트·티켓’은 현재 코드와 화면의 명칭입니다.

## 1 화면 구성과 기본 데이터

주 메뉴는 **홈 / 프로젝트 / 보낸 안내**입니다. 프로젝트 안에는 **전체 티켓 / 보낸 안내** 탭을 두고, 확인 대기 티켓에서 **보낼 내용 확인** 화면으로 이동합니다. 안내 원문과 Slack 링크는 별도의 기록 창에서 확인합니다.

데스크톱에서는 왼쪽 메뉴와 상단 경로를 표시하고, 작은 화면에서는 메뉴와 내용 영역을 화면 폭에 맞게 재배치합니다. 프로젝트 바로가기, 키보드 포커스 표시, 본문 바로가기, 티켓 탭의 키보드 이동과 안내 창의 Esc 닫기를 지원합니다.

### 최초 실행 시 예시 데이터

| 프로젝트 | 함께할 동료 | 신청한 동료 | 필수 참여 중 신청 전 | 전체 티켓 | 확인 대기 / 예정 / 완료 |
| --- | ---: | ---: | ---: | ---: | --- |
| 연례 건강검진 | 120명 | 108명 | 5명 | 5건 | 2 / 1 / 2 |
| 가을 워크숍 | 100명 | 38명 | 8명 | 4건 | 1 / 2 / 1 |
| 사내 사진 공모전 | 80명 | 0명 | 0명 | 4건 | 1 / 3 / 0 |

동료 목록은 총 160명이며 마케팅팀·개발팀·운영팀·디자인팀으로 구분합니다. 최초 안내 기록은 3건입니다. 위 표는 저장된 변경 사항이 없는 초기 상태이며, 등록·신청·취소·확정 변경 후에는 신청 수치가 달라집니다. 새로 등록한 행사에는 아직 규칙으로 생성한 티켓이 없습니다.

예시 기준일은 **2026년 10월 3일**로 고정합니다. D-day와 ‘이번 달’도 이 기준을 사용하며, 실제 오늘 날짜를 자동으로 반영하지 않습니다.

## 2 핵심 기능 요약

아래 기능을 제품의 중심으로 유지합니다. ‘현재 할 수 있는 일’은 예시 데이터·모의 실행의 범위이며, 실제 운영 수준으로 완성하기 위한 요구사항은 13절에 구분합니다.

| 기능 | 현재 할 수 있는 일 | 구현 범위 |
| --- | --- | --- |
| F01 홈 현황 | 프로젝트별 확인할 일, 현황 요약과 최근 안내 확인 | 등록한 프로젝트와 계산된 신청 현황 표시. 티켓은 여전히 예시 |
| F02 프로젝트 전체 티켓 | 한 프로젝트의 확인 대기·예정·완료 티켓 조회 | 티켓별 초안 확인과 안내 기록 연결 |
| F03 프로젝트 캘린더 | 신청 마감·행사·안내 예정일을 월간 일정으로 확인 | 월 이동, 날짜 선택, 목록 전환 |
| F04 안내 초안 편집 | 본문 직접 수정과 말투에 따른 초안 변경 | 준비된 템플릿 사용 |
| F05 팀별 DM 대상 선택 | 대상 범위와 한 팀·여러 팀·전체 팀 선택 | 프로젝트 대상 명단과 유효한 신청 기록으로 수신 명단 계산 |
| F06 Slack 채널 선택 | 게시할 채널과 공개 범위 확인 | 예시 채널 구성원 기준 표시 |
| F07 확인 후 보내기 | 내용과 대상을 확인한 뒤 티켓별 보내기 실행 | 실제 전송 없는 모의 실행 |
| F08 보낸 안내 관리 | 원문 보기·수정, Slack 링크 저장, 기존 기록 추가 | 브라우저 안에서 기록 관리 |
| F09 저장과 복원 | 운영 정보, 신청 기록, 안내 기록, 티켓 완료 상태와 캘린더 설정 유지 | 브라우저 로컬 저장소 사용 |

## 3 F01 홈 현황

담당자가 오늘 챙길 프로젝트와 최근 안내를 한 화면에서 확인합니다.

- 현황 요약에는 진행 중인 프로젝트 수, 확인 대기 티켓 수, 신청 마감 요약과 보낸 안내 수를 표시합니다.
- ‘함께 챙길 프로젝트’에는 확인 대기 티켓이 있는 프로젝트만 표시합니다. 대표 업무, 추가 업무 수, D-day, 신청 인원과 신청률을 함께 보여줍니다.
- 프로젝트 행 전체를 누르면 해당 프로젝트의 **모든 티켓**이 열립니다.
- ‘최근 보낸 안내’는 최근 날짜순으로 최대 3건을 표시합니다. 안내를 누르면 원문과 Slack 링크를 확인하는 기록 창이 열립니다.
- 확인 대기 티켓을 모두 처리한 프로젝트는 홈의 확인할 일 목록에서 빠지지만, 프로젝트 메뉴에서는 계속 조회할 수 있습니다.

**현재 한계:** 신청 인원은 대상 명단·신청 기록으로 계산하지만 최초 명단은 예시입니다. ‘이번 주 신청 마감’ 집계는 달력 주차 대신 예시 기준일에서 마감까지 7일 이하인 프로젝트를 세는 방식입니다. 새 프로젝트에 대한 확인할 일은 아직 자동 생성하지 않습니다.

## 4 F02 프로젝트 전체 티켓

한 프로젝트의 신청 현황, 모든 티켓과 관련 안내 기록을 함께 확인합니다.

- 상단에 필수 신청·자율 신청·합계의 대상/신청/신청 전 인원을 표로 표시합니다. 각 행의 신청과 신청 전은 대상을 정확히 나누며, 신청률은 합계 행의 신청 ÷ 대상입니다. 확정 대기는 신청에 포함하고 취소는 신청 전으로 집계합니다.
- 동료별 명단에서 ‘신청 취소’를 누르면 동료·팀·프로젝트를 명시한 확인 창이 열립니다. 사유를 입력하고 확정해야 취소됩니다. 대상 명단에는 남고 신청 전 상태로 바뀝니다. 신청·확정·취소 때마다 이전 상태, 새 상태, 시각, 사유를 이 브라우저의 변경 기록에 추가합니다.
- ‘전체 티켓’ 탭에서는 미완료 티켓을 날짜가 빠른 순서로 먼저, 완료 티켓을 실제 안내 기록 시각이 최근인 순서로 아래에 보여줍니다. 같은 날짜에는 확인 대기 티켓이 예정 티켓보다 먼저 옵니다.
- 티켓에는 제목, 날짜, 목적, 판단 근거와 상태를 표시합니다.
- 확인 대기 티켓의 ‘보낼 내용 확인’을 누르면 **그 티켓의 초안과 보내기 설정**이 열립니다.
- 완료 티켓의 ‘보낸 안내 보기’를 누르면 연결된 안내 기록이 열립니다.
- ‘보낸 안내’ 탭에서는 해당 프로젝트의 기록만 최근 날짜순으로 조회합니다.
- 일정 영역에는 신청 마감, 행사일 또는 운영 종료·발표일, 담당자, 참고 자료 이름과 최근 안내 최대 2건을 표시합니다.

**핵심 규칙:** 안내 하나를 보내면 해당 티켓만 완료로 바뀝니다. 나머지 티켓, 프로젝트 상태와 신청 인원은 그대로 유지합니다.

**현재 한계:** 화면의 티켓과 판단 시점은 미리 준비한 예시입니다. 미완료 티켓 본문에는 현재 신청 수치를 보여주지만 제안 이유는 아직 규칙으로 갱신하지 않습니다. 완료 티켓은 당시 기록으로 연결합니다. 별도 규칙 평가 모듈은 구현했으나 화면 연결, 보류 기록, 예정 티켓의 자동 활성화는 남아 있습니다. 프로젝트 등록·수정과 신청·취소·확정 변경은 구현했지만 운영 종료는 아직입니다.

## 5 F03 프로젝트 캘린더

홈 하단에서 여러 프로젝트의 신청 마감과 행사 일정을 함께 확인합니다.

- 기본 보기는 월간 캘린더이며 월요일부터 일요일까지 표시합니다.
- 신청 마감, 행사일 또는 운영 종료·발표일, D-7·D-3·D-1 안내 예정일을 구분합니다.
- 이전 달·다음 달·이번 달 이동과 날짜 선택을 지원합니다.
- 날짜를 선택하면 해당 날짜의 모든 일정과 시각을 캘린더 아래에 표시합니다. 각 일정에서 프로젝트 상세로 이동할 수 있습니다.
- ‘목록’ 보기로 바꾸면 프로젝트명, 신청 마감, 신청 인원과 확인 대기 건수를 표로 보여줍니다.
- 작은 화면에서도 7열 달력을 유지하고, 선택한 날짜의 상세 목록으로 일정을 확인합니다.

**현재 한계:** 안내 예정일은 마감일에서 날짜를 계산한 표시입니다. 자동 현황 확인이나 예약 발송은 실행하지 않으며, 티켓의 보내기 완료에 따라 캘린더 일정이 자동 변경되지 않습니다. 안내 예정 시각은 미정으로 표시합니다.

## 6 F04 안내 초안 편집

확인 대기 티켓에서 프로젝트 이름, 마감과 신청 안내가 포함된 초안을 수정합니다.

- 메시지 본문을 직접 입력하거나 수정할 수 있습니다.
- ‘친근하고 밝게’, ‘친근하고 간결하게’, ‘신청 요청을 명확하게’ 중 말투를 선택하면 본문이 바로 새 초안으로 바뀝니다. 직접 수정한 본문도 교체된다는 안내를 선택란 아래에 표시합니다.
- 새 초안 문구는 `prototype/message-templates.js`에서 관리합니다. 세 말투 모두 같은 프로젝트 제목·마감·담당자·신청 링크를 사용하며, ‘이미 신청하셨다면…’ 문장은 넣지 않습니다. 이미 보낸 안내 원문은 수정하지 않습니다.
- 본문을 수정하거나 새 말투를 적용하면 기존 보내기 확인 체크를 해제합니다.
- 공백뿐인 본문은 보내기 예시를 실행할 수 없습니다. 본문 입력은 최대 20,000자입니다.

**현재 한계:** 실제 AI가 생성한 문장이 아니라 준비된 템플릿을 사용합니다. 신청 URL은 예시 문구이며 실제 신청 페이지에 연결되지 않습니다. 보내기 전 초안은 같은 브라우저의 로컬 저장소에 보관하며, 다른 기기와 공유되지 않습니다.

## 7 F05 DM 대상 선택

DM을 받을 동료의 범위를 정한 뒤 팀별로 선택합니다.

| 대상 범위 | 포함하는 동료 |
| --- | --- |
| 아직 신청하지 않은 동료 | 프로젝트 참여 대상 중 신청 전인 동료 |
| 프로젝트에 함께할 모든 동료 | 신청 완료 여부와 관계없는 프로젝트 참여 대상 전원 |
| 모든 동료 | 예시 동료 목록 160명 전체 |

- 팀으로 고르기에서는 한 팀·여러 팀·전체 팀을 선택합니다. 팀 옆에는 선택한 대상 범위에 해당하는 인원수를 표시합니다.
- 동료 직접 고르기에서는 현재 대상 범위 안의 동료를 이름·팀으로 검색해 개별 체크합니다. 팀 선택과 개인 선택은 각각 유지되며, 현재 선택 방식만 DM 대상에 적용합니다.
- 수신자 수와 필수 참여 중 신청 전 인원을 계산합니다. 명단에는 이름, 팀과 신청 상태를 표시하며 8명씩 이전·다음 페이지로 조회합니다.
- 대상 범위와 현재 팀 또는 개인 선택의 교집합으로 명단을 계산하므로 같은 동료를 중복으로 포함하지 않습니다.
- 선택한 동료가 없으면 안내 문구를 표시하고 보내기 버튼을 비활성화합니다.
- 팀별 선택은 **각 동료에게 개별 DM을 보내는 대상 선택 방식**입니다. 그룹 DM 대화를 만드는 기능은 아닙니다.

**현재 한계:** 동료와 팀은 예시 데이터이고 Slack 계정과 연결되지 않았습니다. 필수 참여 동료만 따로 선택하는 전용 필터는 없으며, 포함 인원을 표시하는 방식입니다. 신청·취소·확정 대기는 수신 명단에 즉시 반영됩니다.

## 8 F06 Slack 채널 선택

DM 대신 채널에 공지를 게시하는 방식을 선택할 수 있습니다.

- 전체 공지 또는 마케팅·개발·운영·디자인 공지 채널을 여러 곳 추가할 수 있습니다. 처음에는 채널을 자동 선택하지 않습니다. 선택한 채널은 추가한 순서대로 목록에 쌓이고 개별 제거할 수 있습니다.
- 채널별 예시 구성원과 프로젝트 대상 외 인원, 선택한 채널 전체의 고유 공개 인원을 구분해 표시합니다. 여러 채널에 속한 동료는 게시물을 중복해서 볼 수 있습니다.
- DM의 대상 범위와 팀 선택 조건을 채널 공개 범위에 적용하지 않습니다.
- 게시 단위는 **선택한 채널마다 공지 1건**입니다. 구성원 수를 개별 발송 성공 수나 실제 열람 수로 표시하지 않습니다.
- 확인 문구도 DM 수신자 확인에서 ‘게시할 채널·공개 범위 확인’으로 바뀝니다.

**현재 한계:** 채널 목록과 구성원은 예시입니다. 현재 ‘공개 인원’ 표시는 예시 구성원 수로 계산하며 실제 공개 범위를 검증한 값이 아닙니다. 실제 Slack 채널 검색, 공개·비공개·외부 공유 여부와 게시 권한 확인, 워크스페이스 연결은 구현하지 않았습니다. PRD의 공개 범위 확인 요구사항을 충족한 것으로 간주하지 않습니다.

## 9 F07 확인 후 보내기와 티켓 완료

본문과 받는 동료 또는 게시 채널을 확인한 뒤 **보내기 예시**를 실행합니다.

1. 확인 대기 티켓에서 초안과 보내는 방법을 선택합니다.
2. 하단 확인 체크를 누르면 현재 본문 전체와 DM 수신 동료 또는 채널별 공개 범위가 확인 창에 표시됩니다.
3. 확인 창 안의 체크를 완료해야 하단 체크가 적용됩니다. 본문이 비어 있지 않고 대상이 있으며 확인한 본문·대상과 현재 값이 같을 때만 보내기 버튼이 활성화됩니다.
4. 실행하면 안내 기록을 만들고 해당 티켓만 완료로 변경합니다.
5. 프로젝트 전체 티켓 화면으로 돌아가 결과를 표시합니다. 완료 티켓에서 보낸 원문을 다시 열 수 있습니다.

본문, 적용한 말투, DM·채널 방식, 대상 범위, 선택한 팀·개인 또는 채널을 변경하면 확인 체크를 해제합니다. 검토 화면을 벗어나 다시 열거나 새로고침·브라우저 재시작하면 초안과 선택만 복원하고 확인 체크는 비운 상태로 시작합니다. 다시 확인 창을 열어 현재 본문과 수신 대상을 확인해야 보내기 버튼이 활성화됩니다. 완료 티켓은 같은 흐름에서 다시 보내지 못하도록 처리합니다.

기록에는 프로젝트·티켓 식별자, 본문, 보낸 곳 요약과 출처를 저장합니다. DM은 수신자 ID 목록을, 채널 게시에는 채널 ID 목록을 추가로 저장합니다. 보내기 예시는 `simulated` 출처로 구분하며 생성 시각은 예시 값인 2026년 10월 3일 10시를 사용합니다.

**현재 한계:** 실제 전송, 수신자별 성공·실패, 재시도, 예약 실행과 서버 기반 승인 기록은 없습니다. 실행 전 최신 원본을 조회해 대상을 재검증하지도 않습니다. 안내 기록의 Slack 메시지 링크는 자동 생성되지 않습니다. 본문 내용·날짜·신청 링크의 정확성이나 파일·본문의 민감 정보를 검사하지 않으며, 비어 있지 않은 본문과 대상·확인 체크만으로 모의 실행합니다.

## 10 F08 보낸 안내 원문과 기록 관리

홈의 최근 안내, 프로젝트의 최근 안내·보낸 안내 탭, 전체 보낸 안내 메뉴와 완료 티켓에서 안내 기록을 열 수 있습니다.

- 전체 보낸 안내 화면은 등록된 프로젝트마다 카드와 유형 표식을 표시하고, 그 안을 ‘최초 공지’와 ‘리마인드 알림’으로 나눕니다. 각 종류의 기록은 최근 날짜순입니다.
- 새로 추가하는 안내에는 종류를 직접 선택합니다. 기존 예시·이전 버전 기록은 제목과 연결 티켓을 기준으로 분류하며 기록 창에서 종류를 바꿀 수 있습니다.

### 원문 조회와 수정

- 기록 창에서 프로젝트, 제목, 보낸 날짜·시각, 보낸 곳과 원문을 표시합니다.
- ‘기록 내용 수정’으로 보관 중인 원문을 수정하고 저장할 수 있습니다.
- 원문이 없는 기록에는 안내 문구를 표시하며, 수정 화면에서 내용을 추가할 수 있습니다.
- 예시 원문, 직접 추가한 기록, 보내기 예시의 출처를 구분합니다.

### Slack 메시지 링크

- 메시지 링크를 직접 붙여넣어 저장하거나 변경할 수 있습니다.
- HTTPS의 Slack 메시지 주소 형식을 확인하고, 잘못된 주소는 저장하지 않습니다.
- 저장된 링크가 있으면 ‘Slack에서 열기’로 새 탭에서 이동합니다.
- 링크의 실제 존재 여부나 사용자 접근 권한은 검사하지 않습니다. 원문을 Slack에서 자동으로 가져오지도 않습니다.

### 기존 안내 기록 추가

프로젝트 화면 또는 전체 보낸 안내 화면의 ‘안내 기록 추가’를 사용합니다. 프로젝트, 제목, 보낸 날짜·시각과 보낸 곳을 입력하고 **원문 또는 Slack 메시지 링크 중 하나 이상**을 넣어야 합니다.

| 입력 항목 | 현재 조건 |
| --- | --- |
| 프로젝트 | 등록된 예시 프로젝트 중 선택 |
| 안내 종류 | 최초 공지 또는 리마인드 알림 |
| 제목 | 필수, 최대 160자 |
| 보낸 날짜와 시각 | 필수, 직접 입력 가능 |
| 보낸 곳 | 필수, 최대 200자, 채널명·DM 인원 등을 자유롭게 입력 |
| 안내 원문 | 최대 20,000자 |
| Slack 메시지 링크 | 최대 2,000자, 입력하면 주소 형식 검사 |

**핵심 규칙:** 원문과 링크가 모두 비어 있으면 저장하지 않습니다. 기록 추가·수정은 메시지를 전송하거나 Slack 원본을 변경하지 않습니다. 직접 추가한 기록은 티켓을 자동 완료 처리하지 않습니다. 현재 저장 원문은 모의 발송 기록까지 수정할 수 있으므로, 실제 발송 원문을 보존해야 한다는 PRD 요구는 향후 실제 연동에서 별도로 구현해야 합니다.

**현재 한계:** 전체 안내 기록은 예시·직접 추가·보내기 예시를 합쳐 최대 100건까지 추가할 수 있습니다. 기록 삭제, 제목·보낸 날짜·보낸 곳의 저장 후 수정, 기존 티켓과 수동 연결 기능은 구현하지 않았습니다.

## 11 F09 저장과 복원

운영 정보·신청 기록·안내 기록·티켓 처리 결과는 같은 브라우저에서 이어서 확인할 수 있도록 로컬 저장소에 저장합니다.

| 데이터 | 새로고침 후 유지 |
| --- | --- |
| 안내 원문과 Slack 링크, 직접 추가한 기록 | 유지 |
| 보내기 예시로 완료한 티켓과 연결 안내 | 유지 |
| 등록·수정한 운영 정보와 대상·필수 명단 | 유지 |
| 로컬 신청·취소·확정 상태, 변경 이력·취소 사유와 마지막 확인 시각 | 유지 |
| 캘린더의 연도·월·선택 날짜·보기 방식 | 유지 |
| 보내기 전 초안과 DM·채널 방식, 대상 범위, 팀·개인·채널 선택 | 유지 |
| 보내기 확인 체크 | 저장·복원하지 않음. 새로고침 뒤 다시 확인해야 적용 |
| 프로젝트 탭과 동료 명단 페이지 | 초기 상태로 복원 |

저장 데이터를 읽을 때 기록 형식과 프로젝트 연결 등을 확인하고, 잘못된 데이터는 복원 대상에서 제외합니다. 초안과 선택은 티켓별로 복원하고, 확인 체크는 복원하지 않습니다. 완료 티켓은 관련 보내기 예시 기록이 있을 때 복원합니다. 저장 실패 시에는 사용자에게 알리고 현재 열어둔 화면에서는 상태를 유지합니다.

**현재 한계:** 저장 범위는 해당 브라우저의 접속 주소입니다. 다른 브라우저·기기·포트와 공유되지 않고, 사이트 데이터를 지우면 초기 상태로 돌아갑니다. 로컬 기록은 사용자가 수정·삭제할 수 있으므로 감사 기록으로 신뢰할 수 없습니다. 실제 운영에서 취소 사유와 모든 상태 변경을 여러 운영자가 공유하고 보존하려면 인증된 서버와 DB, 서버 시각·행위자 기록, 변경 이력 보호가 필요합니다. 실시간 공동 작업과 다른 탭의 변경 자동 반영도 없습니다.

### 2026년 10월 6일 구현 준비: Supabase 첫 연결

- Supabase Auth 서버 연결과 로컬 API 설정 상태를 확인했습니다. 로그인 화면, 초안 자동 저장 상태·재시도·버전 충돌 선택, 링크·파일 자료 선택 화면을 추가했습니다.
- 안내 파일은 인증된 운영자의 비공개 Storage 경로와 메타데이터 테이블에 저장하도록 구현했습니다. 초안에는 본문·대상·자료 선택을 함께 저장합니다.
- 연결된 Supabase 프로젝트에 SQL 마이그레이션을 적용해 테이블·비공개 버킷·정책을 확인했습니다. 실제 계정으로 로그인해 예시 초안의 생성·수정과 새로고침 후 복원을 확인했습니다. 파일 저장과 다른 탭 복원은 아직 검증하지 못했습니다. 프로젝트·신청 상태·승인·보낸 기록은 여전히 브라우저 저장입니다. 실제 Slack 전송은 없습니다.

### 2026년 10월 5일 구현: PLAN 1단계

- 운영자 정보는 `projects` 배열에 ID·이름·설명·시작일·마감 시각·운영 일정·신청 URL·담당자·대상 동료 ID·필수 동료 ID·확정 방식을 저장합니다. 신청 원본 역할은 별도 `applications` 배열의 `projectId`·`employeeId`·`status`(`applied`/`confirmed`/`cancelled`)·`checkedAt`이 맡습니다. 지금은 모두 브라우저에서 바꾸는 로컬 자료이며 외부 원본 조회는 없습니다.
- 프로젝트 상세의 신청·취소·확정 버튼이 기록을 바꿉니다. 즉시 확정형은 신청을 `confirmed`로, 별도 절차형은 `applied`로 기록합니다. 별도 절차형의 확정 대기자는 신청 인원에 포함되고 미신청 DM에서는 빠집니다. 대상 명단 외 기록은 집계에서 제외하고 건수를 알립니다.
- 신청률은 고유 대상 ID 중 유효한 신청 ID 수를 고유 대상 수로 나눕니다. 대상이 0명이면 신청률 대신 ‘대상 없음’을 표시합니다. 홈·상세·DM 명단은 `calculateStatus`의 같은 결과를 사용합니다.
- 저장 형식은 로컬 저장소 version 3입니다. 이전 version 1의 안내 기록·완료 티켓·캘린더와 version 2의 운영 정보·신청 상태를 읽습니다. 프로젝트 목록에서 두 번 확인해 브라우저의 모든 로컬 자료를 예시로 초기화할 수 있습니다. 직접 입력 데이터는 예시 데이터와 구분해 표시합니다.
- 새 프로젝트는 화면에서 티켓이 비어 있습니다. 예시 프로젝트의 화면 티켓은 고정된 시점과 상태를 유지하며, 판단 근거는 현재 수치와 ‘예시 티켓’ 안내로 대체했습니다. 이후 순수 규칙 평가 모듈을 만들었으나 화면의 실제 시각·공휴일 입력과 연결하는 작업은 남아 있습니다. 고정된 재안내 시간 제한은 요구사항에서 제외했습니다.

### 등록 화면 피드백 반영

- 화면 이름을 ‘프로젝트 등록/수정’으로 바꾸고, ‘이름’은 ‘프로젝트 제목’, ‘담당자’는 ‘담당자 이름’으로 표시합니다. 등록 화면의 불필요한 안내 문장은 제거했습니다.
- 대상과 필수 동료를 ID 문자열 대신 이름 검색·팀 필터·검색 결과 일괄 선택·개별 체크로 지정합니다. 내부 식별자와 저장 형식은 그대로 유지합니다. 필수 체크는 대상 동료에만 적용됩니다.
- 여러 PDF·DOCX·TXT·MD와 붙여넣은 내용을 서버에서 읽고 Gemma로 분석합니다. 스캔 PDF OCR, 출처 검증, 누락·충돌 표시, 후보 선택·수정·적용을 지원합니다. 적용한 근거는 프로젝트와 함께 브라우저에 보관합니다. [SPEC 002의 9절](spec_002.md#9-기획서에서-프로젝트-정보-채우기)에 현재 계약과 제한을 정리했습니다.

## 13 기존 핵심 기능을 완성하기 위해 남은 일

**2절의 F01~F09를 중심으로, 예시 현황·준비된 티켓·모의 발송을 실제 데이터와 동작으로 연결합니다.** 구매·지급·담당자 인계까지 관리하는 새로운 제품으로 확장해야 기존 기능이 완성되는 것은 아닙니다.

### 관련 기준과 구현 계획

- 현황 계산·필수/자율 안내·업무시간·재안내 이력 기준은 [PRD 4절](../docs/PRD.md#4-분석과-리마인드-제안의-기준)을 따릅니다. 발송 조건은 [PRD 5절](../docs/PRD.md#5-안내-품질과-발송의-필수-조건), 미정 항목은 [PRD 8절](../docs/PRD.md#8-구현-전에-남은-결정)에서 관리합니다.
- 단계별 작업과 완료 기준은 [PLAN 3절](../docs/PLAN.md#3-단계별-구현과-완료-기준), 현재 진행 상태와 다음 작업은 [PLAN 6절](../docs/PLAN.md#6-다음-작업과-진행-기록)에서 관리합니다.

- 현재 티켓과 추천 문구는 예시입니다. 안내 처리, 신청·확정, 운영 종료 상태를 구분하며, 예시 동작 확인을 현업 효용의 증거로 사용하지 않습니다.

## 14 확인한 주요 동작

아래 첫 다섯 항목은 이전 구현 당시의 브라우저 확인 기록입니다. 이번 변경에서는 개인 DM 1명 선택, 말투 변경 시 본문 자동 갱신, 확인 창 체크 전후의 보내기 잠금, 본문 수정 후 승인 해제, 여러 채널의 추가 순서·모의 게시 기록·새로고침 복원, 채널 0곳일 때 차단, 프로젝트·종류별 안내 기록을 브라우저에서 확인했습니다. 계산과 초안 문구 경계는 `npm test`로 확인했습니다. 13절의 미구현 요구사항을 검증한 결과는 아닙니다.

- 홈에서 건강검진을 열면 확인 대기·예정·완료 티켓 5건이 모두 표시됩니다.
- 팀별 DM 수신자 계산, 대상이 없는 경우 실행 차단, DM에서 채널로 변경 시 확인 해제가 동작합니다.
- 보내기 예시 이후 해당 티켓만 완료되고 다른 확인 대기 티켓은 유지됩니다.
- 안내 원문 수정, Slack 링크 저장과 기존 기록 추가가 새로고침 후에도 유지됩니다.
- 잘못된 Slack 링크는 저장을 차단합니다.
- 캘린더 월 이동, 날짜별 복수 일정, 목록 전환과 작은 화면에서 가로 넘침이 없는 배치를 확인했습니다.

## 15 Gemma 연결 확인 (2026-10-06)

- `npm run test:gemma`는 `.env`의 API 키·모델 설정으로 가상 문서 두 개의 핵심 정보 추출을 요청합니다. 키를 출력하지 않으며 일반 `npm test`와 분리했습니다.
- 최초 호출은 HTTP 402(선불 크레딧 소진)로 차단됐으나, API 키 교체 후 같은 날 실제 호출에 성공했습니다. 가상 문서 두 개의 행사명·일시·장소·대상과 자료별 근거, 마감일 충돌(11월 8일/10일), 신청 링크 누락 표시를 확인했습니다. 단일 예시 검증이며 실제 파일·다양한 문서의 정확도는 미검증입니다. 이후 여러 자료의 AI 분석을 웹 화면에 연결했습니다. AI 공지 초안 생성은 아직 미구현입니다.
- SDK 설치 후 기존 자동 테스트 43개가 통과했습니다.

## 16 여러 자료 분석과 OCR 웹 연결 (2026-10-06)

- 프로젝트 등록·수정에서 PDF·DOCX·TXT·MD 최대 6개와 텍스트를 함께 분석합니다. 스캔 PDF 자동 OCR과 전체 PDF 이미지 읽기를 지원합니다. 제한과 데이터 계약은 [SPEC 002 9절](spec_002.md#9-기획서에서-프로젝트-정보-채우기)을 따릅니다.
- 실제 워크숍 Word 2개·PDF 1개의 통합 분석에서 이전/현재 마감·링크를 모두 확인했습니다. PDF를 이미지로 읽는 실제 Gemma 호출과 이미지 전용 예시 PDF의 자동 OCR·핵심 필드 추출도 확인했습니다. 예시 외 문서의 정확도를 보장하는 결과는 아닙니다.
- 로컬 QA 서버에서 Supabase 계정 응답만 모의 처리하고 Gemma는 실제 호출했습니다. 웹의 파일 선택 → 로그인(선택 파일 유지) → 분석 → 7개 항목 선택 적용 → 프로젝트 저장·새로고침 → 근거 복원, 입력 변경 시 결과 무효화, 손상 PDF 오류와 선택 파일 유지·재시도 버튼을 확인했습니다. 실제 Supabase 운영자 로그인은 기존 인증 경로를 사용하며 이번 UI QA에서는 새 실계정 로그인을 하지 않았습니다.
- 390px 화면과 데스크톱에서 가로 넘침이 없고 브라우저 오류가 없었습니다. 자동 테스트 50개 통과, npm audit 취약점 0건입니다. 자동 테스트는 실제 AI를 호출하지 않습니다.
- 원본은 서버/DB에 보관하지 않으며 프로젝트 값과 적용 근거는 이 브라우저에 저장합니다. 웹 배포·배포 환경의 PDF/OCR 실행은 이번 작업에서 검증하지 않았습니다.
