# spec_001 현재 프로토타입 기능 명세

작성일: 2026년 10월 3일  
수정일: 2026년 10월 7일
대상: 팀 행사·복지 운영 웹앱의 현재 구현

이 문서는 **현재 구현된 기능과 이를 완성하기 위해 남은 일**을 정리합니다. [PRD](../docs/PRD.md)의 제품 중심은 신청 현황·일정·이전 안내를 연결한 안내 운영입니다. 1~12절은 현재 동작을 설명하고, 13절은 F01~F09의 남은 차이를 정리합니다. 14~16절에는 당시 확인 결과와 과거 구현 기록도 포함되므로 이전 단계의 설명을 현재 상태로 읽지 않습니다. 제품 정책은 [PRD](../docs/PRD.md), 진행 상태는 [PLAN](../docs/PLAN.md)에서 관리합니다. **수정할 프로젝트 등록·공지 화면과 예약 티켓 흐름은 [SPEC 003](spec_003.md)의 목표이며, 이 문서의 현재 기능과 구분합니다.**

초기 화면은 예시 동료 160명과 과거 티켓을 표시합니다. 운영 정보를 직접 등록하고 신청·취소·확정 상태를 변경하거나, 실제 접속이 확인된 Google Sheets 예시 원본의 직원명부·대상·신청이력을 가져올 수 있습니다. 프로젝트별 현황과 DM 대상은 같은 신청 기록에서 계산합니다. 새 프로젝트의 규칙 티켓은 공개 공휴일 달력을 반영해 화면·캘린더에 연결합니다. 운영 상태·초안은 로그인한 계정의 Supabase에 저장합니다. 자료 입력의 Gemini 분석과 카드 기반 초안 생성은 구현했습니다. `managerkim` Supabase 프로젝트에는 예시 시트의 시간별 동기화 함수·DB·Cron과 추가 마이그레이션 2개를 적용했고 임시 예약 실행의 저장 성공을 확인했습니다. 운영자 계정의 로컬 브라우저에서 수동 Sheets 가져오기·신청 현황 반영·새로고침 복원을 확인했습니다. 기존 프로젝트의 등록 시각이 없어 첫 정시 실행의 티켓 평가가 오류로 기록된 문제는 첫 안내만 보류하도록 수정해 운영 함수 v6에 배포했습니다. 이후 수동 실행 #14는 시트 저장 성공·티켓 평가 보류 3건·오류 코드 없음으로 기록됐습니다. 새 함수의 다음 정시 실행과 수정 웹 화면의 운영 배포·검증은 대기 중입니다. 실제 Slack 전송은 구현되지 않았습니다.

**현재 티켓 완료는 모의 안내 발송 완료입니다. 동료의 신청 완료나 행사·복지 운영 종료를 뜻하지 않습니다.** ‘프로젝트·티켓’은 현재 코드와 화면의 명칭입니다.

## 1 화면 구성과 기본 데이터

주 메뉴는 **홈 / 프로젝트 / 보낸 안내**입니다. 프로젝트 안에는 **전체 티켓 / 보낸 안내** 탭을 두고, 확인 대기 티켓에서 **보낼 내용 확인** 화면으로 이동합니다. 예정 티켓에서는 **초안 미리 작성** 화면을 열어 본문과 대상을 준비할 수 있지만, 확인과 모의 발송은 확인 대기 상태에서만 할 수 있습니다. 안내 원문과 Slack 링크는 별도의 기록 창에서 확인합니다.

데스크톱에서는 왼쪽 메뉴와 상단 경로를 표시하고, 작은 화면에서는 메뉴와 내용 영역을 화면 폭에 맞게 재배치합니다. 프로젝트 바로가기, 키보드 포커스 표시, 본문 바로가기, 티켓 탭의 키보드 이동과 안내 창의 Esc 닫기를 지원합니다.

### 최초 실행 시 예시 데이터

| 프로젝트 | 함께할 동료 | 신청한 동료 | 필수 참여 중 신청 전 | 전체 티켓 | 확인 대기 / 예정 / 완료 |
| --- | ---: | ---: | ---: | ---: | --- |
| 연례 건강검진 | 120명 | 108명 | 5명 | 5건 | 2 / 1 / 2 |
| 가을 워크숍 | 100명 | 38명 | 8명 | 4건 | 1 / 2 / 1 |
| 사내 사진 공모전 | 80명 | 0명 | 0명 | 4건 | 1 / 3 / 0 |

초기 동료 목록은 총 160명이며 마케팅팀·개발팀·운영팀·디자인팀으로 구분합니다. 최초 안내 기록은 3건입니다. 위 표는 저장된 변경 사항이 없는 예시 초기 상태입니다. 등록·신청·취소·확정 또는 Google Sheets 가져오기 이후 수치가 달라집니다. 새 프로젝트에는 첫 안내 준비 티켓을 만들고, 검증된 공휴일 달력과 최신 신청 상태가 있으면 규칙 점검 티켓을 갱신합니다.

초기 예시 티켓·안내 기록의 날짜는 **2026년 10월 3일 전후**입니다. D-day와 캘린더의 ‘이번 달’은 실제 한국 날짜를 사용합니다.

## 3 F01 홈 현황

담당자가 오늘 챙길 프로젝트와 최근 안내를 한 화면에서 확인합니다.

- 현황 요약에는 진행 중인 프로젝트 수, 확인 대기 티켓 수, 신청 마감 요약과 보낸 안내 수를 표시합니다.
- ‘함께 챙길 프로젝트’에는 확인 대기 티켓이 있는 프로젝트만 표시합니다. 대표 업무, 추가 업무 수, D-day, 신청 인원과 신청률을 함께 보여줍니다.
- 프로젝트 행 전체를 누르면 해당 프로젝트의 **모든 티켓**이 열립니다.
- ‘최근 보낸 안내’는 최근 날짜순으로 최대 3건을 표시합니다. 안내를 누르면 원문과 Slack 링크를 확인하는 기록 창이 열립니다.
- 확인 대기 티켓을 모두 처리한 프로젝트는 홈의 확인할 일 목록에서 빠지지만, 프로젝트 메뉴에서는 계속 조회할 수 있습니다.

**현재 한계:** 초기 명단과 기존 티켓은 예시입니다. Google Sheets를 가져오기 전에는 예시 또는 직접 입력 상태를 사용합니다. ‘이번 주 신청 마감’은 달력 주차가 아니라 현재 한국 날짜에서 마감까지 7일 이하인 프로젝트를 셉니다. 새 프로젝트의 규칙 티켓은 공휴일 조회와 신청 상태의 최신성 검증에 실패하면 생성·갱신하지 않습니다.

현재 Sheets 동기화는 등록 시각과 첫 안내 검토 시각이 모두 없는 기존 프로젝트에서 **첫 안내 티켓만 보류**합니다. 시각을 만들어 넣거나 다른 신청 현황·리마인드 평가를 중단하지 않습니다. 동기화 실행 기록에는 평가 보류 건수가 남고, 로컬 화면은 시트 자료 저장 결과와 티켓 평가 보류를 구분해 표시합니다. 이 서버 규칙은 운영 `sync-sheets` v6에 적용됐고 수동 실행 #14에서 성공·보류 3건·오류 코드 없음을 확인했습니다. 수정된 웹사이트 화면은 운영에 아직 반영되지 않았습니다.

## 4 F02 프로젝트 전체 티켓

한 프로젝트의 신청 현황, 모든 티켓과 관련 안내 기록을 함께 확인합니다.

- 상단에 필수 신청·자율 신청·합계의 대상/신청/신청 전 인원을 표로 표시합니다. 각 행의 신청과 신청 전은 대상을 정확히 나누며, 신청률은 합계 행의 신청 ÷ 대상입니다. 확정 대기는 신청에 포함하고 취소는 신청 전으로 집계합니다.
- 동료별 명단에서 ‘신청 취소’를 누르면 동료·팀·프로젝트를 명시한 확인 창이 열립니다. 사유를 입력하고 확정해야 취소됩니다. 대상 명단에는 남고 신청 전 상태로 바뀝니다. 신청·확정·취소 때마다 이전 상태, 새 상태, 시각, 사유를 이 브라우저의 변경 기록에 추가합니다.
- ‘전체 티켓’ 탭에서는 미완료 티켓을 날짜가 빠른 순서로 먼저, 완료 티켓을 실제 안내 기록 시각이 최근인 순서로 아래에 보여줍니다. 같은 날짜에는 확인 대기 티켓이 예정 티켓보다 먼저 옵니다.
- 티켓에는 제목, 날짜, 목적, 판단 근거와 상태를 표시합니다.
- 확인 대기 티켓의 ‘보낼 내용 확인’을 누르면 **그 티켓의 초안과 보내기 설정**이 열립니다.
- 완료 티켓의 ‘보낸 안내 보기’를 누르면 연결된 안내 기록이 열립니다.
- ‘보낸 안내’ 탭에서는 해당 프로젝트의 기록만 최근 날짜순으로 조회합니다.
- 일정 영역에는 신청 마감, 행사일 또는 운영 종료·발표일, 담당자, 참고 자료 이름과 최근 안내 최대 2건을 표시합니다.
- 직접 등록한 프로젝트의 상세 화면에는 ‘휴지통으로 이동’ 버튼이 있습니다. 확인 창에서 연결된 티켓·안내 기록 수를 보고 이동하며, 프로젝트 목록의 ‘휴지통’에서 복원합니다. 휴지통에 있는 동안 프로젝트·티켓·신청·초안·기록은 현재 운영 상태에 보존하되 일반 프로젝트·홈·달력·안내 기록·공지 편집 경로에서는 숨깁니다. 예시 프로젝트와 Sheets 기반 프로젝트는 휴지통 대상에서 제외합니다.

**핵심 규칙:** 안내 하나를 보내면 해당 티켓만 완료로 바뀝니다. 나머지 티켓, 프로젝트 상태와 신청 인원은 그대로 유지합니다.

**현재 한계:** 기존 예시 프로젝트에는 미리 준비한 티켓이 남아 있습니다. 새 프로젝트와 신청 변경에는 규칙 평가기를 연결해 티켓과 이유를 갱신하고, 보류·안내하지 않기 사유를 저장합니다. 운영 종료·취소 시 미발송 티켓을 종료 처리합니다. Sheets 기반 프로젝트의 모의 발송 직전 원본 재조회는 연결했습니다. 예시 시트의 서버 정기 실행은 활성화됐지만, 운영자 브라우저 화면의 반영·복원과 신규 프로젝트의 전체 사용자 흐름은 실사용 검증 전입니다. 실제 Slack 발송은 없습니다.

**휴지통 한계:** 복원 가능한 보관이며 영구 삭제·자동 만료는 없습니다. 초안과 첨부 파일도 삭제하지 않습니다. 수정된 화면 코드를 아직 운영 웹사이트에 배포하지 않았으므로, 같은 Supabase 데이터를 읽는 이전 운영 웹 화면은 휴지통 표시 상태를 해석하지 못합니다.

## 5 F03 프로젝트 캘린더

홈 하단에서 여러 프로젝트의 신청 마감과 행사 일정을 함께 확인합니다.

- 기본 보기는 월간 캘린더이며 월요일부터 일요일까지 표시합니다.
- 신청 마감, 행사일 또는 운영 종료·발표일, 규칙으로 생성한 점검 티켓의 예정일·시각을 구분합니다.
- 이전 달·다음 달·이번 달 이동과 날짜 선택을 지원합니다.
- 날짜를 선택하면 해당 날짜의 모든 일정과 시각을 캘린더 아래에 표시합니다. 각 일정에서 프로젝트 상세로 이동할 수 있습니다.
- ‘목록’ 보기로 바꾸면 프로젝트명, 신청 마감, 신청 인원과 확인 대기 건수를 표로 보여줍니다.
- 작은 화면에서도 7열 달력을 유지하고, 선택한 날짜의 상세 목록으로 일정을 확인합니다.

**현재 한계:** 규칙 티켓의 점검 예정일·시각은 공휴일과 업무시간 조정을 반영하고, 미완료 티켓이 변경되면 캘린더도 다시 표시합니다. 초기 예시 티켓은 별도 가상 기록입니다. 예시 시트에 연결된 프로젝트의 서버 정기 확인은 활성화됐으나, 모든 신규 프로젝트와 운영자 브라우저에서의 반영·복원은 검증되지 않았습니다. 예약 발송은 실행하지 않습니다.

## 6 F04 안내 초안 편집

확인 대기 티켓에서 프로젝트 이름, 마감과 신청 안내가 포함된 초안을 수정합니다.

- 메시지 본문을 직접 입력하거나 수정할 수 있습니다.
- 말투와 공지 목적을 선택해도 현재 본문은 유지됩니다. ‘Gemini로 새 초안 문구 생성’을 누르면 검증된 새 문구가 메시지 본문 입력 칸에 바로 들어가고 초안 저장을 시작합니다. Gemini에는 일반 텍스트를 요청하고, 반환된 굵게 표시용 `**` 쌍은 새 본문에 넣기 전에 제거합니다. 이미 저장된 본문은 자동 수정하지 않습니다. 생성 직전 본문으로 되돌릴 수 있습니다. 생성 중 본문·정보 카드·대상이 바뀌면 결과로 덮어쓰지 않습니다. 목적은 연결 티켓에서 첫 안내 또는 추가 안내를 추정합니다.
- 공지 정보 카드의 항목을 수정·제외할 수 있습니다. 서버는 포함된 카드 값만 Gemini에 보내고 날짜·링크·수치 및 근거 없는 주장을 검사합니다. `prototype/message-templates.js`는 테스트에 남아 있지만 현재 검토 화면의 생성 경로는 Gemini를 사용합니다.
- ‘무엇을·해야 할 일·마감’ 중 빠진 항목이 있으면 생성 버튼 위에 필요한 내용을 표시하고 해당 카드 입력란으로 이동합니다. 마감이 지난 신청 안내에는 마감 재확인을 표시하고 보내기 예시를 막습니다.
- 정보 카드에서는 본문 확인을 요구하지 않습니다. 카드의 확인된 값으로 Gemini 초안을 생성하면 본문 재검토 상태가 해소됩니다. 정보 카드를 바꾼 뒤 직접 작성한 본문을 유지할 때에만 본문 옆에서 최신 정보와 맞는지 확인합니다.
- 본문을 수정하거나 새 말투를 적용하면 기존 보내기 확인 체크를 해제합니다.
- 공백뿐인 본문은 보내기 예시를 실행할 수 없습니다. 본문 입력은 최대 20,000자입니다.

기존 예시 티켓·안내 원문에는 예시 문구가 남아 있습니다. 채택한 초안과 카드 수정은 로그인 시 Supabase에 저장됩니다. 카드 항목의 원문 근거·충돌 상태는 생성 입력에 자동 연결되지 않습니다.

## 7 F05 DM 대상 선택

DM을 받을 동료의 범위를 정한 뒤 팀별로 선택합니다.

| 대상 범위 | 포함하는 동료 |
| --- | --- |
| 아직 신청하지 않은 동료 | 프로젝트 참여 대상 중 신청 전인 동료 |
| 프로젝트에 함께할 모든 동료 | 신청 완료 여부와 관계없는 프로젝트 참여 대상 전원 |
| 모든 동료 | 예시 동료 목록 160명 전체 |

- 팀으로 고르기에서는 한 팀·여러 팀·전체 팀을 선택합니다. 팀 옆에는 선택한 대상 범위에 해당하는 인원수를 표시합니다.
- 동료 직접 고르기에서는 현재 대상 범위 안의 동료를 이름·팀으로 검색해 개별 체크합니다. 팀 선택과 개인 선택은 각각 유지되며, 현재 선택 방식만 DM 대상에 적용합니다.
- 수신자 수와 필수 참여 중 신청 전 인원을 계산합니다. 명단에는 이름, 팀과 신청 상태를 표시하며 8명씩 이전·다음 페이지로 조회합니다.
- 대상 범위와 현재 팀 또는 개인 선택의 교집합으로 명단을 계산하므로 같은 동료를 중복으로 포함하지 않습니다.
- `필수 미신청자만 선택`과 `필수 대상 전체 선택` 버튼은 해당 동료 ID를 개인 선택에 넣고 대상 범위를 맞춥니다. 선택한 명단의 필수·자율·대상 외 인원과 신청 상태별 인원을 구분해 보여줍니다. 이 동작은 코드와 로컬 자동 테스트에서 확인했고 실제 계정의 브라우저 클릭·저장·재진입 흐름은 아직 확인하지 않았습니다.
- 선택한 동료가 없으면 안내 문구를 표시하고 보내기 버튼을 비활성화합니다.
- 팀별 선택은 **각 동료에게 개별 DM을 보내는 대상 선택 방식**입니다. 그룹 DM 대화를 만드는 기능은 아닙니다.

**현재 한계:** 동료와 팀은 예시 데이터이고 Slack 계정과 연결되지 않았습니다. 빠른 선택과 인원 구분은 실제 Slack 수신자를 검증한 결과가 아닙니다. 신청·취소·확정 대기는 화면의 수신 명단에 반영됩니다.

## 8 F06 Slack 채널 선택

DM 대신 채널에 공지를 게시하는 방식을 선택할 수 있습니다.

- 전체 공지 또는 마케팅·개발·운영·디자인 공지 채널을 여러 곳 추가할 수 있습니다. 처음에는 채널을 자동 선택하지 않습니다. 선택한 채널은 추가한 순서대로 목록에 쌓이고 개별 제거할 수 있습니다.
- 채널별 예시 구성원과 프로젝트 대상 외 인원, 선택한 채널 전체의 고유 공개 인원을 구분해 표시합니다. 여러 채널에 속한 동료는 게시물을 중복해서 볼 수 있습니다.
- DM의 대상 범위와 팀 선택 조건을 채널 공개 범위에 적용하지 않습니다.
- 게시 단위는 **선택한 채널마다 공지 1건**입니다. 구성원 수를 개별 발송 성공 수나 실제 열람 수로 표시하지 않습니다.
- 확인 문구도 DM 수신자 확인에서 ‘게시할 채널·공개 범위 확인’으로 바뀝니다.

**현재 한계:** 채널 목록과 구성원은 예시입니다. 현재 ‘공개 인원’ 표시는 예시 구성원 수로 계산하며 실제 공개 범위를 검증한 값이 아닙니다. 실제 Slack 채널 검색, 공개·비공개·외부 공유 여부와 게시 권한 확인, 워크스페이스 연결은 구현하지 않았습니다. PRD의 공개 범위 확인 요구사항을 충족한 것으로 간주하지 않습니다.

## 9 F07 확인 후 보내기와 티켓 완료

본문과 받는 동료 또는 게시 채널을 확인한 뒤 **보내기 예시**를 실행합니다.

1. 확인 대기 티켓에서 초안과 보내는 방법을 선택합니다.
2. 하단 확인 체크를 누르면 현재 본문 전체와 DM 수신 동료 또는 채널별 공개 범위가 확인 창에 표시됩니다.
3. 확인 창 안의 체크를 완료해야 하단 체크가 적용됩니다. 본문이 비어 있지 않고 대상이 있으며 확인한 본문·대상과 현재 값이 같을 때만 보내기 버튼이 활성화됩니다.
4. 실행하면 안내 기록을 만들고 해당 티켓만 완료로 변경합니다.
5. 프로젝트 전체 티켓 화면으로 돌아가 결과를 표시합니다. 완료 티켓에서 보낸 원문을 다시 열 수 있습니다.

본문, 적용한 말투, DM·채널 방식, 대상 범위, 선택한 팀·개인 또는 채널을 변경하면 확인 체크를 해제합니다. 검토 화면을 벗어나 다시 열거나 새로고침·브라우저 재시작하면 초안과 선택만 복원하고 확인 체크는 비운 상태로 시작합니다. 다시 확인 창을 열어 현재 본문과 수신 대상을 확인해야 보내기 버튼이 활성화됩니다. 완료 티켓은 같은 흐름에서 다시 보내지 못하도록 처리합니다.

보내기 버튼이 잠겨 있을 때는 로그인, 저장 대기, 마감 경과, 본문·대상·확인 누락 등의 이유를 버튼 위에 표시합니다. 마감이 지난 확인 대기 티켓은 홈의 ‘오늘 확인할 일’에서 제외하고 프로젝트 상세에 ‘마감 정보 확인’으로 남깁니다.

기록에는 프로젝트·티켓 식별자, 본문, 보낸 곳 요약과 출처를 저장합니다. DM은 수신자 ID 목록을, 채널 게시에는 채널 ID 목록을 추가로 저장합니다. 보내기 예시는 `simulated` 출처로 구분하며 실행 시각의 한국 시간을 사용합니다.

Sheets 기반 프로젝트에서 **모의 발송**을 누르면 브라우저가 `sync-sheets` 함수를 호출해 원본을 다시 읽고, 저장된 최신 스냅샷을 승인 당시의 시트 ID·대상 명단·신청 상태와 비교합니다. 조회 실패, 원본 변경, 승인 뒤 화면 상태 변경이 있으면 모의 발송을 중단하고 확인 체크를 해제합니다. 성공하면 당시 본문·대상 ID·자료·원본 재조회 시각을 모의 기록에 남깁니다. 이 코드 경로와 비교 규칙은 로컬 자동 테스트로 확인했으며, 실제 계정의 브라우저 전체 흐름은 아직 확인하지 않았습니다.

현재 브랜치에서는 과거에 운영자가 수정한 신청 이력을 기록에 남기되, **현재 Sheets 대상 명단에 있는 사람의 이력만** 현재 신청 상태와 발송 직전 비교에 합칩니다. 대상에서 빠진 사람의 오래된 이력이 새 스냅샷의 신청 상태를 오염시키지 않게 하는 변경입니다. 로컬 자동 테스트로 확인했으며 운영 웹사이트 반영과 브라우저 재검증은 대기 중입니다.

**현재 한계:** 위 재조회는 브라우저의 모의 발송 경로에만 있습니다. 실제 Slack 전송을 처리하는 서버 안에서 최신 원본 재검증·중복 실행 방지·승인 기록·수신자별 성공·실패·재시도는 구현되지 않았습니다. 예약 발송과 Slack 메시지 링크 자동 생성도 없습니다. Gemini가 생성한 본문은 카드와 대조하지만 운영자가 직접 수정한 최종 본문·파일의 민감 정보 검사와 발송 적합성 검사는 없습니다.

## 10 F08 보낸 안내 원문과 기록 관리

홈의 최근 안내, 프로젝트의 안내 기록 탭, 전체 안내 기록 메뉴와 완료 티켓에서 안내 기록을 열 수 있습니다. 안내 기록은 예시·직접 추가·보내기 예시를 표시하며, 전체 화면에서 출처별로 걸러 볼 수 있습니다.

- 전체 보낸 안내 화면은 등록된 프로젝트마다 카드와 유형 표식을 표시하고, 그 안을 ‘최초 공지’와 ‘리마인드 알림’으로 나눕니다. 각 종류의 기록은 최근 날짜순입니다.
- 새로 추가하는 안내에는 종류를 직접 선택합니다. 기존 예시·이전 버전 기록은 제목과 연결 티켓을 기준으로 분류하며 기록 창에서 종류를 바꿀 수 있습니다.

### 원문 조회와 수정

- 기록 창에서 프로젝트, 제목, 보낸 날짜·시각, 보낸 곳과 원문을 표시합니다.
- ‘기록 내용 수정’으로 보관 중인 원문을 수정하고 저장할 수 있습니다.
- 원문이나 Slack 링크를 바꾸면 이전 값을 수정 시각·수정 계정과 함께 이 기록의 정정 이력에 보관합니다. 이는 실제 Slack 메시지의 수정 이력이 아닙니다.
- 원문이 없는 기록에는 안내 문구를 표시하며, 수정 화면에서 내용을 추가할 수 있습니다.
- 예시 원문, 직접 추가한 기록, 보내기 예시의 출처를 구분합니다.

### Slack 메시지 링크

- 메시지 링크를 직접 붙여넣어 저장하거나 변경할 수 있습니다.
- HTTPS의 Slack 메시지 주소 형식을 확인하고, 잘못된 주소는 저장하지 않습니다.
- 저장된 링크가 있으면 ‘Slack에서 열기’로 새 탭에서 이동합니다.
- 링크의 실제 존재 여부나 사용자 접근 권한은 검사하지 않습니다. 원문을 Slack에서 자동으로 가져오지도 않습니다.

### 기존 안내 기록 추가

프로젝트 화면 또는 전체 보낸 안내 화면의 ‘안내 기록 추가’를 사용합니다. 프로젝트, 제목, 보낸 날짜·시각과 보낸 곳을 입력하고 **원문 또는 Slack 메시지 링크 중 하나 이상**을 넣어야 합니다.

| 입력 항목 | 현재 조건 |
| --- | --- |
| 프로젝트 | 등록된 프로젝트 중 선택 |
| 안내 종류 | 최초 공지 또는 리마인드 알림 |
| 제목 | 필수, 최대 160자 |
| 보낸 날짜와 시각 | 필수, 직접 입력 가능 |
| 보낸 곳 | 필수, 최대 200자, 채널명·DM 인원 등을 자유롭게 입력 |
| 안내 원문 | 최대 20,000자 |
| Slack 메시지 링크 | 최대 2,000자, 입력하면 주소 형식 검사 |

**핵심 규칙:** 원문과 링크가 모두 비어 있으면 저장하지 않습니다. 기록 추가·수정은 메시지를 전송하거나 Slack 원본을 변경하지 않습니다. 직접 추가한 기록은 티켓을 자동 완료 처리하지 않습니다. 현재 저장 원문은 모의 발송 기록까지 수정할 수 있으므로, 실제 발송 원문을 보존해야 한다는 PRD 요구는 향후 실제 연동에서 별도로 구현해야 합니다.

**현재 한계:** 전체 안내 기록은 예시·직접 추가·보내기 예시를 합쳐 최대 100건까지 추가할 수 있습니다. 기록 삭제, 제목·보낸 날짜·보낸 곳의 저장 후 수정, 기존 티켓과 수동 연결 기능은 구현하지 않았습니다.

## 11 F09 저장과 복원

운영 정보·신청 기록·안내 기록·티켓 처리 결과는 로그인한 운영자의 Supabase `operator_states`에 버전 조건으로 저장하고, 성공한 각 변경 상태를 `operator_state_revisions`에 남깁니다. 브라우저에는 복원용 캐시도 저장합니다. 안내 초안은 별도 `notice_drafts`에 저장합니다. 서버가 허용하는 영문자·숫자·하이픈 ID는 그대로 쓰고, 첫 안내처럼 다른 문자나 길이 제한을 넘는 티켓 ID는 안정적인 저장용 ID로 바꿔 저장·조회·목록 복원에 공통 적용합니다. 화면의 티켓 ID와 링크는 유지합니다.

화면의 로그인 진입 버튼과 대화상자 제목은 ‘관리자 로그인’으로 표시합니다. Supabase는 내부 인증·저장 서비스 이름으로만 사용합니다.

| 데이터 | 새로고침 후 유지 |
| --- | --- |
| 안내 원문과 Slack 링크, 직접 추가한 기록 | 유지 |
| 보내기 예시로 완료한 티켓과 연결 안내 | 유지 |
| 등록·수정한 운영 정보와 대상·필수 명단 | 유지 |
| 로컬 신청·취소·확정 상태, 변경 이력·취소 사유와 마지막 확인 시각 | 유지 |
| 캘린더의 연도·월·선택 날짜·보기 방식 | 유지 |
| 보내기 전 초안과 DM·채널 방식, 대상 범위, 팀·개인·채널 선택 | 유지 |
| 보내기 확인 체크 | 저장·복원하지 않음. 새로고침 뒤 다시 확인해야 적용 |
| 프로젝트 탭과 동료 명단 페이지 | 초기 상태로 복원 |

저장 데이터를 읽을 때 기록 형식과 프로젝트 연결 등을 확인하고, 잘못된 데이터는 복원 대상에서 제외합니다. 초안과 선택은 티켓별로 복원하고, 확인 체크는 복원하지 않습니다. 완료 티켓은 관련 보내기 예시 기록이 있을 때 복원합니다. 저장 실패 시에는 사용자에게 알리고 현재 열어둔 화면에서는 상태를 유지합니다.

브라우저 캐시 version 7에는 마지막으로 확인한 서버 운영 정보도 저장합니다. 새로고침이나 다른 탭의 변경이 발견되면 서로 다른 항목은 자동으로 합쳐 다시 저장하고, 같은 항목의 변경만 충돌로 표시합니다. 프로젝트 양식에 저장하지 않은 입력이 있으면 화면 이동을 확인하고 서버 정보 갱신도 보류합니다. 로그아웃할 때 서버에 저장되지 않은 초안은 저장을 재시도하지 않고 버립니다. 운영 정보는 저장을 먼저 시도하며, 운영 정보 저장 실패나 프로젝트 양식의 미저장 변경이 있으면 ‘다시 시도 / 변경 버리고 로그아웃’을 보여줍니다. 새 탭은 같은 출처의 로그인된 탭에서 세션을 받아 로그인 상태를 복원하도록 구성했습니다.

프로젝트 편집에서는 안내 점검 설정을 접어 두고, 대상 동료가 0명이면 저장하지 않습니다. 예시 자료 초기화는 로그인 중에는 사용할 수 없고, 로그아웃 상태에서도 지울 내용을 확인한 뒤 실행합니다. 현재 날짜와 예시 자료 표시는 화면에 명시합니다.

**현재 한계:** 서버 상태와 초안은 로그인 계정별로 분리되어 조직의 다른 운영자 계정과 공유되지 않습니다. 브라우저 캐시는 서버 저장을 대체하지 않으며 저장 실패·버전 충돌을 확인해야 합니다. 다른 기기에서 운영 상태를 복원하는 전체 흐름과 안내 파일 저장은 별도 실사용 검증이 필요합니다. 실시간 공동 편집과 실제 발송 결과의 감사 모델은 없습니다.

### 2026년 10월 5일 과거 작업 기록: PLAN 1단계

- 운영자 정보는 `projects` 배열에 ID·이름·설명·시작일·마감 시각·운영 일정·신청 URL·담당자·대상 동료 ID·필수 동료 ID·확정 방식을 저장합니다. 신청 원본 역할은 별도 `applications` 배열의 `projectId`·`employeeId`·`status`(`applied`/`confirmed`/`cancelled`)·`checkedAt`이 맡습니다. 지금은 모두 브라우저에서 바꾸는 로컬 자료이며 외부 원본 조회는 없습니다.
- 프로젝트 상세의 신청·취소·확정 버튼이 기록을 바꿉니다. 즉시 확정형은 신청을 `confirmed`로, 별도 절차형은 `applied`로 기록합니다. 별도 절차형의 확정 대기자는 신청 인원에 포함되고 미신청 DM에서는 빠집니다. 대상 명단 외 기록은 집계에서 제외하고 건수를 알립니다.
- 신청률은 고유 대상 ID 중 유효한 신청 ID 수를 고유 대상 수로 나눕니다. 대상이 0명이면 신청률 대신 ‘대상 없음’을 표시합니다. 홈·상세·DM 명단은 `calculateStatus`의 같은 결과를 사용합니다.
- 당시 저장 형식은 로컬 저장소 version 3이었습니다. 이전 version 1의 안내 기록·완료 티켓·캘린더와 version 2의 운영 정보·신청 상태를 읽었습니다. 이후 계정별 서버 저장과 마지막 서버 상태를 포함한 로컬 캐시 version 7로 발전했습니다.
- 당시 새 프로젝트에는 화면 티켓이 없었고 별도 규칙 평가기만 있었습니다. 이후 실제 시각·공휴일 입력과 화면 티켓을 연결했습니다. 초기 예시 티켓은 가상 시점과 상태를 유지합니다.

### 등록 화면 피드백 반영

- 화면 이름을 ‘프로젝트 등록/수정’으로 바꾸고, ‘이름’은 ‘프로젝트 제목’, ‘담당자’는 ‘담당자 이름’으로 표시합니다. 등록 화면의 불필요한 안내 문장은 제거했습니다.
- 대상과 필수 동료를 ID 문자열 대신 이름 검색·팀 필터·검색 결과 일괄 선택·개별 체크로 지정합니다. 내부 식별자와 저장 형식은 그대로 유지합니다. 필수 체크는 대상 동료에만 적용됩니다.
- 여러 PDF·DOCX·TXT·MD와 붙여넣은 내용을 서버에서 읽고 Gemini로 분석합니다. 스캔 PDF OCR, 출처 검증, 누락·충돌 표시, 후보 선택·수정·적용을 지원합니다. 적용한 근거는 프로젝트와 함께 계정별 Supabase 상태에 저장하고 브라우저에도 복원용 캐시를 남깁니다. [SPEC 002의 9절](spec_002.md#9-기획서에서-프로젝트-정보-채우기)에 현재 계약과 제한을 정리했습니다.

## 15 Gemini 연결 확인 (2026-10-06)

- `npm run test:gemini`는 `.env`의 API 키·모델 설정으로 가상 문서 두 개의 핵심 정보 추출을 요청합니다. 키를 출력하지 않으며 일반 `npm test`와 분리했습니다.

- 이어서 등록 화면의 중복과 요약 패널 배치 오류를 수정했습니다. 이제 분석 결과의 명확한 단일 후보는 빈 등록 입력칸에 바로 채워지고, 기존 값은 유지됩니다. 별도의 `저장 전 운영 정보 요약`과 정상 후보의 중복 편집 카드는 표시하지 않습니다. 형식 확인·충돌·기존 값과 다른 후보만 결과 영역에서 선택해 입력하며, 원문 근거와 찾지 못한 정보는 접어서 볼 수 있습니다. 하단 등록 입력칸에서 직접 수정하면 해당 확인 항목도 해소됩니다. 로그인된 로컬 브라우저의 가상 메모로 자동 입력·기존 제목 보존·마감 형식 수정 후 입력·하단 입력칸의 직접 수정·요약 제거를 확인했습니다. 사용자 PDF·DOCX의 실제 결과와 운영 웹 배포는 대기 중입니다.
- 이어서 저장 전 요약을 등록 화면 안에 상시 표시하지 않고 별도 팝업에서 열도록 수정했습니다. `운영 정보 미리보기`는 현재 입력값의 요약을 보여주고, 등록/변경 저장도 같은 팝업을 거쳐 `확인하고 저장`을 눌러야 저장됩니다. 팝업의 `입력칸으로 돌아가기`나 Escape 키는 저장 없이 팝업을 닫습니다. 요약에는 무엇을·대상·해야 할 일·마감·언제·어디서·신청 방법·비용·예외·문의·링크와 각 출처·확인 상태가 표시됩니다. 운영 웹 배포는 대기 중입니다.
- 직접 등록한 프로젝트의 첫 안내 티켓이 곧바로 `종료`로 바뀌던 로컬 평가 경로를 수정했습니다. 첫 안내와 리마인드를 분리해 평가하며, 필수 대상이 없어도 자율 대상이 있으면 D-3·D-1 신청 현황 확인 티켓을 예정 상태로 만듭니다. 자율 신청 목표가 비어 있으면 목표 미달 판단 없이 현황만 확인합니다. 신청 원본이 최신이 아니면 대상 수를 채우지 않은 시점 확인 티켓으로 표시합니다. 등록/수정 팝업 상단에서 저장 전 예상 티켓을 볼 수 있고, 공휴일 기준이 확인되지 않았으면 정확한 리마인드 시각 대신 확인 필요 안내가 표시됩니다. 자동 테스트 113개가 통과했고 별도 비로그인 로컬 브라우저에서 팝업·미확인 달력 안내를 확인했습니다. 로그인된 실제 프로젝트의 티켓 복구·서버 저장·새로고침 복원과 운영 웹 배포는 대기 중입니다.

### 2026년 10월 6일 운영 상태·티켓·공지 카드 갱신

- 프로젝트, 대상 명단, 신청·취소 이력, 티켓, 보낸 안내를 Supabase `operator_states`에 버전 조건으로 저장하고 `operator_state_revisions`에 변경 당시 상태를 남깁니다. 브라우저 캐시는 복원용입니다. 저장 상태·탭 충돌을 표시합니다.
- 새 프로젝트와 변경된 신청 상태는 규칙 평가기로 티켓을 갱신합니다. 공휴일은 별도 키 없이 Nager.Date 한국 전국 `Public` 목록에서 조회합니다. 정부 원천 자료는 아니고 반영 시차가 있을 수 있습니다. 조회가 실패하거나 공휴일 응답이 검증되지 않으면 정기 점검 티켓을 만들지 않습니다. 등록 화면에서 프로젝트별 점검 시각·마감 전 간격·자율 기준·업무시간을 설정합니다. 보류·안내하지 않기 사유와 마감/운영 상태 변경 사유를 저장합니다.
- 문서 후보를 카드에서 직접 수정한 뒤 프로젝트에 반영하고, 검토 화면의 공지 정보 카드에서 항목을 수정·제외합니다. Gemini는 카드에 포함된 확인된 사실로 초안을 쓰며, 말투 변경만으로 본문을 재생성하지 않습니다. `Gemini로 새 초안 문구 생성` 버튼을 눌러 새 후보를 요청합니다. 확인되지 않은 URL·날짜는 서버가 거부합니다. 이전 구현 단계에서 가상 정보로 실제 Gemini 호출을 확인했으며, 이번 로컬 통합에서는 실제 Gemini를 다시 호출하지 않았습니다.
- 이후 로컬 사용성 수정에서 새 Gemini 문구를 본문 입력 칸에 직접 넣도록 바꿨습니다. 운영자 로그인 브라우저에서 실제 생성 결과가 입력 칸에 나타나고 되돌리기 버튼과 Supabase 저장 표시가 뜨는 것을 확인했습니다. 되돌리기 클릭과 이 새 문구의 새로고침 복원은 미확인입니다.
- Google Sheets 서비스 계정으로 예시 시트의 네 탭을 실제 조회·정규화했습니다(직원 160명·프로젝트 3개·신청 사건 17건·현재 신청 상태 11건). 수동 가져오기 화면 경로를 구현했으며, 로그인 화면에서 가져오기부터 Supabase 저장·복원까지는 통합 검증이 남았습니다. Slack 전송, 조직 공동 권한, 원본 기획서 보존 정책도 별도 작업입니다.

### 2026년 10월 7일 새 시트 프로젝트 ID 등록

- 새 프로젝트 등록 시 시트 `프로젝트` 탭의 `projectId`를 입력할 수 있습니다. 비워 두면 내부 ID가 생성됩니다. 기존 프로젝트 ID는 화면에서 바꿀 수 없습니다. ID가 같은 시트 프로젝트의 대상·신청이력은 다음 동기화에서 연결됩니다. ID 입력 검사는 로컬 자동 테스트만 확인했고, 새 시트 프로젝트의 브라우저 등록·저장·가져오기·복원과 배포 사이트는 미확인입니다.
