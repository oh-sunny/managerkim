# SPEC 002 · 기획서 입력, 대상 선택, 안내 자료와 초안

작성일: 2026년 10월 5일  
상태: **일부 구현 · 여러 자료 분석과 OCR 웹 연결 완료 (2026-10-06)**

이 문서는 [PRD](../docs/PRD.md)의 기획서 입력과 안내 검토·발송 흐름을 확장한다. [spec_001](spec_001.md)은 현재 프로토타입의 동작, [PLAN](../docs/PLAN.md)은 구현 순서, [데이터 구조 초안](../docs/data-architecture.md)은 서버 저장의 큰 틀을 설명한다. Supabase 초안 저장과 여러 PDF·Word·텍스트의 Gemma 분석·OCR·근거 검토를 연결했다. 실제 Slack 첨부와 조직별 자료 보관·검사 정책은 후속이다. 현재 자료 분석 계약은 9절에 적는다.

## 1. 목표와 범위

운영자가 안내를 준비할 때 **필수 신청 대상 중 아직 신청하지 않은 동료를 즉시 찾고 선택**할 수 있어야 한다. 이번 안내에 사용할 링크와 파일을 명시적으로 고른 뒤, 최종 확인 화면과 실제 발송 결과, 보낸 안내 상세에서 같은 자료를 확인할 수 있어야 한다. 수정한 초안은 화면을 벗어나거나 새로고침해도 복구할 수 있어야 한다.

프로젝트를 등록할 때는 기획서에서 운영 정보의 후보와 근거를 찾아 운영자가 확인한 값만 적용한다. PDF·DOCX와 선택적 AI 해석으로 입력 범위를 넓히는 흐름은 9절에서 다룬다.

기획서·관련 문서를 프로젝트 정보 추출에 넣는 동작과 **동료에게 보낼 안내 자료로 지정하는 동작**은 구분한다. 추출용 원본은 자동으로 메시지에 첨부되지 않는다. 운영자가 발송용으로 선택한 자료만 이번 안내에 포함한다.

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| S2-01 | 필수/자율과 신청 상태를 나눠 보여주고 필수 미신청자를 한 번에 DM 대상으로 선택 | 필수 |
| S2-02 | 안내별 링크와 파일을 선택·검토하고 Slack 전송에 반영 | 필수 |
| S2-03 | 실제 발송 시점의 원문·링크·파일·대상·결과를 이력에 고정 | 필수 |
| S2-04 | 본문·대상·자료 등 발송 전 초안 자동 임시 저장·복원. 발송 확인 체크는 복원하지 않음 | 필수 |
| S2-06 | 본문·첨부 자료의 민감 정보 검사와 운영자 검토를 거쳐 발송 | 필수 |
| S2-05 | 여러 PDF·DOCX·텍스트에서 근거 있는 운영 정보 후보를 추출하고 OCR·충돌 검토 후 적용 | 구현 |
| S2-07 | 구성원의 행동에 필요한 정보 카드를 수정·제외한 뒤 안내 유형·말투별 초안을 생성 | 기본 흐름 구현 · 실제 사용성 검증 필요 |

## 2. 필수 신청 대상 선택

### 2.1 화면과 선택 규칙

`보낼 내용 확인 > 보내는 방법과 대상`에서 프로젝트 대상 명단과 **마지막으로 성공한 신청 상태 조회**를 기준으로 다음 수치를 분리한다.

| 표시 | 계산 | 용도 |
| --- | --- | --- |
| 필수 대상 | `project_targets.required = true`인 고유 동료 | 전체 필수 규모 |
| 필수 · 신청 전 | 필수 대상 중 유효한 신청/확정 기록이 없는 동료 | 기본 리마인드 대상 |
| 자율 · 신청 전 | 자율 대상 중 유효한 신청/확정 기록이 없는 동료 | 선택적 안내 대상 |
| 신청 또는 확정 | 유효한 신청 또는 확정 기록이 있는 동료 | 재신청 안내에서 제외 |

취소되어 유효한 신청이 없다면 `신청 전`으로 계산한다. 별도 승인·선정 방식에서는 신청 완료 후 승인 대기인 동료도 미신청자로 취급하지 않는다. 명단에서 식별되지 않는 동료와 조회 실패 상태는 임의로 `신청 전`에 넣지 않고 확인 필요로 표시한다. 숫자와 개인 목록은 동일한 계산 결과를 사용한다.

- 기본 수신 범위가 `신청 전`인 티켓에는 상단에 **`필수 · 신청 전 5명`** 같은 요약과 **`필수 미신청자 5명 선택`** 버튼을 둔다. 누르면 DM·개인 선택 모드로 이동하고 해당 ID만 한 번에 선택한다. 사용자가 이후 개별 추가·해제할 수 있다.
- 최초 공지처럼 이미 신청한 필수 대상까지 보내야 할 때는 별도 **`필수 대상 전체 선택`** 동작을 제공한다. 이 동작은 현재 티켓의 신청 상태 범위가 아니라 프로젝트의 필수 대상 전체를 선택하므로, 신청자 포함 여부를 버튼과 확인 화면에 드러낸다. 리마인드에서 기본 추천은 항상 `필수 · 신청 전`이다.
- 개인 목록은 `필수 · 신청 전`, `자율 · 신청 전`, `신청/확정` 순서로 묶고 각 행에 필수/자율, 신청 상태, 팀을 표시한다. 검색·팀 필터를 써도 현재 선택 수와 필수 선택 수는 전체 기준으로 유지한다. 선택 버튼은 **기존 개인 선택을 해당 집합으로 교체**하므로 `…만 선택` 문구와 적용 후 인원을 보여준다.
- 팀 전체 선택을 유지하되 선택된 팀에 필수/자율이 섞이면 요약에 각각 몇 명인지 표시한다. 필수만 보내려면 필수 빠른 선택을 사용하도록 연결한다. 중복 ID는 한 명으로 계산한다.
- 채널 게시는 개인별 필수 대상에게만 발송하는 수단이 아니다. 채널 모드에서는 `필수 5명에게만 안내` 같은 표현을 쓰지 않고, 선택 채널의 전체 공개 범위와 프로젝트 대상 밖의 열람 가능성을 보여준다. 필수 개인만 대상으로 하려면 DM으로 전환한다.
- 최종 확인 창에는 **필수 선택 인원 / 자율 선택 인원**, 실제 수신자 이름·팀·신청 상태, 원본 조회 시각을 표시한다. 개인 선택 0명, 최신 상태 확인 실패, 대상 변경이 있으면 승인·발송을 막고 다시 확인한다. 승인 뒤 신청·취소로 수신 명단이 달라지면 승인을 해제한다.

### 2.2 예시

연례 건강검진의 대상 120명, 신청 108명, 신청 전 12명 중 필수 미신청 5명이라면 `필수 미신청자 5명 선택`을 눌렀을 때 DM 수신자는 **그 5명만** 된다. 나머지 자율 미신청 7명은 자동으로 포함되지 않는다. 단, 운영자가 수동으로 추가할 수 있고 최종 확인 창에는 `필수 5명 · 자율 2명`처럼 구분한다.

## 3. 안내용 링크와 파일

### 3.1 자료 등록과 초안 편집

프로젝트에는 재사용 가능한 `안내 자료` 목록을 둔다. 항목 유형은 **링크**(표시 이름·URL)와 **파일**(표시 이름·원본 파일명·형식·크기·버전)이다. 프로젝트 등록 시 넣은 기획서나 추출용 파일은 별도 분류이며 발송용 목록에 자동 등록하지 않는다. 운영자가 해당 자료를 안내용으로 명시적으로 추가하고 접근 가능 여부를 확인해야 한다.

`보낼 내용 확인` 화면에 `이번 안내에 포함할 자료` 영역을 둔다.

1. 기존 프로젝트 자료 선택 또는 새 링크·파일 추가.
2. 링크는 표시 이름과 URL을 확인하고 **본문에 삽입**한다. 선택한 링크가 본문에서 삭제되거나 바뀌면 발송 전 충돌을 표시해 다시 삽입하거나 선택을 해제한다.
3. 파일은 별도 **첨부 카드**로 보여준다. 파일을 본문 URL 한 줄로 대체하지 않는다. 카드에 이름·형식·크기·버전을 표시하고 제거할 수 있다.
4. 운영자가 본문에 직접 붙인 URL도 저장 시 추출해 `본문 링크`로 표시한다. 자료 목록에서 고른 링크와 중복이면 하나의 URL로 묶되 출처를 유지한다. 직접 입력한 URL은 선택 자료와 별도로 최종 확인 대상에 포함한다.
5. 신청 링크처럼 프로젝트 운영 정보에서 온 URL도 **해당 안내 본문에 들어간 경우** 발송 당시 URL로 기록한다. 원본 프로젝트 URL이 나중에 바뀌어도 과거 안내의 URL을 바꾸지 않는다.

URL은 형식과 허용 스킴(`https:`)을 검사한다. 실제 접근 권한·내용·유효기간은 자동 검사가 보장하지 않으므로 운영자 확인 항목으로 둔다. 파일은 서버에서 허용 형식·크기·안전 검사·접근 권한을 확인하고 비공개 저장소에 보관한다. 허용 형식·최대 크기·보존 기간과 Slack으로 외부 업로드해도 되는 자료의 범위는 조직 정책 확정 후 설정값으로 관리한다. 임시 서명 URL이나 저장소 비밀 경로를 메시지 본문에 넣지 않는다.

### 3.2 Slack 전송과 실패 처리

실제 연동 단계에서는 서버가 승인된 본문과 파일의 **고정 버전**을 읽어 각 DM 수신자 또는 선택 채널에 전송한다. 링크는 본문 텍스트의 URL로 보내고, 파일은 Slack 파일 업로드 방식으로 첨부한다. 여러 파일과 여러 목적지를 지원하되, 한 목적지의 본문 성공을 다른 목적지나 파일의 성공으로 간주하지 않는다. Slack SDK의 [`filesUploadV2`](https://docs.slack.dev/tools/node-slack-sdk/web-api/) 등 현재 지원되는 업로드 방식을 연동 시점에 재검증한다. [Slack 파일 안내](https://docs.slack.dev/messaging/working-with-files/)에 따라 Slack에 업로드한 파일과 원격 파일 참조도 구별한다.

발송 직전에는 선택한 파일이 존재하고 승인한 버전과 해시가 일치하는지, 링크가 본문과 일치하는지, 전송 권한과 대상이 유효한지 검사한다. 자료가 삭제·교체되거나 본문·링크·파일·대상·채널이 수정되면 이전 승인을 해제한다. 파일 업로드만 실패한 경우에도 그 목적지는 `부분 실패`로 표시하고 어떤 파일이 실패했는지 남긴다. 응답이 없어 결과를 알 수 없으면 `결과 불명`으로 기록한다. 재시도는 목적지·파일 단위의 기존 결과를 확인한 뒤 수행하며, 전체 발송을 무조건 반복하지 않는다.

현재 프로토타입의 모의 발송에서는 실제 Slack 업로드가 없음을 분명히 표시한다. 모의 기록은 선택한 첨부 정보의 스냅샷을 남길 수 있지만 Slack 파일 ID·실제 첨부 성공으로 표시하지 않는다.

## 4. 최종 확인과 보낸 안내 상세

`보내기`를 활성화하는 최종 확인 창은 다음을 한 화면에서 보여준다.

- 확정할 **본문 전체**와 본문에 들어간 링크 목록(표시 이름·URL)
- 파일 카드 목록(파일명·형식·크기·버전)
- DM이면 필수/자율 인원과 이름·팀, 채널이면 선택 채널별 공개 범위
- 신청 현황의 마지막 성공 조회 시각, 변경·누락·접근 확인 경고

운영자가 이 내용을 확인해야 승인 체크가 완료된다. 최종 확인 뒤 본문·링크·파일·대상·방식·채널 중 하나가 바뀌면 체크를 해제한다. 화면을 새로 열거나 새로고침하면 확인 체크가 사라지며, 저장된 초안 내용을 다시 검토해야 한다.

`보낸 안내` 목록의 프로젝트·최초 공지/리마인드 구분을 유지하고, 행에는 `링크 2개 · 파일 1개`처럼 자료 수를 표시한다. 상세 화면에는 당시의 본문과 함께 아래 항목을 **발송 시점 스냅샷**으로 보여준다.

| 항목 | 상세에서 보일 내용 |
| --- | --- |
| 본문 링크 | 발송 당시 표시 이름·정확한 URL·출처(선택 자료/직접 입력/신청 링크). 현재 URL로 덮어쓰지 않음 |
| 첨부 파일 | 당시 이름·형식·크기·파일 버전·해시. 보존 중인 원본 다운로드 가능 여부와 Slack 파일 링크는 각각 구분 |
| 발송 결과 | 목적지별 시각·상태(성공/부분 실패/실패/결과 불명)·Slack 메시지/파일 ID 및 링크(있는 경우) |
| 기록 출처 | 모의 발송/실제 연동 발송/수동 기록과 확인 수준 |

이전 기록에 자료 필드가 없으면 `당시 첨부 정보가 기록되지 않음`으로 표시한다. 명시적으로 빈 목록을 저장한 기록만 `첨부 없음`으로 표시한다. 수동으로 입력한 외부 발송 기록의 링크·파일은 운영자 진술임을 밝히며 실제 Slack 전송 증거처럼 다루지 않는다. 발송 스냅샷을 수정하지 않고 정정 이력을 별도 사건으로 남긴다. 보존 기간이 지나 원본 파일을 더는 열 수 없어도 이름·형식·크기·버전·발송 결과 메타데이터는 정해진 이력 보존 정책에 따라 유지한다.

## 5. 초안 임시 저장과 복원

### 5.1 저장 범위와 사용자 경험

초안은 티켓 또는 별도 안내 작성 건의 **안정적인 초안 ID**로 구분한다. 본문, 말투, 발송 방식, 신청 상태 범위, 팀/개인/채널 선택, 링크·파일 선택과 순서, 수정 시각, 수정 주체, 버전을 저장한다. **확인 체크는 초안에 저장하지 않고 복원하지 않는다.** 새로고침이나 다른 기기에서 초안을 다시 열면 본문과 선택은 복원되지만 보내기 버튼은 잠겨 있다. 운영자가 현재 본문·대상·자료·채널을 확인 창에서 다시 검토해야 체크가 적용된다. 발송 직전에는 최신 신청 현황과 자료 버전을 서버가 다시 검증한다.

- 본문 입력과 선택 변경 후 약 1초간 입력이 멈추면 자동 저장한다. 화면 이동 시에도 저장을 시도한다. `저장 중`, `임시 저장됨 · 시각`, `저장 실패 · 다시 시도`를 분명히 보여준다. 실패 시 저장된 것처럼 표시하지 않는다.
- 새로고침·브라우저 재시작 후 같은 안내에 돌아오면 마지막 저장본을 복원한다. 보내기 또는 명시적 폐기 후에는 초안을 완료/폐기 상태로 두어 새 작성 화면에 잘못 복원하지 않는다.
- 말투 변경으로 본문을 재생성할 때 현재 직접 수정한 본문을 덮어쓸 수 있음을 보여주고, 이전 본문을 되돌릴 수 있는 초안 버전을 남긴다. 템플릿·AI가 다시 만들어도 링크·첨부 선택을 몰래 제거하지 않는다.
- 다른 탭이나 장치에서 더 최신 버전이 저장되었다면 조용히 덮어쓰지 않고 충돌을 표시한다. 서버 저장은 버전 조건을 사용한다. 브라우저 오프라인·용량 부족·업로드 미완료 상태를 저장 완료로 오인하지 않는다.

### 5.2 저장 단계

| 단계 | 저장 방식 | 제한 |
| --- | --- | --- |
| 로컬 프로토타입 | 본문과 선택 메타데이터를 브라우저 저장소에 저장. 파일 본문을 유지하려면 IndexedDB 등 별도 로컬 파일 저장 수단을 쓰고, 없으면 재선택 필요 상태로 표시 | 같은 브라우저·기기·출처에서만 복원. 실제 Slack 첨부 불가 |
| 서버/DB 연결 후 | `notice_drafts`와 초안 버전·자료 연결을 DB에, 파일은 비공개 객체 저장소에 저장 | 로그인·프로젝트 접근 제한, 보존/삭제 정책, 버전 충돌 처리 필요 |

`localStorage`에 파일 바이너리, Slack 토큰, 비공개 파일의 임시 접근 URL을 저장하지 않는다. 파일 메타데이터만 저장된 상태를 실제 업로드 완료와 구분한다. 서버 전환 시 로컬 초안의 이전 여부를 별도로 결정하고, 자동 동기화된 것처럼 표현하지 않는다.

### 5.3 본문·자료의 민감 정보 검사

발송용 파일과 본문이 저장되면 서버에서 해당 버전의 텍스트를 추출하고 검사한다. 텍스트 PDF·문서뿐 아니라 스캔된 PDF·이미지는 OCR이 필요하다. 검사 규칙은 개인 식별 번호, 연락처·주소·계좌 같은 식별 정보와 건강검진 **개인 결과**처럼 문맥에 따라 민감한 정보를 포함한다. 일반적인 건강검진 안내문과 개인별 검진 결과는 구분해야 한다. 첫 버전은 명확한 형식의 탐지와 사람이 확인할 수 있는 의심 문구 표시로 시작하며, AI 분류를 쓰려면 조직이 외부 처리 범위를 먼저 정한다.

검사 상태를 `대기/검사 중/검토 필요/통과/검사 실패`로 보여준다. 탐지 항목마다 유형과 파일의 페이지·위치 또는 본문 위치를 보여주고, 실제 값은 화면에 필요한 만큼만 표시한다. 담당자는 해당 내용을 삭제·가림 처리한 새 버전을 올리거나 자료를 제외하고 재검사한다. 정책상 허용되는 예외는 확인자·사유·시각을 남긴다. 검사가 실패하거나 의심 항목이 미해결이면 발송을 막는다. 자동 검사에서 탐지하지 못한 정보가 있을 수 있으므로 `통과`는 안전 보증이 아니며 최종 본문·자료·게시 채널은 사람이 확인한다. 파일이나 본문 버전이 바뀌면 이전 검사 결과를 재사용하지 않는다.

## 6. 최소 데이터 계약

아래는 물리 테이블 확정 전의 **논리 구조**다. 모든 ID는 이름이나 팀명이 아닌 안정적인 식별자이며 시각은 시간대를 포함한다.

| 데이터 묶음 | 필수 속성 | 불변/변경 규칙 |
| --- | --- | --- |
| `project_resources` | `id`, `projectId`, `kind`(link/file), `label`, `url` 또는 비공개 파일 키, `version`, 파일명·MIME·크기·SHA-256, 상태, 생성/수정자·시각 | 새 파일 업로드·링크 수정은 새 버전. 추출용 `project_inputs`와 별개 |
| `notice_drafts` | `id`, `projectId`, `ticketId`, `body`, `tone`, `mode`, `scope`, 대상 선택 규칙·명시 ID·채널 ID, `version`, `updatedAt`, `updatedBy`, 상태 | 변경마다 버전 증가. 승인과 분리 |
| `notice_draft_resources` | 초안 ID, 자료 ID·버전, 포함 방식(link/file), 순서, 본문 반영 여부 | 선택 변경은 초안 버전 변경·승인 해제 |
| `notice_approvals` | 초안 ID·버전, 본문/자료/대상/채널 서명, 승인자·시각, 신청 원본 조회 시각 | 서명과 실행 직전 상태가 다르면 승인 무효 |
| `resource_scans`, `resource_scan_findings` | 자료/본문 버전·해시, 검사 상태·시각·규칙 버전, 탐지 유형·위치·검토자·사유 | 버전 변경 시 재검사. 민감한 값 전문을 기본 보관하지 않음 |
| `notice_send_attempts` | 시도 ID·승인 ID, 원문 스냅샷, 대상/채널 스냅샷, 링크/파일 스냅샷, 시작·완료 시각, 출처 | 시도 이후 원문과 자료 목록을 덮어쓰지 않음 |
| `notice_delivery_results` | 시도 ID, 목적지 ID, 본문 결과, 파일별 결과, Slack 메시지/파일 ID·링크, 오류·시각 | 목적지별 성공·실패·결과 불명 분리. 재시도는 이전 결과와 연결 |

링크 스냅샷은 `label`, `url`, `origin`, `resourceId/version`(있을 때)을 포함한다. 파일 스냅샷은 `resourceId/version`, 원본 파일명, MIME, 크기, SHA-256, 저장/보존 상태를 포함한다. 실제 Slack 결과는 발송 전 스냅샷과 분리해 결과가 도착할 때 기록한다. 프로젝트 자료 수정이나 파일 삭제가 과거 안내의 화면·증거를 변경하지 않아야 한다.

## 7. 구현 순서와 인수 조건

[PLAN](../docs/PLAN.md)의 **3단계**에서 필수 대상 빠른 선택, 자료 선택 UI, 모의 발송 스냅샷, 로컬 초안 저장·복원을 만든다. **4A**에서 인증된 서버 초안/파일 저장과 버전 충돌·접근 제어를, **4C**에서 민감 정보 검사·검토 차단과 실제 Slack 파일 업로드·목적지별 결과를 연결한다. 기획서의 PDF·DOCX·선택적 AI 해석은 **5단계**에서 확장한다. 단계별 완료 상태는 구현 후 PLAN과 spec_001에 반영한다.

1. 건강검진 예시에서 `필수 · 신청 전 5명`을 한 번에 고르면 DM 대상이 정확히 5명이며 자율 미신청 7명은 포함되지 않는다. 개별 추가·해제 및 팀 선택 후에도 구분 수치가 맞는다.
2. 신청 완료·승인 대기자는 필수 미신청자 빠른 선택에 들어가지 않는다. 발송 전 신청 상태가 변하거나 조회에 실패하면 기존 승인이 취소되고 발송을 막는다.
3. 링크 1개와 파일 1개를 고른 뒤 최종 확인에 본문 URL과 첨부 카드가 각각 보인다. 선택 파일이 바뀌거나 없어지면 재승인을 요구한다. 모의 발송 기록에도 당시 자료 목록이 남는다.
4. 실제 연동에서 DM 여러 명 또는 채널 여러 곳에 보냈을 때 목적지별 본문·파일 결과가 기록된다. 한 곳의 파일 업로드 실패가 전체 성공으로 표시되지 않고, 결과 불명 목적지에 무조건 다시 보내지 않는다.
5. 보낸 안내 상세에서 당시 원문·URL·파일 버전·발송 결과를 확인한다. 이후 프로젝트 자료를 바꿔도 과거 기록은 그대로이며, 예전 기록의 자료 정보 부재와 실제 `첨부 없음`이 구분된다.
6. 본문·대상·자료를 수정하고 새로고침하면 마지막 **저장 완료** 버전이 복원된다. 저장 실패는 실패로 표시된다. 확인 체크는 항상 비워지고 보내기 버튼은 잠긴다. 다른 탭의 최신 버전을 덮어쓰지 않는다.
7. 기획서에서 찾은 후보마다 원문과 위치를 확인할 수 있고, 누락된 값은 추측하지 않는다. 서로 다른 마감일이나 대상이 발견되면 운영자가 충돌을 해결하기 전에는 확정 정보에 적용하지 않는다.
8. 개인 건강검진 결과가 담긴 파일을 첨부하면 위치와 이유가 `검토 필요`로 표시되어 보내기가 잠긴다. 삭제·가림 처리한 새 버전은 재검사하고, 읽을 수 없는 파일은 검사 실패로 차단한다. 일반 안내문도 최종 담당자 검토를 거친다.

## 8. 연동 전 확정할 운영 설정

실제 조직 자료와 Slack을 연결하기 전에 허용 파일 형식·최대 크기, 파일 악성코드 검사 방식, DM과 채널에 올려도 되는 문서의 보안 등급, 비공개 채널·외부 공유 채널 허용 범위, 원본 파일과 발송 이력의 보존 기간, 다운로드 권한을 확정한다. 이 값들은 배포 환경의 정책 설정으로 관리하고 최종 확인 화면에서 적용된 제한을 보여준다.

## 9. 기획서에서 프로젝트 정보 채우기

### 9.1 업로드와 분석

프로젝트 등록·수정 화면에서 PDF·DOCX·UTF-8 TXT·MD 여러 개와 붙여넣은 내용을 함께 분석한다. ‘자료 분석하기’를 눌러야 Google Gemma로 전송한다. 분석은 기존 Supabase 운영자 세션 인증과 동일 출처 검사를 통과한 요청만 받는다. 전달되는 텍스트·페이지 이미지, 원본 미보관, 공지 자동 첨부가 아님을 화면에 표시한다.

| 제한 | 현재 값 |
| --- | --- |
| 파일 | 최대 6개, 각 2MB·합계 2.8MB |
| PDF | 파일당 30쪽 |
| OCR | 전체 최대 8쪽 |
| 텍스트 | 붙여넣기 및 전체 추출 결과 각각 8만 자 이내 |
| API 요청 | JSON 최대 4.1MB (파일은 base64) |
| 처리 시간 | 모델 호출당 최대 65초, 분석 전체 모델 호출 예산 140초, 화면 대기 155초 |

서버는 확장자·파일 서명·크기·DOCX 압축 해제 크기를 검사한다. 읽기 실패·암호화·빈 자료·제한 초과는 해당 파일과 이유를 표시하며, 일부 파일을 몰래 제외한 채 분석을 완료하지 않는다. 바이러스 검사나 문서의 안전성 보증은 구현하지 않았다. PDF의 텍스트는 페이지 위치, DOCX는 본문/표/머리말/꼬리말/각주/미주의 문단 위치를 유지한다. Word 안에 삽입된 이미지는 OCR 대상이 아니며 PDF로 저장해 입력할 수 있다.

텍스트가 적거나 대체 문자가 포함된 PDF 페이지는 서버에서 이미지로 렌더링해 Gemma의 이미지 입력으로 전사한다. 텍스트와 이미지가 섞인 PDF는 운영자가 ‘PDF 전체를 이미지로 읽기’를 선택할 수 있다. OCR 결과에는 자료·페이지와 OCR 표시를 남기며 판독 불가 문자는 추측으로 보정하지 않도록 요청한다. 빈 결과·누락된 OCR 페이지는 오류로 처리한다. OCR 인용 검사는 인식된 텍스트와의 일치만 확인하므로 원본 픽셀의 정확성까지 보장하지 않는다.

### 9.2 핵심 정보와 근거 계약

Gemma는 제목, 목적·설명, 담당자, 신청 시작, 마감, 행사 일정, 장소, 대상 설명, 신청 방법·유의사항, 정원·선정 조건, 신청 링크, 확정 방식, 종류의 후보를 반환한다. 신청률 계산·대상 동료 ID 확정·공지 발송은 수행하지 않는다.

결과는 원문 전사가 아닌 **공지에 사용할 편집된 핵심 정보**다. 목적은 직원에게 안내할 내용을 한 문장으로, 대상은 필수·자율 조건과 인원을 보존한 짧은 문구로, 신청 방법은 여러 자료를 합친 3~5줄의 행동 목록으로 작성하도록 요청한다. 문서 작성 목적·버전·중복 표현은 제외한다. 보완 관계인 절차를 문서별 충돌로 나누지 않으며 실제 모순만 선택 대상으로 남긴다. 요약 정확성은 운영자 검토 대상이다.

속도를 위해 원문 발췌에 짧은 ID를 붙이고 모델은 요약값과 근거 ID만 반환한다. 서버가 ID를 실제 원문·위치에 연결하고 기존 검증을 수행한다. 존재하지 않는 ID는 근거로 인정하지 않는다. 추출 출력 한도는 5,000토큰, OCR은 12,000토큰이다. 별도 요약 호출은 추가하지 않는다. 화면은 실제 경과 시간을 표시하며 PDF 전체 이미지 인식은 추가 설정에 배치한다. 스캔 자동 OCR은 유지한다.

응답은 분석 ID·시각·모델, 자료 ID·이름·SHA-256·추출 구간, 필드별 후보·근거·상태로 구성한다. 각 근거의 sourceId/segmentId가 실제 입력에 있고 인용 문구가 그 구간에 포함되는지 서버가 확인한다. 근거 없는 후보는 제외하고 확인 필요로 표시한다. 이 검사는 인용 존재 여부이며 의미 해석의 정확성은 운영자가 검토한다.

모델이 완전한 JSON 객체 앞뒤에 설명·마크다운을 붙이면 객체를 분리해 해석한다. 잘린 괄호나 인용 문구를 임의로 복구하지 않는다. JSON 문법 오류·빈 응답·출력 길이 초과는 남은 시간 안에서 원본 자료로 한 번 자동 재요청한다(OCR·핵심 정보 추출을 합쳐 최대 1회). 출력 중단 사유를 확인해 길이 초과·생성 중단·형식 오류를 구분하며, 중단된 응답의 일부를 정상 결과로 채택하지 않는다. 실패 로그에는 단계·오류 코드·종료 사유·응답 길이·경과 시간·재요청 여부만 기록하며 원문·모델 응답·API 키는 기록하지 않는다.

서로 다른 후보는 나란히 표시한다. 최신·확정 자료가 있어도 이전 날짜·링크를 자동 선택·삭제하지 않는다. 명시적 날짜·링크는 규칙 추출 결과도 합쳐 모델이 옛 자료를 생략하는 경우를 줄인다. 같은 날짜의 한국어·ISO 표기는 통일한다. 시간이 없는 마감과 범위형 일정은 원문 후보로 보여주되 필드에 적용하려면 운영자가 확인한 형식으로 수정해야 한다. 없는 값은 ‘자료에 없음’으로 표시하고 새 프로젝트의 날짜·확정 방식에 임의 기본값을 넣지 않는다.

### 9.3 선택 적용과 저장

결과 화면은 제목·목적·대상·마감·일정·신청 방법 순서의 간결한 노트로 표시한다. 수정 입력과 원문 근거는 항목별로 접고, 없는 항목은 한 곳에 모은다. 충돌·근거 확인 필요·형식 미완성 후보는 선택하지 않는다. 단일 정상 후보는 현재 값이 비어 있거나 같은 경우 체크해 두되, 기존 값과 다르면 선택하지 않는다. 체크는 적용 승인 자체가 아니며 운영자가 ‘검토한 정보 반영’을 눌러야 값을 채운다. 체크를 해제하면 기존 값은 유지된다. 하나라도 형식 오류가 있으면 전체 적용을 중단한다. 대상 설명을 적용해도 실제 동료 명단·필수 대상은 자동 선택하지 않는다.

프로젝트 저장 시 적용한 값·원래 후보·근거 문구·파일 해시·분석 및 적용 시각·모델·수정 여부를 프로젝트의 sourceReviews에 보관한다. 재편집 화면에서 근거를 다시 볼 수 있다. 프로젝트 저장소는 현재 브라우저 localStorage이며 서버 저장·다른 기기 공유가 아니다. 원본 파일·전체 추출 텍스트·미적용 후보는 서버/DB에 보관하지 않고 요청·화면 메모리에서만 처리한다. 화면 이동·새로고침으로 선택 파일·미적용 분석이 사라진다. 외부 AI 제공자의 보존 정책과 앱의 미보관은 별개다.

자료를 추가·제외하거나 붙여넣은 내용·OCR 옵션을 바꾸면 이전 결과를 무효화한다. 실패 시 선택한 자료를 유지해 재시도할 수 있다. 취소·화면 이동 이후 도착한 결과는 적용하지 않으며, 취소는 서버의 이미 시작된 요청·과금 취소를 보장하지 않는다. 같은 서버 인스턴스에서 한 운영자의 동시 분석을 차단하며, 배포 전체의 사용량 제한은 후속이다.

### 9.4 검증과 후속 범위

혼합 PDF·DOCX 추출, 실제 Gemma OCR·통합 분석, 날짜·링크 충돌, 없는 정보, 원문에 없는 인용 제외, 형식·크기 오류, 인증·출처·동시 실행 경계를 검증한다. 웹에서는 파일 선택 → 로그인 → 분석 → 후보 선택 → 적용 → 저장·재편집 흐름을 확인한다. 라이브 모델 검증과 자동 테스트의 모의 모델 검증을 구분한다.

원본 비공개 서버 저장·보존/삭제 정책, 정교한 악성코드 검사, 표·도형·손글씨의 정확도 평가, 조직별 접근 정책, AI 공지 초안 생성은 후속이다. 현재의 자료 분석 결과를 자동 발송 승인으로 사용하지 않는다.

## 10. 공지용 정보 카드와 초안 생성 (S2-07 · 미구현)

[PRD의 공지용 정보 카드](../docs/PRD.md)를 구현할 때의 계약이다. 현재 9절의 Gemma 분석은 프로젝트 등록 필드의 후보를 찾아 적용한다. **이번 안내의 행동·마감·비용·예외를 따로 확정하는 카드와 카드 기반 초안 생성은 아직 구현하지 않았다.**

1. 업로드한 기획서·관련 자료와 운영자가 확정한 프로젝트 정보에서 이번 안내에 필요한 후보를 만든다. 최초 공지·신청 요청·리마인드 등 안내 목적을 먼저 지정하고, 신청 현황을 쓰는 리마인드에는 성공한 원본 조회 시각을 함께 표시한다.
2. 카드 항목은 `what`, `audience`, `action`, `deadline`, `whenWhere`, `how`, `costSupport`, `exceptions`, `contact`, `resources`로 구분한다. `action`과 `deadline`을 설명 문단에 합치지 않는다. 각 항목은 표시값, 원문 근거와 위치, 출처 종류(문서·확정 운영 정보·담당자 입력), 상태(`found`·`needs_review`·`conflict`·`not_applicable`), 이번 안내 포함 여부를 가진다.
3. 모델이 없는 값을 추측하거나 여러 자료의 충돌을 임의 해결하지 못하게 한다. 날짜만 있으면 시각은 비워 둔다. 링크는 원문과 일치하는지 확인하고, 첨부할 파일은 추출용 입력과 별도로 운영자가 선택한다. 문서의 비용·예외 문구를 생략하거나 단정적으로 바꾸면 담당자가 원문과 대조할 수 있어야 한다.
4. 담당자가 항목별 값을 확인·수정·제외해 카드를 확정한다. 직접 입력·수정한 값은 문서 확인값과 구분한다. 신청 요청인데 행동 또는 적용되는 마감이 확인되지 않았다면 확인 필요로 표시하고 발송 가능한 사실인 것처럼 자동 완성하지 않는다.
5. 확정 카드에서만 `친근한 공지`·`정중한 공지`·`마감 강조 공지`·`리마인드 공지` 등 초안을 만든다. 톤을 다시 선택해도 카드의 대상·행동·마감·링크는 유지하고, 제외한 항목은 다시 넣지 않는다. 생성된 본문은 기존 초안 저장·버전 충돌·최종 확인 흐름을 따른다.

**인수 조건:** 행동과 마감이 독립적으로 보이고, 근거 없는 `18:00`·회사 지원·변경 제한 같은 사실이 생성되지 않는다. 누락·충돌은 담당자 확인 대상으로 남는다. 운영자가 제외한 내용은 어떤 톤에서도 되살아나지 않으며, 저장한 카드 버전과 실제 보낸 본문을 나중에 대조할 수 있다. 정보 카드 없이도 현재의 직접 입력·템플릿 방식은 계속 사용할 수 있다.
